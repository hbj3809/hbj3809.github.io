이벤트 스트림 처리

개요배경⁠·요구⁠·범위

제약사 이커머스 몰은 결제⁠·정산⁠·회원⁠·주문이 하나의 Spring Boot 모놀리스에 들어 있었고, PG사 결제 SDK도 그 안에 직접 포함돼 있었습니다. 기준은 하나였습니다. 정산과 ERP(SAP) 인터페이스에는 한 치의 오차도, 이슈도 없어야 한다는 요구였습니다. 이 기준에 맞춰 결제 모듈과 통합 인터페이스 모듈을 MSA로 분리하고, 정산⁠·거래원장 처리를 Kafka Streams 이벤트 처리로 바꿨습니다.

  • 범위결제⁠·통합 인터페이스 모듈 분리, PG 연동 REST API 전환, Kafka Streams 원장⁠·정산 처리, SAP 비동기 연동, 자체 ELK 검색, CI/CD⁠·모니터링
  • 요구정산⁠·ERP 인터페이스는 오차⁠·이슈 없이 동작, 결제 모듈 독립 배포, 정산 배치의 DB 부하 해소, 상용 검색 라이선스 비용 제거
  • 결제수단예치금⁠·적립금⁠·쿠폰⁠·기타 결제수단
  • 협업Kafka에 익숙하지 않은 개발진을 위해 마지막 1개월 동안 Kafka 현황 대시보드와 Grafana 모니터링까지 제공

전체 아키텍처

몰의 Web⁠·Mobile 요청은 API Gateway를 거쳐 결제⁠·정산⁠·원장 서비스로 나뉩니다. 결제⁠·정산⁠·원장 세 서비스가 내는 주문⁠·결제 이벤트는 Kafka로 모이고, Kafka Streams가 이를 윈도 단위로 집계해 원장⁠·정산 서비스로 넘깁니다. 원장⁠·정산 서비스는 결과를 RDBMS(MySQL)에 저장하고, SAP에는 거래처별 월 마감 때 비동기로 보냅니다. 집계 결과는 ELK Stack에도 쌓입니다. 검색은 상용 엔진 대신 FastAPI 검색 API⁠·ELK⁠·벡터 DB로 직접 구축했고, 몰과 백오피스의 검색 요청도 API Gateway를 거칩니다.

AS-IS → TO-BE 구조 전환

결제⁠·정산⁠·회원⁠·주문, PG SDK, 정산 배치가 한 덩어리로 묶인 모놀리스를 결제 도메인 서비스와 Kafka Streams 비동기 처리로 나눈 이벤트 드리븐 구조로 바꿨습니다.

  • AS-IS 문제 ①결제 모듈만 고쳐도 전체 재배포(배포 리스크)
  • AS-IS 문제 ②정산 배치가 돌 때 DB 부하 스파이크
  • AS-IS 문제 ③A사 검색엔진 라이선스 고비용
  • TO-BE ①Monolith → MSA, 결제 모듈 독립 배포(안정성)
  • TO-BE ②Batch → Event Stream, 실시간 원장 처리(Windowing)
  • TO-BE ③오픈소스(ELK) 전환, 검색엔진 라이선스 연간 약 3,000만원↓ 제거
  • 트랜잭션 처리Kafka 일 평균 1.5만 건 안정 처리

결제 → 원장 이벤트 흐름

결제 응답과 원장⁠·정산 처리를 분리했습니다. 결제 서비스는 PG 승인과 결제 정보 저장(커밋)까지만 맡고, 커밋이 끝난 뒤에 결제 완료 이벤트를 발행합니다. 그래서 저장되지 않은 결제가 원장에 먼저 잡히는 일이 없고, 원장 생성⁠·정산 반영⁠·SAP 연동은 이벤트로 이어집니다.

Kafka Streams 윈도 집계

주문⁠·결제가 끝난 뒤 원장을 만들 때 두 가지 윈도를 나눠 배치했습니다. Tumbling Window는 구간이 겹치지 않아 이벤트가 정확히 한 구간에만 들어갑니다. 그래서 구간 합계를 모두 더하면 전체 합계와 같고, 정산⁠·거래원장처럼 중복 없이 맞아야 하는 집계에 맞습니다. Hopping Window는 구간 길이와 이동 간격을 따로 정해 구간이 겹치므로 같은 이벤트가 여러 구간에 들어갑니다. 합계를 확정하기보다 최근 흐름을 보는 집계에 맞는 방식입니다.

  • Tumbling구간 합계의 합 = 전체 합계 → 정산⁠·원장 대사에 적합
  • Hopping같은 이벤트가 여러 구간에 포함 → 추이⁠·현황 확인에 적합
  • 결과 저장RDBMS⁠·ELK Stack, ERP 반영은 거래처별 월 마감 때 비동기

개념 데이터 모델

주문에서 결제, 결제 이벤트, 거래원장, 정산 구간, 거래처별 월 마감, 세금계산서⁠·ERP 연동으로 이어지는 흐름을 개념 엔티티로 정리했습니다. 결제 1건에는 여러 결제수단을 함께 쓸 수 있습니다. 원장 항목은 결제가 저장(커밋)된 뒤 발행된 결제 이벤트에서 만들어집니다. 원장은 이벤트가 들어오는 대로 정산 구간(Tumbling 윈도)에 집계하고, 세금계산서⁠·ERP 전송은 거래처별 월 마감으로 묶었습니다. SAP 전송 결과(ERP_TRANSFER)와 세금계산서 발행 상태(TAX_INVOICE)도 따로 기록했습니다. 결제 정보는 암호화⁠·토큰화해 보관합니다.

설계 결정왜 이렇게 했나

결제 모듈부터 떼어 낸 이유

정산⁠·ERP 연동의 정확성이 가장 중요한 기준이었습니다. 결제가 모놀리스에 묶여 있으면 결제만 고쳐도 회원⁠·주문까지 다시 배포해야 합니다. 그래서 결제와 통합 인터페이스를 먼저 분리해 변경과 장애의 범위를 결제 안에 가뒀습니다.

PG 연동을 SDK에서 REST API로

설치형 SDK는 결제 모듈을 프로젝트에 묶어 독립 배포를 막았고, 라이선스 비용도 API 방식보다 높았습니다. REST API 구조로 바꿔 결제 서비스를 따로 배포하고 교체할 수 있게 했습니다.

메시지 처리에 Kafka를 고른 이유

결제 한 건이 SAP⁠·정산 데이터⁠·내부 상태 변경으로 동시에 퍼지고, 실패하면 다시 처리할 수 있어야 했습니다. Redis⁠·RabbitMQ 후보와 '여러 시스템으로의 확장', '재처리' 두 기준으로 비교해 Kafka를 골랐습니다.

배치 대신 Kafka Streams 윈도 집계

정산 배치가 도는 시점마다 DB 부하가 튀었습니다. 이벤트가 들어올 때마다 윈도 단위로 나눠 집계하도록 바꿔, 부하가 한 시점에 몰리지 않고 원장도 이벤트가 들어오는 대로 쌓이게 했습니다.

SAP 연동을 비동기로

AS-IS는 SAP와 동기로 연동했습니다. 결제 처리와 ERP 반영을 이벤트로 나눠 ERP 쪽 처리가 결제 흐름을 붙잡지 않게 했고, Kafka에 남은 이벤트로 연동을 다시 처리할 수 있게 했습니다.

검색을 자체 구축한 이유

몰과 백오피스 어드민 검색에 연간 약 3,000만원의 상용 엔진 라이선스를 내고, 유지보수도 공급사에 기대고 있었습니다. ELK Stack⁠·FastAPI⁠·벡터 DB로 직접 구축해 비용과 외부 의존을 함께 줄였습니다.

주요 구현

결제 흐름을 서비스로 나누는 데 그치지 않고, 그 서비스를 안전하게 배포하고 들여다볼 수 있는 환경까지 갖췄습니다.

  • 결제 서비스예치금⁠·적립금⁠·쿠폰⁠·기타 결제수단의 승인⁠·취소, PG 연동
  • PG 연동설치형 SDK → REST API 구조로 전면 전환
  • 원장⁠·정산Kafka Streams Tumbling⁠·Hopping Window로 정산⁠·거래원장 처리, 트랜잭션 처리 비동기화
  • ERP 연동SAP SD⁠·PP⁠·FI 연동 정산⁠·세금계산서 자동화 파이프라인과 API(RFC/SOAP)
  • 보안결제 정보 AES-256 암호화⁠·토큰화, PCI-DSS 기준 이중 인증⁠·접근 제어
  • 검색ELK Stack⁠·FastAPI⁠·벡터 DB 자체 구축으로 A사 검색엔진 완전 대체
  • 배포Jenkins⁠·Docker Blue/Green 무중단 배포 파이프라인
  • 관측백오피스 Kafka 현황 대시보드, Grafana 모니터링, Scouter APM

성과

오픈 뒤 결제가 안정적으로 처리됐고, A사 검색엔진 라이선스 지출이 사라졌습니다. 결제 API 처리부터 SAP 연동⁠·세금계산서 발행⁠·정산까지 한 흐름으로 일원화돼, 현업에서 속도와 안정성 면에서 좋은 평가를 받았습니다.

  • 결제 성공률 99.9% 이상(오픈 후, KICC⁠·이지페이 PG 제공 데이터)
  • 오픈 후 결제 에러⁠·민원 0건(2024.07.11 오픈 기준)
  • Kafka 기반 일 평균 1.5만 건 결제 트랜잭션 처리 체계
  • 결제 모듈 독립 배포 체계 확보(Blue/Green)

성능 시험 리포트

JMeter로 부하를 걸고 Scouter APM으로 메모리⁠·CPU⁠·응답 시간을 관측했습니다. 시험은 dev → stg → prod 순으로 진행했고, 내부⁠·외부 QA 인력 20명이 참여했습니다. 동시 사용자는 실제 사람 50명에서 100명까지 단계적으로 늘렸고, 테스트 함수로 부하 강도를 더 높이는 시험도 했습니다. 동시 트랜잭션 처리 때 메모리⁠·CPU⁠·응답 시간을 기존 구조와 개선 구조로 나눠 비교했습니다. 리포트의 판단은 자원 효율 향상, 처리 성능 안정화, MSA 독립 배포 체계 확보였습니다.

SDK 내장 결제 모듈의 정산 정합성⁠·배포 리스크

문제 현황

배포 리스크
  • 결제⁠·정산⁠·회원⁠·주문이 한 모놀리스에 묶여 있음
  • PG사 결제 SDK가 프로젝트 안에 직접 들어 있음
  • 예치금⁠·적립금⁠·쿠폰 결제는 SAP 정산 데이터와 맞아야 함
  • 정산⁠·ERP 인터페이스는 한 치의 오차도 없어야 한다는 요구

원인 분석

구조 결합
  • 결제만 고쳐도 전체를 다시 배포해야 하는 구조
  • CI/CD가 없어 시스템을 멈춘 뒤 배포, 일부 클레임 발생
  • 설치형 SDK 결제 모듈의 SAP 정산 정합성 이슈
  • SAP 연동도 동기 방식

해결 과정

원인 분석

결제 모듈이 모놀리스 한 배포 단위에 묶여 있어 결제만 고쳐도 전체를 다시 배포해야 했습니다. CI/CD가 없어 시스템을 멈춘 뒤 배포했고, 그 과정에서 일부 클레임이 생겼습니다. 설치형 SDK 방식 결제 모듈에는 SAP 정산 데이터 정합성 이슈가 있었고, SAP 연동도 동기 방식이었습니다.

  4. 결제 정보 AES-256 암호화⁠·토큰화, PCI-DSS 기준 이중 인증⁠·접근 제어 적용

CASE 02 / 04스트리밍처리

정산 배치가 만드는 DB 부하 스파이크

문제 현황

부하 집중
  • 정산은 Spring Batch⁠·Cron 배치로 실행
  • 배치가 도는 시점마다 DB 부하가 튐
  • 결제 한 건이 SAP⁠·정산⁠·내부 상태로 퍼져도 일관되게 처리돼야 함

원인 분석

구조 한계
  • 정해진 시점에 한꺼번에 처리하는 배치 구조
  • 그래서 부하가 배치 시점에 몰림
  • 후속 처리 중 하나가 실패하면 다시 처리할 수단이 필요

해결 과정

윈도 집계
  1. Kafka⁠·Redis⁠·RabbitMQ를 확장⁠·재처리 두 기준으로 비교해 Kafka 선택
  2. 원장 생성에 Kafka Streams Tumbling⁠·Hopping Window를 나눠 배치
  3. 집계는 RDBMS⁠·ELK에 저장, SAP는 거래처별 월 마감 때 비동기 반영
  4. Kafka 기반 일 평균 1.5만 건 결제 트랜잭션 처리 체계 구성

결과

스트림 전환
  • 정산 처리 방식을 Batch → Event Stream으로 전환
  • 배치 시점에 몰지 않고 이벤트마다 윈도 단위로 나눠 처리
  • Kafka로 일 평균 1.5만 건 결제 트랜잭션 처리
전체 설명 보기
문제 상황

정산은 Spring Batch⁠·Cron 배치로 돌았고, 배치가 도는 시점마다 DB 부하가 튀었습니다. 결제 한 건은 SAP⁠·정산 데이터⁠·내부 상태 변경으로 동시에 퍼지면서도 일관되게 처리돼야 했습니다.

원인 분석

정산을 정해진 시점에 한꺼번에 처리하는 배치 구조라 부하가 그 시점에 몰렸습니다. 결제 후속 처리가 여러 시스템으로 퍼지는데, 그중 하나가 실패했을 때 다시 처리할 수단도 필요했습니다.

해결 과정
  1. 메시지 처리 후보(Kafka⁠·Redis⁠·RabbitMQ)를 '여러 시스템으로의 확장', '재처리' 두 기준으로 비교해 Kafka 선택
  2. 주문⁠·결제 완료 뒤 원장을 만들 때 Kafka Streams Tumbling⁠·Hopping Window를 나눠 배치
  3. 윈도 집계 결과를 RDBMS⁠·ELK Stack에 저장하고, SAP에는 거래처별 월 마감 때 비동기로 반영
  4. Kafka 기반 일 평균 1.5만 건 결제 트랜잭션 처리 체계 구성
결과

정산을 배치 시점에 몰지 않고, 이벤트가 들어올 때마다 윈도 단위로 나눠 처리하는 구조(Batch → Event Stream)로 바꿨습니다. Kafka로 일 평균 1.5만 건의 결제 트랜잭션을 처리했습니다.
