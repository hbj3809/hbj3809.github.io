무엇을, 왜 만들었나

컨트롤 플레인이 1대뿐인 온프레미스 k3s 의 구조 한계를 실사용 기반 사이징으로 검토하고, Terraform root 8개와 GitOps 로 AWS EKS 플랫폼을 새로 지어 구축 당일 플랫폼 앱 14개를 가동했습니다. 서비스 전용 운영 환경을 먼저 신축한 뒤 기존 서비스 호스트 11개를 같은 이름으로 순차 이관했고(정지창 서비스별 5~40분), 분석 DB 는 증설 없이 단일 writer + 시점 복구 구조로 바꿔 PITR 리허설 RPO 130초·노드 강제 종료 시 DB 159초 복귀로 복구 경로를 실증했습니다.

개요배경·목표·내 역할

온프레미스 임대 서버 위의 쿠버네티스(k3s)는 컨트롤 플레인이 1대뿐이었고, 볼륨이 노드 디스크에 묶여 노드를 비울(drain) 수 없었으며, 백업은 DB 일일 덤프가 전부였습니다. 회사가 AWS EKS 이관 방향을 논의하던 시점에 기술 검토와 사이징을 맡았고, 승인된 구성안대로 새 플랫폼을 코드로 짓고 사내 서비스를 같은 이름으로 옮겼습니다. 이관 뒤에는 분석 DB 의 복구 경로를 리허설과 노드 강제 종료 훈련으로 실증했습니다.

  • 목표: 서버 1대 장애가 전 서비스 정지로 번지지 않는 기반 · 모든 변경은 코드와 PR 로만 · 기존 서비스는 같은 호스트 이름으로 순차 이관
  • 내 역할: 기술 검토·실사용 기반 사이징·로드맵 → Terraform·GitOps 설계·구축 → 서비스 전용 운영 환경 신축 → 순차 이관 → DB 복구 실증
  • 결정 주체: 구성안·예산은 팀장 승인, 분석 DB 의 비용·구조 제약은 회사 결정
  • 팀: 스타트업 개발팀, 인프라 전담 인력 없음 · Claude Code·Codex 에이전트와 협업, 위험 작업은 본인 승인
  • 기간: 2026.08 ~ 2026.09 — 검토·승인 → 기반 구축 하루 → 운영 환경 신축·서비스 이관 나흘 → 3노드 안정화
  • 범위 밖: 온프레미스 게이트웨이 교체·클러스터 보안 하드닝(별도 사례), 프론트엔드 코드

왜 옮겼나구 환경의 구조 한계 6가지

기존 개선 과제(컨트롤 플레인 이중화, 스토리지 교체, 버전 잠금 해소, 오프사이트 백업)가 관리형 서비스로 흡수되는지 하나씩 대조해 '조건부 찬성'으로 결론 냈습니다. 같은 검토서에 '관리형은 클러스터 아래만 가져가고, 그 위의 앱 운영·버전 주기·비용 통제는 여전히 우리 몫'이라는 목록도 함께 적었습니다.

구 환경 한계무엇이 문제였나EKS 에서의 대응확인한 것
단일 서버가 곧 클러스터컨트롤 플레인 1대에 SSO·공유 DB 까지 동거, 서버 장애 = 전 서비스 정지관리형 컨트롤 플레인(다중 AZ) + 노드 3대 AZ 분산컨트롤 플레인 운영·etcd 백업은 AWS 책임
노드에 박힌 스토리지볼륨이 특정 노드 디스크에 고정돼 drain·노드 교체 불가, 용량 제한도 강제되지 않음EBS 동적 프로비저닝(PVC), 온라인 확장, 삭제 보호 정책노드 강제 종료 훈련에서 디스크 자동 재부착
버전 잠금·지원 종료k3s 와 Argo CD 버전이 서로 묶여 업그레이드 불가, 인그레스 컨트롤러 지원 종료최신 안정 버전으로 신설, Envoy Gateway(Gateway API) + NLB단계 관문(타임아웃 경계·클라이언트 IP 보존) 통과
백업·재해복구 부재DB 일일 덤프 수준, 시점 복구·복원 리허설·클러스터 백업 없음DB 물리 백업 + WAL 을 S3 로(PITR), Velero 클러스터 백업PITR 리허설 RPO 130초, 백업 후 삭제·복원 데이터 일치
수동 운영 드리프트정본 파일과 실제 클러스터가 어긋나는 일 반복, 짧게 만료되는 레지스트리 토큰을 CronJob 으로 연명Terraform + GitOps 전면, 노드 역할·Pod Identity구축 당일 플랫폼 앱 14개 동기화·정상
진입·출구 단일 IP모든 호스트가 와일드카드 DNS·공인 IP 하나에 묶임, 회선 장애 = 전면 중단NLB 3개 AZ 분산 + 아웃바운드 NAT 고정 IP 1개외부기관 화이트리스트를 새 고정 IP 로 재등록

전체 구조

사용자 요청은 DNS → NLB → Envoy Gateway 를 거쳐 프라이빗 서브넷의 앱으로 들어갑니다. 컨트롤 플레인은 AWS 관리형이고, 노드 3대는 AZ 마다 1대씩 둡니다. 플랫폼 앱(Argo CD·cert-manager·Sealed Secrets·LB Controller·Envoy Gateway·모니터링·Velero 등)은 전부 GitOps 로만 배포합니다.

  • NLB 는 ip 타깃으로 Envoy 파드에 직결해 실제 클라이언트 IP 를 보존(실트래픽으로 확인)
  • Envoy Gateway 는 AZ 마다 1개씩 두고 최소 가용 수를 지정해 노드 1대를 잃어도 진입점 유지
  • 컨트롤 플레인 감사 로그는 CloudWatch 로 보관
  • 레지스트리 인증은 노드 역할로 바꿔 토큰을 주기적으로 갱신하던 CronJob 폐기

네트워크서브넷 3계층과 들어오고 나가는 관문

VPC 하나에 성격이 다른 서브넷 3종을 AZ 마다 두었습니다. '무엇이 어디에 놓이는가'가 곧 보안 경계라서, 열린 문은 NLB 의 443/80 하나로 좁혔습니다.

  • 퍼블릭: NLB·NAT 만 두고 서버는 두지 않음
  • 프라이빗: 노드와 모든 파드. 파드가 VPC IP 를 직접 받으므로 가장 큰 대역을 배정하고, 프리픽스 위임으로 노드당 파드 수용량 확보
  • 클러스터 서브넷: 컨트롤 플레인이 VPC 에 꽂는 접점 전용, 노드 배치 금지
  • 인바운드: NLB → Envoy Gateway(TLS 종료·호스트별 라우팅·IP 화이트리스트 기본 거부) → 앱(자체 JWT 인증)
  • 아웃바운드: S3 트래픽은 게이트웨이 엔드포인트로 NAT 를 거치지 않고, 그 외 외부 API 는 NAT 고정 IP 하나로 수렴해 외부기관 화이트리스트를 IP 하나로 관리
  • 내부: NetworkPolicy 로 DB·Kafka 접근을 허용 목록 기반으로 제한
  • 계정·노드: S3 계정 단위 공개 차단, 이미지 push 시 취약점 스캔, 노드 메타데이터 서비스는 IMDSv2 강제·홉 제한으로 파드가 노드 자격 증명에 닿지 못하게

코드 정본 두 개Terraform 과 GitOps 의 역할 분담

클러스터 밖(AWS)은 Terraform, 클러스터 안(앱·설정)은 GitOps 저장소와 Argo CD 가 정본입니다. 두 저장소만 있으면 인프라 전체를 다시 만들 수 있게 하는 것이 목표였습니다.

  • root 를 8개로 나누고 state 를 root 별로 분리·잠금·암호화해 실수 하나가 번지는 범위를 줄임
  • Argo CD 설치 자체도 Terraform 이 소유 — 앱 레이어의 시작점까지 코드
  • 콘솔 수동 변경 금지: 손으로 바꾼 것은 코드와 어긋나는 순간 드리프트가 된다는 온프렘 시절 교훈
  • 사람 권한도 코드: 클러스터 접근 명부(관리자·네임스페이스 한정 개발자·감사자 + SSO 와 독립된 비상 경로)에 한 줄 추가 후 적용
  • plan 을 파일로 저장해 검토한 뒤 그 파일만 적용 — 처음부터 설계한 통제가 아니라, AI 에이전트의 자동 승인 적용이 도구의 권한 분류기에 막히면서 정착한 방식
  • 월 예산 알림도 코드로 함께 관리

핵심 흐름호스트 하나씩 옮기고, 레코드 삭제 한 번으로 되돌리기

구 클러스터의 호스트 전부가 와일드카드 DNS 레코드 하나에 묶여 있었습니다. 구체 레코드가 와일드카드보다 우선한다는 규칙을 이용해 '호스트 하나 = 레코드 하나'로 만들었고, 전환은 레코드 추가, 되돌리기는 삭제 한 번이 되도록 했습니다.

  • 순서: 클러스터 조회 도구 → 모니터링 → 메시지 조회 도구·사내 업무 도구 → SSO → 개발 API → 분석 DB·워크플로·BI → 개발 SPA → CI → 대시보드·GitOps 본 호스트
  • 구 버전을 그대로 옮기지 않고 각 컴포넌트를 최신 안정 버전으로 올리며 이관
  • 개발 API 는 설정 파일 대신 환경변수로만 배선해 같은 이미지가 구·신 양쪽에서 뜨게 함 → 되돌리기 안전
  • SSO 는 핫카피 리허설 후 정지창 컷오버, 토큰 발급자·서명 키를 보존해 연동 앱 무수정
  • 협력사 소관 호스트는 이관 대상에서 빼고 구 클러스터에 남겨 와일드카드로 계속 서빙

스토리지EBS·PVC 와 AZ 경계

EBS 는 실제 블록 디스크라 한 번에 한 노드, 그것도 같은 AZ 의 노드에만 붙습니다. 이 제약 하나가 노드그룹을 AZ 별로 나눈 이유이자 분석 DB 의 복구 방식을 정한 출발점이 됐습니다.

  • 동적 프로비저닝: 파드가 용량을 선언하면 디스크가 자동 생성되고, 파드와 디스크의 수명이 분리됨
  • Retain 표준: PVC 를 지워도 디스크는 바로 지워지지 않아 실수에 한 번 더 안전
  • 확장은 '허용'이지 '자동'이 아님 — 사용률 경보가 울리면 사람이 숫자를 올리는 구조
  • 구 환경의 노드 디스크 볼륨은 용량이 장부상 숫자였지만 EBS 는 실제 상한 — 이관 직후 WAL 보관 볼륨이 가득 차는 일을 처음 겪고 확장·보존 기간 정비로 해결

파드의 AWS 권한저장된 키에서 Pod Identity 로

구 환경에서는 파드가 AWS 를 쓰려면 액세스 키를 시크릿으로 저장해야 했고, 회전은 사람이 챙겼습니다. 새 클러스터에서는 '이 서비스어카운트 = 이 IAM 롤' 연결만 코드로 선언합니다.

  • 사용처: DB 백업→S3, 로그·클러스터 백업, 인증서 DNS 검증, 빌드 이미지 push, API 첨부 저장 — AWS 를 쓰는 워크로드 전부
  • 새 클러스터는 정적 AWS 키 없이 노드 역할·워크로드 신원으로 운영(구 클러스터 쪽 키 정리는 별도)

구성요소별 As-Is → To-Be

단순히 옮기지 않고, 공유하던 것은 끊고 수명이 다한 것은 후계로 바꾸며 옮겼습니다.

사내 SSO개발 모드·단일 인스턴스로 공개 운영운영 모드 이중화(Keycloak 26.4 → 26.7.2), 관리 콘솔 접근 제한, 시크릿 재발급토큰 발급자·서명 키 보존으로 연동 앱 무수정 전환

인증서발급·갱신을 사람이 챙기고 DNS 검증은 정적 IAM 키에 의존cert-manager 가 DNS 검증 레코드를 워크로드 신원으로 직접 기록, 만료 전 자동 갱신사람 개입과 정적 키 제거

분석 DB 복구 모델단일 writer 의 장애 경로

추가 노드·관리형 DB 없이 3노드를 유지하기로 한 회사 결정에 맞춰, 분석 DB 는 단일 writer + 객체 저장소 시점 복구(PITR) 구조로 정했습니다. 자동 failover 가 없는 DR 구조라서, 장애 경로마다 어떻게 돌아오는지를 정하고 실제로 해 봤습니다.

  • DB 노드 EC2 강제 종료: 대체 노드 자동 생성 → 기존 디스크 7개 자동 재부착 → DB 159초 복귀(앱 재가동 완료는 약 28분 뒤)
  • 격리 PITR 리허설: 1·2차 실패 후 3차에서 RPO 130초, 복원 생성→검증 27분 18초(탐지·판단·전환 제외 기술 구간)
  • 실수 삭제는 복제본도 함께 지워지므로, 복구 축은 처음부터 백업·PITR 이 맡도록 분리

설계 결정왜 이렇게 골랐나

운영 환경을 먼저 새로 짓는다

옮길 데이터·사용자가 없는 서비스 운영 환경을 첫 워크로드로 신축해 IaC·배포 라인·모니터링·보안을 위험 없이 검증했습니다. 그러면 이관은 '검증된 클러스터로의 두 번째 배포'가 됩니다. 순서는 운영 환경 신축 → 개발 환경 이관 → 구 환경 정리로 제안해 승인받았습니다.

실사용으로 사이징, 기준은 N-1

이관 대상의 실사용 CPU·메모리·스토리지·사용자향 트래픽을 재서, 노드 1대를 잃어도 버티는 기준(N-1)으로 노드 수·크기와 월 비용 모델을 만들었습니다. 비용은 온프렘보다 늘 수 있다는 점을 숨기지 않고, 대신 얻는 가용성·백업·관리형 운영을 함께 제시했습니다.

AZ 마다 노드그룹 하나

EBS 볼륨은 AZ 에 묶여 같은 AZ 노드에만 붙습니다. 노드그룹을 하나로 합치면 교체 노드가 다른 AZ 에 떠 DB 볼륨이 붙을 곳을 잃습니다. AZ 별로 나눠 교체 노드가 같은 AZ 에 뜨도록 보장했고, 노드 강제 종료 훈련에서 디스크 7개 자동 재부착으로 확인했습니다.

단일 대용량 볼륨 대신 PVC 동적 생성

EBS 는 한 번에 한 노드에만 붙기 때문에 노드들이 나눠 쓰는 대용량 볼륨안은 구조적으로 맞지 않았습니다. 앱마다 PVC 로 디스크를 자동 생성하고, 온라인 확장 허용·삭제 시 디스크 보존 정책을 표준으로 정했습니다.

게이트웨이 자산 재사용 — Envoy Gateway + NLB

온프렘에서 먼저 Gateway API 기반 Envoy Gateway 로 교체해 둔 라우트·정책을 토폴로지만 바꿔 그대로 이식했습니다. 클라우드 전용 어노테이션으로 다시 쓰지 않아도 됐고, NLB 를 ip 타깃으로 붙여 클라이언트 IP 를 보존했습니다.

관문을 통과해야 다음 단계로

단계마다 게이트 스모크를 두었습니다. 백엔드 타임아웃 경계(경계 안 요청은 성공, 넘긴 요청은 504), 장시간 무데이터 연결 유지, 실제 클라이언트 IP 보존, 클러스터 내부에서 공개 호스트로 재진입, 백업 후 네임스페이스·PVC 삭제 → 복원까지 확인한 뒤에야 넘어갔습니다.

메시지는 옮기지 않는다

모든 토픽의 정본이 DB 에 있다는 점을 확인해, 메시지를 복사하지 않고 컨슈머만 새 KRaft 클러스터로 돌렸습니다. '무엇을 옮기지 않아도 되는가'를 먼저 찾은 것이 이관 위험을 크게 줄였습니다.

AI 에이전트와 함께, 위험 작업은 사람이

적용 전 적대적 리뷰로 확장 지원 등급이 암묵적으로 선택돼 컨트롤 플레인 요금이 크게 오를 수 있던 위험 등 구성 결함 4건을 미리 막았습니다. 부분 적용이 의존성까지 끌어와 3개 AZ 노드가 동시에 교체된 일은 피해 없이 기록하고 절차를 고쳤습니다. 복구 훈련 실행은 대부분 Codex 가 했고, 단계 통과와 파괴 작업은 제가 승인했습니다.

EBS 는 진짜 상한이다

온프렘 볼륨은 용량이 장부상 숫자였지만 EBS 는 실제 하드 리밋입니다. 이관 직후 제가 하루 전 구성한 개발 DB 의 WAL 보관 볼륨이 가득 찼고, 원인(하트비트가 주기적 WAL 전환을 계속 일으킴)을 찾아 온라인 확장·보존 단축으로 풀었습니다. 온프렘 감각의 사이징은 다시 검증해야 한다는 교훈입니다.

성과서비스별 정지창

기존 호스트 11개를 같은 이름으로 옮기면서, 서비스마다 정지창을 따로 잡아 짧게 끊었습니다.

  • 구축 당일 플랫폼 앱 14개 정상 가동 · 네트워크 리소스 38개 적용·라이브 대조
  • 적용 전 적대적 리뷰로 구성 결함 4건 사전 차단
  • 기존 서비스 호스트 11개를 같은 호스트 이름으로 이관, SSO 연동 앱 수정 없음
  • 자사 빌드 잡 6종 kaniko 전환 — 새 클러스터는 정적 AWS 키 없이 노드 역할·워크로드 신원으로 운영

성과복구·전환 실측

새 플랫폼이 '돌아간다'에서 끝내지 않고, 장애가 났을 때 실제로 얼마 만에 돌아오는지를 쟀습니다.

CASE 01 · 기술검토·플랫폼설계

컨트롤 플레인 1대의 한계 — '옮기기' 대신 '새로 짓고 검증한 뒤 옮기기'

1문제 상황

온프레미스 임대 서버 위의 k3s 는 컨트롤 플레인이 1대였고 SSO·공유 DB 까지 같은 서버에 있었습니다. 볼륨이 노드 디스크에 묶여 drain 이 불가능했고, k3s 와 Argo CD 버전이 서로 묶여 올릴 수 없었으며, 오프사이트 백업이 없었습니다. 회사는 EKS 이관 방향을 논의 중이었지만 비용·사이징·순서·공유 컴포넌트 경계가 정해지지 않은 상태였습니다.

2원인 분석

구조 문제가 두 종류로 섞여 있었습니다. 컨트롤 플레인 이중화·스토리지·etcd 백업처럼 관리형이 흡수하는 문제와, 앱 운영·버전 주기·비용 통제처럼 관리형으로 가도 여전히 우리 몫인 문제입니다. 기존 클러스터 위에서 하나씩 고치면 나중에 또 옮겨야 하는 이중 공사가 됩니다.

3해결 과정
  1. 기존 개선 과제를 '관리형이 흡수하는가'로 하나씩 대조해 조건부 찬성 결론, 관리형이 해결해 주지 않는 목록도 함께 작성
  2. 이관 대상 실사용(CPU·메모리·스토리지·사용자향 트래픽)을 재서 노드 1대 상실 기준(N-1) 사이징·월 비용 모델 작성
  3. 순서를 '운영 환경 신축 → 개발 환경 이관 → 구 환경 정리'로 뒤집자고 제안해 팀장 승인
  4. Terraform root 8개(state·예산·네트워크·EKS·접근·스토리지·Argo CD·DNS 전환)와 Terraform 이 소유한 Argo CD 로 하루 만에 기반 구축
  5. 단계 관문(타임아웃 경계·무데이터 연결 유지·클라이언트 IP 보존·내부 재진입·백업 후 삭제·복원)을 통과해야 다음 단계로
  6. AI 에이전트 작업에 적용 전 적대적 리뷰를 걸어 구성 결함을 적용 전에 차단
4결과

구축 당일 플랫폼 앱 14개가 모두 동기화·정상 상태로 가동됐고, 네트워크 리소스 38개를 적용해 라이브와 대조했습니다. 적대적 리뷰로 컨트롤 플레인 요금이 크게 오를 수 있던 지원 등급 암묵 선택을 포함한 구성 결함 4건을 적용 전에 막았고, 새 클러스터는 정적 AWS 키 없이 구성했습니다.

관리형은 클러스터 아래만 가져갑니다. 그 위는 그대로 우리 몫이라 코드화와 관문으로 메워야 했습니다. 첫 워크로드를 신축으로 시작하니, 이후 이관은 '검증된 클러스터로의 두 번째 배포'가 됐습니다.

CASE 02 · 마이그레이션

수십 GB 분석 DB 를 하루에 옮기기 — 정지창을 추정 대신 복원 리허설로

1문제 상황

매출 파이프라인 DB·워크플로 메타DB·BI 가 구 클러스터의 단일 PostgreSQL 인스턴스에 함께 있었고, 규모는 수십 GB 였습니다. 정지창을 감으로 잡을 수는 없었고, 다른 libc 기반 이미지로 물리 복원하면 정렬(collation) 인덱스가 깨질 위험이 있었습니다.

2원인 분석

물리 복원은 OS 의 정렬 규칙(libc)에 묶이는데, 구 이미지가 musl(alpine) 계열이었습니다. 또 정지창 길이는 사실상 복원 시간이 결정하는데, 그 시간을 잰 적이 없었습니다.

3해결 과정
  1. 구 이미지와 같은 digest 로 새 StatefulSet 을 만들고 기존 튜닝을 그대로 유지해 인덱스 손상 위험 제거
  2. 서비스 이름을 구와 똑같이 둬 소비자 재배선 없이 전환되게 설계
  3. WAL 동기화·일일 베이스 백업 리그를 워크로드 신원으로 S3 에 연결
  4. S3 의 베이스 백업과 WAL 만으로 복원 리허설 — 내려받기·압축 해제·WAL 재생을 단계별로 측정하고 핵심 테이블 행 수·BI 카드 수를 원본과 대조
  5. 컷오버: 구 인스턴스 정지 → WAL 스위치·S3 동기화 → 복원(최종 WAL 반영 확인) → 소비자 3종 실접속
  6. 워크플로 스케줄러는 새 버전으로 올리며 S3 원격 로깅을 붙이고, 워커가 API 서버를 경유한다는 점을 확인해 NetworkPolicy 보정
  7. 구 객체 저장소의 리포트·수집 파일을 S3 로 옮기고 바이트 일치 확인
4결과

복원 리허설은 약 13.7분이었고 검증 항목이 전부 일치했습니다. 이 숫자로 정지창을 정해 이관을 시작한 날 컷오버를 마쳤고, 실제 복원 단계는 846초였습니다(전체 정지창 길이가 아님).

배운 점

정지창은 '얼마나 걸릴까'가 아니라 '재 보니 얼마였다'로 정해야 합의가 빠릅니다. 단계별로 재니 압축 해제가 가장 긴 구간이라는 것도 보였습니다. 같은 이미지 계열, 같은 서비스 이름처럼 '바꾸지 않을 것'을 먼저 정한 것이 위험을 크게 줄였습니다.

CASE 03 · 복구설계·복구검증

DB 하나가 노드 하나를 잠식 — 스탠바이에서 단일 writer DR 까지

1문제 상황

이관 직후 분석 DB 하나가 한 노드 예약 자원의 큰 몫을 차지했고, 주기적인 전처리 피크 때는 그 노드 CPU 를 거의 다 썼습니다. 노드 예약이 꽉 차 빌드 에이전트가 뜰 자리가 없던 일도 실제로 있었습니다. 볼륨이 AZ 에 묶여 있어 노드가 죽으면 DB 는 노드가 돌아올 때까지 멈추는 구조였습니다.

2원인 분석

EBS 볼륨의 AZ 종속, 복제본 없는 단일 인스턴스, 배치 피크와 서빙이 같은 노드에 동거한 것이 겹쳤습니다.

3해결 과정
  1. 먼저 이미 확보한 노드 여유분으로 다른 AZ 에 스트리밍 스탠바이를 가동하고, 노드 역할 정비·DB CPU 예약 우측화를 병행
  2. 노드 상향·DB 전용 노드·관리형 DB 3안을 '장애 때 누가 대응하는가'와 비용 기준으로 비교한 검토 자료 작성
  3. 회사가 추가 노드·관리형 DB 없이 3노드 유지를 결정 → 구조를 'HA 가 아닌 DR'로 재정의하고 'PITR 리허설 → 노드 복구 훈련 → 스탠바이 철거' 관문 순서 설계
  4. 운영 writer 를 건드리지 않는 격리 PITR 리허설 구현(서비스 연결 없음·아카이브 끔·임시 볼륨)
  5. 1차(시간 형식 파서 거부·복원 시간 초과)와 2차(검증 SQL 결함) 실패의 원인을 고쳐 3차 통과
  6. 승인된 정지창에서 writer 를 동결하고 DB 노드 EC2 를 실제로 강제 종료 — 수동 drain·강제 분리 없이 전체 워크로드 복구 확인
  7. 두 관문 통과 뒤 스탠바이 워크로드·복제 슬롯·전용 디스크를 잔재 없이 철거
  8. 노드 1대 상실에 대비해 장기 사용량 근거로 예약 자원을 컴포넌트 하나씩 나눠 보정하고, 매번 수용 시험으로 확인
  9. 계획·런북·실행은 대부분 Codex 에이전트, 단계 통과와 파괴 작업(EC2 종료·디스크 삭제) 승인은 본인
4결과

PITR 리허설 3차에서 RPO 130초, 복원 생성→검증 27분 18초로 승인한 복구 목표를 통과했습니다. DB 노드 강제 종료 훈련에서는 대체 노드가 뜨고 기존 디스크 7개가 자동으로 다시 붙어 DB 가 159초 만에 돌아왔습니다(앱 재가동 완료는 약 28분 뒤). 노드 1대 상실 시 CPU 재배치 장부는 부족에서 소폭 여유로 바뀌었지만, 목표로 잡은 여유에는 못 미쳤습니다.

CASE 04 · 이관설계

와일드카드 DNS 하나에 묶인 서비스를 하나씩 옮기기

1문제 상황

구 클러스터의 호스트 33개가 와일드카드 DNS 레코드 하나에 의존했고, 그중에는 여러 시스템이 함께 쓰는 사내 SSO 같은 공유 컴포넌트가 섞여 있었습니다. 한꺼번에 전환하면 장애 범위가 전체로 커지고, SSO 는 개발 모드로 공개 운영되고 있었습니다.

2원인 분석

와일드카드 레코드는 '전부 아니면 전무'로만 바꿀 수 있습니다. 반면 DNS 에서는 구체 레코드가 와일드카드보다 우선하므로, 호스트 단위로 쪼갤 여지가 있었습니다.

3해결 과정
  1. DNS 존을 전수 조사해 구체 레코드 우선 규칙을 확인하고, 'Terraform 으로 호스트 레코드 추가 = 전환, 삭제 = 롤백' 구조 설계
  2. 각 컴포넌트를 최신 안정 버전으로 올리며 한 번에 하나씩 이관
  3. 개발 API 는 설정 파일 대신 환경변수로만 배선해 같은 이미지가 구·신 양쪽에서 뜨게 함
  4. SSO 는 핫카피 리허설로 스키마 자동 마이그레이션을 확인한 뒤 정지창 컷오버, 이중화된 운영 모드로 재구성하고 토큰 발급자·서명 키 보존
  5. CI 는 Docker 소켓 의존을 kaniko 로 바꾸고(자사 잡 6종) 레지스트리 push 를 워크로드 신원으로, 설정은 JCasC 로 코드화
  6. 새 CI 로그인 무한 리다이렉트 — 제가 새 OIDC 클라이언트에 기본 스코프를 명시하면서 사용자 식별 클레임이 빠진 것이 원인, 규명 후 수정
4결과

기존 호스트 11개를 같은 호스트 이름 그대로 옮겼고, 정지창은 개발 API 5분·SSO 약 7분·CI 약 40분이었습니다. SSO 는 연동 앱을 하나도 고치지 않고 전환됐습니다.

전환 단위를 작게 만들면 되돌리기가 '삭제 한 번'이 됩니다. 그리고 내가 만든 설정도 원인 후보에 넣어야 합니다. 무한 리다이렉트는 제 설정 실수였고, 기본값을 덮어쓰는 설정은 무엇이 함께 빠지는지 확인해야 한다는 점을 배웠습니다.
