온프렘 쿠버네티스 → AWS EKS 이관

단일 컨트롤 플레인 온프렘 클러스터를 AWS EKS 로 옮기면서, 그 전후로 게이트웨이 교체·보안 하드닝·복구 훈련까지 이어서 했습니다. 인프라 전담 인력 없이 AI 에이전트와 함께 진행했습니다.

왜 옮겼나

컨트롤 플레인이 하나라 노드를 비울(drain) 수 없었고, 쿠버네티스와 GitOps 도구 버전이 서로 묶여 올릴 수 없었으며, 오프사이트 백업이 없었습니다. 기존 개선 과제가 관리형 서비스로 해결되는지 하나씩 대조하고, 실사용(CPU·메모리·스토리지·트래픽)을 재서 노드 1대를 잃어도 버티는 기준으로 사이징·월 비용 모델을 만들어 "운영 환경 신축 → 개발 환경 이관 → 구 환경 정리" 순서를 제안했고 승인받았습니다.

먼저 한 일: 게이트웨이 교체

보안 지원이 끝난 ingress-nginx 가 포트를 독점하고 DNS 가 와일드카드라 조금씩 옮길 수 없었습니다. 타임아웃의 의미가 다른 점(유휴 기준 60초 vs 요청 전체 15초)을 로그와 설정 덤프로 실측해 정책을 설계했고, 호스트 33개를 Envoy Gateway 로 옮겼습니다. 같은 날 1·2차 시도는 실패해 자동 롤백됐습니다. 1차는 라이브만 고치고 생성기를 고치지 않은 제 실수, 2차는 "오브젝트가 사라지면 포트도 풀린다"는 오판이었습니다. 사전 게이트와 단계별 타임아웃, 소켓 해제 기준 판정으로 고친 3차에서 중단 23.2초로 성공했습니다.

새 플랫폼

  • 코드로만 바꾸기: Terraform root 8개(상태·예산·네트워크·EKS·접근·스토리지·GitOps·DNS 전환)를 root 별 상태 분리·잠금·KMS 로 나누고, 앱은 Terraform 이 소유한 Argo CD 위에 올려 모든 변경을 PR 로만 하게 했습니다.
  • 정적 키 없이: 이미지 풀·DNS 인증서 발급·백업에 쓰던 장기 AWS 키를 노드 역할과 EKS Pod Identity 로 바꿨습니다.
  • 단계별 관문: 타임아웃 경계(290초 200 / 320초 504), 장시간 무데이터 연결 유지, 실제 클라이언트 IP 보존, 클러스터 내부 재진입, 백업 후 네임스페이스 삭제 → 복원 리허설을 통과해야 다음 단계로 넘어갔습니다.
  • 전용 운영 환경: 다른 서비스와 공유하던 캐시·DB·메시지 브로커를 끊고 Valkey Sentinel·PostgreSQL·Kafka KRaft 3노드로 새로 구성, 장애 시험에서 Sentinel 승격 6.5초를 확인했습니다.
  • 서비스 이관: 호스트별 DNS 레코드 추가 = 전환, 삭제 = 롤백 구조로 기존 서비스 11개를 같은 이름으로 옮겼습니다. 사내 SSO 는 개발 모드에서 이중화된 운영 모드로 재구성하며 토큰 발급자·서명 키를 보존해 연동 앱을 고치지 않았습니다.

복구를 실제로 해 보기

증설 없이 분석 DB 를 단일 writer + 객체 저장소 기반 시점 복구(PITR) 구조로 바꿨기 때문에, 복구가 실제로 되는지 확인해야 했습니다. 운영 DB 를 건드리지 않는 격리 리허설은 두 번 실패했고(시간 형식 파서, 검증 SQL 결함), 고친 세 번째에서 RPO 130초·복원 검증 27분으로 목표를 통과했습니다. DB 노드 EC2 를 실제로 강제 종료한 훈련에서는 대체 노드가 뜨고 기존 디스크 7개가 자동으로 다시 붙어 DB 가 159초 만에 돌아왔습니다.
