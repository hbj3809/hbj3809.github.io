무엇을, 왜 만들었나

여러 제약사와 사내 관리자가 한 백엔드·DB 를 함께 쓰는 의약품 유통 데이터 분석 SaaS pharmscope 의 백엔드를 Kotlin·Spring WebFlux 로 설계·구현했다. 자체 발급 JWT 인증·세션, 회사 단위 테넌트 격리, 배포 단위를 늘리지 않는 모듈러 모놀리스, SSE·Kafka 실시간 알림을 만들었다. 운영 공개 전 AI 멀티에이전트 감사로 고위험 2건 포함 10건의 결함을 고쳤고, 지금은 상용 서비스로 운영 중이다.

개요배경·목표·내 역할

pharmscope 는 국내 대형 의약품 유통사의 매출 데이터를 제약사가 자기 제품 기준으로 분석하는 SaaS 다. 여러 제약사와 사내 관리자가 한 백엔드·DB 를 함께 쓰기 때문에, 다른 회사의 데이터가 한 번이라도 보이면 서비스가 성립하지 않는다. 2026.05 에 인증·세션을 먼저 만들고, 그 위에 운영 공개 전까지 기능정의서의 계약사 관리·계정 관리·보안 로그·운영관리(공지·FAQ·1:1 문의)·실시간 알림을 갖춰야 했다.

  • 기간: 2026.05 인증 설계 착수 → 2026.06~09 기능 구축 → 2026.09 CBT 외부 공개 → 상용 운영
  • 목표: 계약 상태·IP·세션을 서버에서 보장하는 인증, 회사 단위 데이터 격리, 배포 단위를 늘리지 않는 확장 구조
  • 내 역할: 백엔드 설계·구현 전담(Claude Code 활용). 범위·모듈 구조·정책 선택지는 에이전트 질의에 답해 직접 확정
  • 다른 사람 몫: 요구사항·화면 기획은 기획팀, 화면 구현은 FE. 쿠키 방식은 FE 와 합의, 역할 4종·로그인 잠금 시간·중복 로그인 최종 정책은 기획 확정
  • 범위 밖: 기능정의서의 약품 승인 기능은 아직 착수 전

아키텍처단일 배포 모듈러 모놀리스

배포 단위는 하나로 두고 기능을 Gradle 모듈로 나눴다. 인증이 필요한 요청은 인증 필터에서 토큰 검증을 받고, 회사 식별자는 토큰 클레임으로만 서비스에 전달된다. 기능 모듈은 공통 모듈(응답 형식·에러 코드·보안 부품·OpenAPI)과 인증·식별 코어에만 기대고, 새 모듈은 의존 한 줄을 추가하면 자동 등록된다. 리액티브 런타임이라 실행 중에는 JDBC 를 쓰지 않고(Flyway 기동 1회만 예외), 비밀번호 해시·토큰 서명 같은 CPU 작업은 별도 스레드로 격리했다. 이후 매출 분석 모듈도 같은 인증·격리 위에 붙었다(분석 API·성능 튜닝은 별도 프로젝트에서 다룬다).

핵심 흐름 ① 로그인과 토큰 자동 회전

로그인은 실패 잠금 확인 → 아이디·비밀번호와 역할 → 계정·회사·계약 상태 → IP 허용 목록(고객사 로그인) → 임시 비밀번호 재설정 강제를 차례로 통과해야 토큰을 받는다(토큰 발급까지 7단계 체인). 관리자와 고객사는 로그인 경로부터 나뉘고, 다른 쪽 계정으로 시도하면 계정 존재 여부를 드러내지 않는 같은 오류를 돌려준다. access 가 만료되면 인증 필터가 refresh 쿠키로 회전해 새 access 를 응답 헤더로 내려주므로, 프론트는 갱신 API 를 따로 부르지 않고 헤더의 토큰만 바꾼다. 회전할 때도 계정·계약 상태를 다시 확인해, 이미 발급된 토큰이라도 계약이 끝나면 다음 회전에서 막힌다.

핵심 흐름 ② 테넌트 격리

고객사 영역 요청에는 회사 식별자를 받지 않는다. 회사는 토큰 클레임에서만 꺼내고, 리소스를 읽을 때는 회사 필터 쿼리나 동일 회사 검증을 거친다. 다른 회사 리소스는 403 으로 막고, 첨부처럼 존재 여부 자체를 숨겨야 하는 경로는 404 로 돌려준다. DB 의 부분 유니크 인덱스·FK·CHECK 제약을 마지막 안전망으로 깔았고, 리소스 CRUD 를 추가하는 변경에는 '타사 접근 403' 통합 시험을 넣도록 규칙화했다. 규칙은 프로젝트 작업 지침에도 넣어 AI 에이전트와 함께 개발할 때 같은 기준으로 점검한다. 다만 규칙은 지침일 뿐이라, 운영 공개 전 감사에서 회사 경계 결함을 추가로 찾아 고쳤다(문제 해결 4).

핵심 흐름 ③ 실시간 알림 fan-out

SSE 연결은 여러 서버 인스턴스에 흩어질 수 있다. 한 인스턴스에서 생긴 알림을 모든 접속자에게 보내려면 모든 인스턴스가 모든 이벤트를 받아야 하므로, 공용 소비 그룹이 아니라 인스턴스마다 독립된 소비 그룹을 두었다. 알림을 발행한 인스턴스도 직접 밀지 않고 Kafka 로 받은 것만 밀어 중복 수신을 막는다. 알림은 DB 알림함에 먼저 저장해, 재시도·DLQ 없이도 접속하지 않은 사용자와 유실분을 조회로 보완한다. 트리거는 문의 등록(→관리자)·답변(→작성자)·중요 공지(→전체 고객사) 3종이고, 이후 다른 알림도 같은 알림함·SSE 경로를 재사용한다.

  • 트리거는 비동기로 실행하고 발행 대기 시간에 상한을 둬, Kafka 가 느려져도 답변·공지 API 가 막히지 않음
  • 사용자·인스턴스별 동시 연결 상한(초과 시 429), 세션이 무효화되면 열린 SSE 스트림도 종료
  • 공용 알림의 읽음 상태를 사용자별 기록으로 바꿔 회사 사이에 읽음이 공유되지 않게 함
  • 단계별 발행 성공·실패, 활성 연결, 거부, 연결 시간, 미읽음 지표 노출, 경보 규칙 2종·대시보드 패널 7개를 GitOps 저장소에 반영
  • EmbeddedKafka → 소비자 → SSE 를 잇는 종단 시험으로 발행부터 전달까지의 경로를 회귀 고정

개념 데이터 모델

실제 테이블·컬럼 이름이 아닌 개념 모델이다. 계약사(테넌트)가 모든 고객 데이터의 경계이고, 매출 조회 범위는 계약사에 연결된 매입처로 정해진다. 활성 매입처 연결은 매입처당 하나만 허용하는 부분 유니크 인덱스를 둬, 한 매입처가 두 계약사에 동시에 묶여 데이터가 교차 노출되는 일을 DB 가 거부한다. 알림은 관리자 전체·고객사 전체·개인 세 가지 수신 범위를 갖고, 공용 알림의 읽음은 사용자별로 따로 기록한다. 문의는 비로그인 제출도 받으므로 계약사·작성자 연결이 선택적이다. 스키마는 Flyway 로 버전 관리한다.

계약사 서비스 상태 전이

계약사는 상품·계약기간 없이 미계약으로 등록되고 대표 계정 초대가 함께 나간다. 관리자가 서비스 설정에서 상품·계약기간을 정하면 시작일에 따라 활성 또는 대기로 간다. 토큰은 활성 회사에만 발급하므로 미계약 회사와 시작일 전 대기 회사의 로그인은 '서비스 설정 미완료'로 막힌다. 계약 만료는 로그인·토큰 회전 때 상태를 바꾸는 지연 가드와, 요청마다 토큰의 계약 종료 클레임을 보는 즉시 가드 두 겹으로 막는다. 계정은 발급 직후 대기(임시 비밀번호)이고 비밀번호 재설정에 성공하면 활성으로 바뀌며, 운영자가 임시 비밀번호를 재발급하면 다시 대기로 돌아가고 세션이 즉시 무효화된다.

설계 결정왜 이렇게 했나

선택지를 비교해 고른 방식과 그 대가를 함께 적었다. 대가는 대부분 실제로 문제가 된 뒤 보완했다.

결정고른 방식왜대가·보완
인증 방식사내 SSO 대신 서비스가 직접 발급하는 JWT고객사 계정은 계약 상태·IP 허용 목록·임시 비밀번호 재설정·초대 만료 같은 서비스 정책을 따라야 해서, 로그인 판단을 서비스가 직접 통제하기 위해. 사내 SSO 는 직원용 도구에 둠토큰 회전·세션·블랙리스트를 직접 만들어야 했고, 병렬 요청의 동시 회전 문제를 겪은 뒤 보완(문제 해결 1)
언어·런타임Kotlin + Coroutines, Spring WebFlux + R2DBC(직접 결정)오래 걸리는 분석 조회, 실시간 알림 같은 장기 연결, 외부 호출이 한 서버에 섞여 있어 요청마다 스레드를 붙잡지 않는 비차단 구조가 맞았다. Coroutines 로 비동기 코드를 순차 코드처럼 읽히게 쓰고, Kotlin 의 null 안전성으로 응답·DTO 실수를 줄이려 했다비밀번호 해시·토큰 서명 같은 CPU 작업은 별도 스레드로 격리하고, 실행 중 JDBC 사용 금지(Flyway 기동 1회만 예외)를 규칙으로 둠
배포 구조단일 배포 + Gradle 모듈(모듈러 모놀리스)기능이 늘어도 배포 단위·이미지·CI·게이트웨이 경로를 새로 만들지 않기 위해. 새 모듈은 의존 추가만으로 자동 등록관리자·고객사가 함께 쓰는 공지·FAQ·문의가 인증 모듈에 쌓이자 운영관리 도메인 모듈로 추출(행위 변경 없이 기존 시험 통과). 공통 요소는 공통 모듈 한 곳에만
토큰 보관access 는 프론트 메모리, refresh 는 HTTP-only 쿠키(FE 와 합의)스크립트가 refresh 를 읽지 못하게(XSS 대비) 하고, 쿠키 자동 전송을 노린 요청(CSRF)은 Origin/Referer 허용 목록으로 한 번 더 막기 위해허용 출처 목록을 CORS 와 CSRF 검사가 함께 읽는 단일 설정으로 묶고 기동 때 형식 검증
토큰 갱신별도 갱신 API 없이 인증 필터가 만료 시 자동 회전, 새 access 는 응답 헤더프론트는 헤더의 토큰만 바꾸면 되고, 1회용 refresh 의 회전·재사용 탐지를 서버 한곳에서 처리병렬 요청의 동시 회전 문제가 생겨 사용자별 락과 직전 토큰 유예로 보완(문제 해결 1)
회사 식별고객사 영역의 회사 식별자는 토큰 클레임에서만요청 값을 바꿔 다른 회사 데이터에 접근하는 객체 수준 권한 우회를 구조로 막기 위해규칙만으로는 빈틈이 남아 DB 제약·타사 403 통합 시험·감사로 보완
실시간 전달SSE + DB 알림함 + 인스턴스별 Kafka 소비 그룹SSE 연결이 여러 인스턴스에 흩어지면 모든 인스턴스가 모든 알림을 받아야 함(공용 그룹이면 한 인스턴스만 받음). DB 에 먼저 저장해 접속하지 않은 사용자도 조회로 받게재시도·DLQ 없이 최신부터 소비하고 유실은 알림함 조회가 맡음. SSE 인증은 Bearer 헤더 전용
문의 접수제출은 이벤트 발행, 소비자가 멱등 키로 저장 + DLQ비로그인 문의까지 저장을 보장하고 중복 전달에도 한 건만 남기기 위해입력 길이 초과로 DLQ 에 조용히 쌓이던 경로를 QA 재검증에서 찾아 입력 정규화로 정정
외부 호출공통 빌더로 서킷브레이커·재시도·타임아웃 일괄 적용외부 장애가 리액티브 IO 스레드를 묶어 전체 API 를 늦추지 않게멱등하지 않은 호출은 재시도를 꺼 중복 저장을 막음
등록·수정 메타수정일·수정자는 nullable, DB 기본값 없음R2DBC 가 null 필드를 INSERT 에서 빼면 DB 기본값이 등록 시점에 수정일을 채우는 함정 때문잘못 정의된 기존 테이블을 마이그레이션으로 정정하고 작업공간 공통 규칙으로 명문화
API 계약모든 엔드포인트에 OpenAPI 설명과 에러 코드별 JSON 예시, 응답 스키마 자동 주입프론트가 백엔드 코드를 보지 않고 에러 분기까지 구현할 수 있게운영 환경에서는 API 문서 비활성

주요 기능

계약사 온보딩·관리

미계약 상태로 등록하고 대표 계정을 초대한 뒤, 서비스 설정에서 상품·계약기간을 정하면 활성·대기로 전이. 대표 변경은 한 트랜잭션에서 강등·승격하고 두 계정의 세션을 즉시 무효화하며 사유를 화면에 전달. 첨부는 서버 프록시와 열거할 수 없는 외부 ID 로만 노출

계정·보안 로그

관리자 계정 발급, 접속 이력·이상 접속(연속 실패·야간 접속)·변경 이력·첨부 열람 이력 조회와 CSV 내보내기(UTF-8 BOM·한글 헤더) 공통화

운영관리(공지·FAQ·1:1 문의)

관리자·고객사·비로그인 세 경로가 함께 쓰는 도메인 모듈. 공용 카테고리, 상단 고정·노출 기간, 앞으로만 진행하는 문의 3단계 상태(접수·처리중·답변완료), 저장 시 HTML 정화

고객사 셀프 관리

대표·사원이 소속 계정을 직접 관리(조회는 사원, 변경은 대표). 회사·사용자 식별자는 토큰에서만 받고, 타사 계정을 지정하면 403 이 나는 것을 회귀 시험으로 고정

비밀번호 찾기

메일 토큰 링크로만 재설정, 토큰은 1회성·사용자당 1개. 찾기를 신청하면 활성 세션을 폐기하고, 재설정 전까지 메일 링크 외의 경로(기존 비밀번호·변경 페이지)로 우회하지 못하게 함

실시간 알림

문의 등록→관리자, 답변→작성자, 중요 공지→전체 고객사 3종 트리거. 이후 추가된 알림도 같은 알림함·SSE 경로를 재사용

기획서 대조 개발 절차

기획서의 화면 요소·검증 규칙·기능 설명을 항목별로 쪼개 DTO 검증·상태 전이·에러 코드·응답 필드·권한과 1:1 대조하고 구현됨/누락/불일치/프론트 소관으로 분류. Figma MCP 로 에이전트가 화면 주석을 직접 읽게 하고, 주요 변경마다 멀티에이전트 적대 리뷰와 전체 시험을 관문으로 둠

CASE 01 / 04동시성제어

토큰 동시 회전 경쟁으로 모든 탭이 로그아웃되던 문제

문제 현황

전 탭 로그아웃
  • 운영 공개 전 프론트 연동 시험 중 발견
  • 자리를 비웠다 돌아오면 열린 모든 탭이 로그아웃
  • refresh 토큰을 오래 유지하는 설계 의미가 사라짐
  • 관리자·고객 계정을 함께 열면 고객 탭이 관리자 신원으로 바뀜

원인 분석

설계 빈틈
  • access 만료 직후 병렬 요청이 같은 1회용 refresh 로 동시 회전
  • 첫 요청만 성공, 나머지는 재사용 공격으로 판정돼 승자 세션까지 삭제
  • 직접 만든 재사용 탐지 설계가 정상 동시 요청을 고려 못 함
  • 쿠키는 브라우저당 하나, 필터는 토큰·쿠키 주인을 비교 안 함

해결 과정

락·유예 도입
  1. 로그로 물증 확보 후 사용자별 Redis 락으로 회전 직렬화
  2. 직전 토큰 쌍을 짧게 보관, 유예 안 재요청엔 같은 쌍 멱등 재응답
  3. 쓰기 순서는 유예 기록 먼저·새 토큰 나중, 끊겨도 재시도로 복구
  4. 주인 비교 가드·계정별 쿠키 슬롯 추가, AI 리뷰 지적 회귀도 수정

결과

회귀 고정
  • 동시 갱신 시험 4건이 모두 같은 새 토큰으로 수렴
  • 회귀 시험으로 고정, 프론트 코드 변경 없음
  • 다른 계정끼리 한 브라우저에서 서로 영향 없이 갱신
전체 설명 보기
문제 상황

운영 공개 전, 프론트와 개발 환경에서 연동 시험을 하던 중 자리를 비웠다 돌아오면 열려 있던 모든 탭이 로그아웃됐다. refresh 토큰을 오래 유지하도록 설계한 의미가 사라지는 문제였다. 같은 브라우저에서 관리자와 고객 계정을 함께 열면 고객 탭이 관리자 신원으로 바뀌는 문제도 함께 드러났다.

원인 분석

access 가 만료된 직후 SPA 의 병렬 요청들이 같은 1회용 refresh 쿠키로 동시에 회전을 시도했다. 첫 요청만 성공하고 나머지는 재사용 공격으로 판정됐고, 그 처분이 승자의 새 세션까지 지웠다. 본인이 만든 '1회용 회전 + 재사용 탐지' 설계가 정상 클라이언트의 동시 요청을 고려하지 못한 빈틈이었다. 신원이 바뀐 것은 refresh 쿠키가 브라우저당 하나라 마지막 로그인이 덮어쓰고, 필터가 만료된 access 의 주인과 쿠키 주인을 비교하지 않았기 때문이다.

해결 과정
  1. 개발 환경 로그로 물증 확보(승자 1건 성공, 나머지는 재사용 판정)
  2. 사용자별 Redis 분산 락(소유권 확인)으로 같은 사용자의 회전을 직렬화하고, 로그아웃·강제 무효화도 같은 락을 쓰게 해 무효화와 회전이 엇갈려 키가 되살아나는 경우를 막음
  3. 회전 성공 시 직전 토큰과 새 토큰 쌍을 짧게 보관해, 유예 시간 안에 직전 토큰이 다시 오면 같은 쌍을 멱등하게 재응답. 재사용 탐지는 유예 밖이거나 두 세대 이전 토큰일 때로 한정
  4. 요청 취소·인스턴스 종료로 쓰기가 중간에 끊겨도 다시 시도하면 복구되도록 취소 불가 구간과 쓰기 순서(유예 기록 먼저, 새 토큰 저장 나중)를 정함
  5. 만료 access 주인과 쿠키 주인을 비교하는 가드와 계정별 쿠키 슬롯을 넣고, AI 적대 리뷰가 찾은 락 취소 경쟁 상태와 쿠키 이름 변경으로 CSRF 2차 방어가 꺼지던 회귀를 함께 수정
결과

동시 갱신 4건이 모두 같은 새 토큰으로 수렴하는 것을 회귀 시험으로 고정했고, 프론트 코드는 바꾸지 않았다. 계정별 쿠키 슬롯으로 서로 다른 계정이 한 브라우저에서 서로 영향 없이 갱신된다.

CASE 02 / 04인증설계

새로고침 세션 유실 진단과 세션 정책 재설계

문제 현황

세션 유실
  • 운영 공개 전 연동 시험 중 분석 API 가 모두 401
  • 다시 로그인하면 '이미 로그인됨'으로 차단
  • QA 에선 쿠키를 지운 사용자가 기존 세션 끝까지 재로그인 불가
  • 이 문제가 QA 최우선 이슈로 올라옴

원인 분석

명세 불일치
  • Loki 요청 로그·회전 지표로 가설을 지워 명세·구현 불일치 확정
  • 문서는 새로고침 복원을 약속, 구현은 만료 access 일 때만 갱신
  • 메모리 access 가 사라진 새로고침 요청은 바로 401
  • 재로그인 차단은 '먼저 로그인한 세션 우선' 정책 때문

해결 과정

정책 재설계
  1. 토큰 없는 요청도 refresh 쿠키로 인증 복원, 실패 시 익명 진행
  2. 복원이 토큰 발급 통로가 될 critical 결함을 출처 게이트로 차단
  3. 관리자 신원이 고객 화면으로 가던 결함을 영역별 출처 결합으로 차단
  4. 중복 로그인은 기존 세션 인계로 전환, 기획 후속안대로 알림 후 인계

결과

병합 전 반영
  • 프론트 코드 변경 없이 새로고침 복원 동작
  • critical 포함 AI 적대 리뷰 확정 10건을 병합 전 반영
  • 사건·게이트·인계 규칙을 보안 정책 문서 정본으로 남김
전체 설명 보기
문제 상황

운영 공개 전 프론트 연동 시험 중 분석 API 가 모두 401 이 되고, 다시 로그인하면 '이미 로그인됨'으로 막혔다. 이후 QA 에서도 브라우저 쿠키를 지운 사용자가 기존 세션이 끝날 때까지 재로그인하지 못하는 문제가 최우선 이슈로 올라왔다.

원인 분석

프론트 연동 문서는 '새로고침하면 쿠키로 세션을 복원한다'고 약속했지만, 구현은 만료된 access 토큰이 왔을 때만 갱신했다. 새로고침으로 메모리의 access 가 사라진 요청은 바로 401 이 됐다. 재로그인이 막힌 것은 '먼저 로그인한 세션 우선' 정책 때문이었다.

해결 과정
  1. 요청 로그(Loki)와 회전 지표로 가설을 하나씩 지우고 명세·구현 불일치를 원인으로 확정
  2. 토큰 없는 요청도 refresh 쿠키로 인증을 복원하는 부트스트랩 구현: 실패하면 401 대신 익명으로 진행하고, 계정 쿠키가 여럿이면 추측하지 않음
  3. AI 적대 리뷰가 '복원 기능이 토큰 발급 통로로 악용될 수 있다'는 critical 결함을 찾음 → 판정 후 실제 서비스 화면에서 온 요청만 복원하는 게이트로 병합 전 차단, 회전 때 IP 허용 목록 재검사를 포함해 확정 10건 반영
  4. 이후 관리자 신원이 고객 화면으로 이어지는 결함을 본인 관리자 계정에서 발견 → 회전 전에 계정의 영역(관리자·고객)을 조회하고 영역별 출처를 결합해 차단, 개발 환경 실경로로 검증한 뒤 시험 흔적 정리
  5. '먼저 로그인한 세션 우선'은 쿠키를 잃은 정당 사용자만 가두고 비밀번호를 가진 사람은 막지 못한다는 근거로 기존 세션 인계로 전환(밀려난 세션은 즉시 차단), 기획 후속안에 맞춰 '중복 로그인 알림 후 확인 시 인계'로 조정
결과

프론트 코드 변경 없이 새로고침 복원이 동작했고, 복원 기능의 critical 결함을 포함한 AI 적대 리뷰 확정 10건을 병합 전에 반영했다. 사건·게이트·인계 규칙은 보안 정책 문서에 정본으로 남겼다.

CASE 03 / 04보안설계

삭제 계정 이메일 재사용 도입과 교차 테넌트 오조작 선제 차단

문제 현황

정책 변경
  • QA 요청으로 삭제 계정 이메일 재사용 허용 필요(기획 확정)
  • 조회·생성 경로 여러 곳이 '이메일은 하나뿐' 가정에 기댐

원인 분석

교차 오조작
  • 계정 유일성을 이메일 전체 유니크에 맡기고 있었음
  • 일부 경로는 번호로 찾은 계정을 이메일로 다시 해석
  • 재사용 시 삭제 계정 처리가 다른 회사 신규 계정에 영향 가능
  • 개발·QA 재검증에서 발견, 고객 노출 없음

해결 과정

경로 정비
  1. 삭제 계정 제외 부분 유니크로 바꾸고 조회 15곳을 활성 한정
  2. 계정 생성 경로 4곳에 사전 중복 검사·409·공백 정규화
  3. 조회한 계정 행을 그대로 전달, 삭제 계정 번호 지정은 404 통일
  4. 같은 유형을 멀티에이전트 전수조사·반증 검증으로 점검·수정

결과

공개 전 차단
  • QA 백엔드 티켓 6건 반영
  • 활성 한정 조회 15곳·계정 생성 경로 4곳 정비
  • 교차 오조작을 운영 공개 전 차단, 회귀 시험으로 고정
전체 설명 보기
문제 상황

운영 공개 전 QA 요청으로 삭제된 계정의 이메일을 다시 쓸 수 있게 해야 했다(정책은 기획 확정). 그동안 '이메일은 하나뿐'이라는 가정에 기댄 조회·생성 경로가 여러 곳에 있었다.

원인 분석

계정 유일성을 이메일 전체 유니크에 맡기고 있었고, 일부 경로는 계정 번호로 찾은 계정을 이메일로 다시 해석했다. 재사용을 허용하자 한 회사의 삭제 계정 처리가 같은 이메일을 쓰는 다른 회사 신규 계정에 영향을 줄 수 있는 교차 오조작이 생겼다. 개발·QA 재검증 단계에서 찾았고 고객에게 노출되지 않았다.

해결 과정
  1. 이메일 전체 유니크를 삭제 계정을 뺀 부분 유니크 인덱스로 바꾸고, 이메일 기반 조회 15곳을 활성 계정 한정으로 전환
  2. 계정 생성 경로 4곳에 사전 중복 검사·중복 시 409·공백 정규화 적용
  3. 재검증에서 교차 오조작을 찾아 조회한 계정 행을 그대로 넘기도록 분리하고, 계정 번호로 지정하는 경로는 삭제 계정이면 404 로 통일
  4. 같은 유형이 다른 경로에 남았을 가능성을 멀티에이전트 전수조사와 반증 검증으로 점검해 확정 건을 수정(문제 해결 4의 감사 결과에 합산)
  5. 앞서 개발 환경에서 문의 답변 알림이 다른 계정으로 가던 문제를 고치며 세운 '이메일은 신원 기준이 아니다' 원칙을 이번 점검 목록으로 사용
결과

QA 백엔드 티켓 6건을 반영하고 활성 계정 한정 조회 15곳·계정 생성 경로 4곳을 정비해, 교차 오조작을 운영 공개 전에 막고 회귀 시험으로 고정했다.

진행 순서

  1. 2026.08
    신원 기준 교정(개발 환경)
    문의 작성자 신원을 바뀔 수 있는 로그인 ID 대신 제출 시점의 내부 식별자로 고정, '이메일은 신원 기준이 아니다' 원칙
  2. 2026.08
    삭제 계정 이메일 재사용 허용
    부분 유니크 인덱스, 활성 계정 한정 조회, 생성 경로 사전 검사
  3. 2026.08
    재검증에서 교차 오조작 발견
    조회한 행을 그대로 전달하도록 분리, 삭제 계정 지정 시 404
  4. 2026.08

    멀티에이전트 전수조사와 반증 검증으로 확정 건 수정
  5. 2026.09
    운영 공개
    공개 전 반영 완료, 회귀 시험으로 고정

이메일처럼 바뀌거나 다시 쓰일 수 있는 값은 신원 기준이 될 수 없다. 신원은 변하지 않는 내부 식별자로 고정하고, 앞선 결함에서 얻은 원칙을 다음 정책 변경의 점검 목록으로 쓴다.

CASE 04 / 04보안점검

운영 공개 전 AI 멀티에이전트 보안 감사와 공개 범위 하드닝

문제 현황

공개 직전
  • CBT 직전 짧은 기간에 인증·권한·입력·설정 전반 점검 필요
  • 기능이 빠르게 늘어 변경 단위 리뷰만으론 부족
  • 에이전트 하나의 리뷰는 오탐이 섞여 그대로 반영 불가

원인 분석

시험 사각
  • 결함은 이미 개발 환경에 배포된 코드에 있었음
  • 설정 검증·권한 경계·IP 판정·입력 정화는 여러 모듈에 걸친 축
  • 이런 축은 기능별 시험이 잘 못 잡음
  • 외부 공개 앞두고 게이트웨이 공개 범위도 좁혀야 했음

해결 과정

감사·하드닝
  1. 멀티에이전트로 10개 축 병렬 탐지, 발견마다 별도 에이전트가 반증
  2. 필수 비밀 없으면 기동 실패(fail-fast), 관리자 등급 권한 경계 보강
  3. IP 판정·요청 제한·저장형 XSS 겹 방어, 무효 세션의 SSE 종료
  4. 게이트웨이 경로 차단·HTTPS·HSTS 적용 뒤 고객 도메인만 공개

결과

수정 후 공개
  • 확정 결함 고위험 2건 포함 10건(중위험 8건) 수정
  • 시험과 함께 고친 뒤 고객 도메인만 외부 공개
  • '탐지 + 반증' 리뷰를 일반 기능 변경 관문으로도 사용
전체 설명 보기
문제 상황

운영 공개(CBT) 직전, 짧은 기간에 인증·권한·입력·설정 전반의 결함을 찾아야 했다. 기능이 빠르게 늘어난 뒤라 변경 단위 리뷰만으로는 범위를 다 덮기 어려웠고, 에이전트 한 개의 리뷰 결과는 오탐이 섞여 그대로 반영할 수 없었다.

원인 분석

결함은 이미 개발 환경에 배포된 코드에 있었다. 기동 시 설정 검증, 관리자 등급 사이의 권한 경계, 클라이언트 IP 판정, 입력 정화처럼 여러 모듈에 걸친 축은 기능별 시험이 잘 잡지 못했다. 외부 공개를 앞두고 게이트웨이 경로 구성에도 공개 범위를 좁혀야 할 곳이 있었다.

해결 과정
  1. Claude Code 멀티에이전트로 10개 축(테넌트 격리·인젝션·파일 업로드·토큰·세션 등)을 병렬 탐지하고, 발견마다 별도 에이전트가 반증·재현하게 해 통과한 확정 건만 판정·수정
  2. 필수 비밀 설정이 없으면 기동을 실패시키고(fail-fast), 관리자 등급 사이의 권한 경계를 보강
  3. 클라이언트 IP 판정 강화, 비로그인 문의 요청 제한, 저장형 XSS 겹 방어(저장 시 HTML 정화), 세션 무효화 시 열린 SSE 스트림 종료
  4. 게이트웨이 구성도 따로 감사해 공개 범위 밖 경로를 차단하고, HTTPS 강제·HSTS·크롤링 차단·무인증 요청 제한을 GitOps 로 적용한 뒤 고객 도메인만 공개
  5. 인프라·제품 결정이 필요한 항목은 백로그로 문서화하고, 관리 콘솔은 사내망 잠금을 유지한 채 커밋 하나로 다시 잠글 수 있게 구성
결과

확정 결함 고위험 2건 포함 10건(중위험 8건)을 시험과 함께 고친 뒤 고객 도메인만 외부에 공개했다. 같은 '탐지 + 반증' 리뷰는 보안 외의 일반 기능 변경에도 검증 관문으로 썼다.

배운 점

에이전트 하나의 자기 검증을 믿지 않고 탐지와 반증을 나눈다. 고치지 못한 위험은 숨기지 않고 문서로 남기고, 공개 범위는 되돌리기 쉬운 형태로 연다.

정리이 프로젝트에서 남긴 것

회사 경계는 지침만으로는 빈틈이 남았고, 세션 보안 규칙은 정상 사용자의 병렬 요청을 공격으로 판정하거나 재로그인을 막기도 했다. 그래서 회사 경계는 토큰 클레임·DB 제약·타사 접근 403 시험·공개 전 감사로 겹쳐 막고, 세션 규칙은 정상 사용자 입장에서 다시 따져 고친 뒤 공개했다.
