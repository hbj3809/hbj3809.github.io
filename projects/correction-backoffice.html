프로젝트 개요
무엇을, 왜 만들었나

국내 대형 의약품 유통사의 매출 데이터를 제약사 고객(pharmscope)에게 보여 주기 전에 현업 데이터 운영팀이 검수⁠·보정합니다. 이 백오피스는 그 보정 루프를 화면⁠·API⁠·처리 큐로 옮긴 사내 도구입니다. 1차로 만든 새 계산 엔진은 운영 전환에서 실패해 약 4시간 만에 되돌렸습니다. 그 뒤 기존 보정 표를 유일한 정본으로 두고, 영향받은 달만 한 트랜잭션으로 재처리하는 가벼운 구조로 다시 설계했습니다. 33개월을 실측해 차이 0을 확인한 금액 항등식 '원천 = 정상 + 반려'를 자동 롤백 가드로 두고, 접수 당일 반영을 운영에 올렸습니다. 공급사 매출 다시 받기, 반영 알림, 경보까지 서버와 배치 쪽을 설계⁠·구현했습니다.

개요배경⁠·목표⁠·내 역할

pharmscope는 국내 대형 의약품 유통사의 매출 데이터를 제약사 고객에게 분석 화면으로 제공하는 서비스입니다. 원천 데이터에는 표준코드⁠·주소⁠·채널이 비거나 틀린 행이 섞여 있어 현업 데이터 운영팀이 검수하고 보정합니다. 이 보정은 엑셀 회신 → 개발자 수기 DB 입력 → 다음 날 새벽 재처리에 기대고 있었습니다. 지난 달 데이터에 대한 보정은 새벽 재처리에 다시 반영되지 않는 결함도 있었습니다. 이 루프를 화면⁠·API⁠·처리 큐로 옮겨, 접수한 보정이 그날 고객 화면에 반영되는 사내 control plane을 만들었습니다.

  • 목표보정 접수 당일 반영, 틀린 금액이 공개되지 않게 자동 차단, 사람이 DB를 직접 고치는 일 없애기
  • 내 역할재설계 방향(기존 보정 표를 정본으로 하는 8단계 전환)을 정해 승인받음. 경보와 고객 API 쪽 반영 알림까지 설계⁠·구현
  • 다른 사람 몫화면 구현은 FE 개발자, 검수 기준과 검수 입력은 현업 데이터 운영팀. 기존 전처리 구조는 다른 사람이 만든 것이고, 그 위에서 재설계
  • 개발 방식Claude Code 멀티 에이전트 워크플로(조사⁠·설계안⁠·심사⁠·반박 검토). 코드⁠·PR⁠·읽기 확인은 에이전트, 병합⁠·운영 SQL⁠·되돌릴 수 없는 단계 실행⁠·결정은 본인

아키텍처

화면⁠·관리자 API⁠·배치 작업⁠·고객 API의 책임을 나눴습니다. 관리자 API는 접수⁠·묶음⁠·설정과 실행 요청까지만 맡습니다. 실제 반영(보정 표 쓰기와 재처리)은 배치 작업이 매출 DB 안에서 한 트랜잭션으로 합니다. 고객 API는 조회 SQL⁠·인덱스⁠·캐시 키를 그대로 두고, '공개 시각'이 바뀌면 다음 조회부터 새 값을 읽습니다. 중앙 DB(프로젝트⁠·역할⁠·감사)는 특정 사업에 묶지 않아, 다른 사업도 같은 기반에 얹을 수 있습니다.

보정 반영 흐름접수 → 묶음 → 반영

보정 한 건이 고객 화면에 닿는 길입니다. 접수한 보정은 그날 낮 예약 묶음에 들어가거나, 운영자가 즉시 실행을 요청합니다. 여러 달에 걸친 접수는 업무 외 시간으로 미룹니다.

  • 영향받은 달원문 키(제품⁠·배송처)가 관측된 달 색인으로 계산해 전 기간을 다시 계산하지 않음
  • 안전장치금액 항등식 '원천 = 정상 + 반려'가 깨지면 트랜잭션 전체를 되돌리고 실패로 닫음
  • 자동 중지보정이 도는 동안 고객 조회에 시간 초과가 생기면 예약 처리를 멈추고, 관리자가 재개할 때까지 대기
  • 확정과 공개 표시 분리확정 뒤 멈춘 묶음은 다음 점검 작업이 이어 받아 공개까지 마무리
  • 반영 알림고객 조회 경로 밖의 작업이 끝난 묶음을 읽어 어드민⁠·영향 계약사 알림 생성

보정 묶음 상태

묶음은 상태 기계로 관리합니다. 서버가 상태를 판정해 화면 상단 띠에 '오늘 실패', '확정 뒤 공개 대기', '즉시 실행이 오래 대기'를 급한 순서로 보여 줍니다. 운영자는 화면만 보고 지금 손댈 곳을 압니다. 여러 달에 걸친 접수는 처음부터 야간 대기로 저장되고, 그날 시작하지 못한 즉시 묶음은 실패로 닫혀 재시도를 기다립니다.

개념 데이터 모델

실제 테이블 이름 대신 개념 이름으로 그린 데이터 모델입니다. 보정의 정본은 기존 보정 표 하나뿐입니다. 보정 표의 행마다 마지막으로 적용한 묶음을 남겨, 화면에 그 행이 어디서 왔는지(보정 접수⁠·이관⁠·기록 없음)를 보여 줍니다. 예전 수기 보정 이력도 묶음 이력으로 옮겼습니다.

  • 직원⁠·역할⁠·감사: 중앙 DB, 특정 사업에 묶지 않음
  • 검수 항목⁠·접수⁠·묶음⁠·보정 표⁠·키 관측 달 색인⁠·다시 받기: 매출 DB
  • 보정 표 범주: 표준코드⁠·주소⁠·채널⁠·검토 완료 목록

8단계 전환

4개 저장소(고객 API⁠·DB 마이그레이션, 배치, 관리자 API, 배포 매니페스트)에 걸친 전환을 8단계로 나눴습니다. 단계마다 통과 조건, 되돌리는 방법, 보관본을 먼저 정한 뒤 진행했습니다.

  1. 1단계
    기준선 측정과 되돌리기 실증기준선 측정 도구를 먼저 만들고, Testcontainers로 마이그레이션 순서와 옛 이미지 기동을 실증해 되돌리기를 '이미지 태그 교체'로 단순화
  2. 2단계
    고객 API 요청 경로 정리요청마다 되풀이되던 동의 철회 접근 확인 조회를 줄임. 처음 설계한 필터 제거안은 대조 실험에서 유일한 차단 장치로 드러나 철회하고, 중복 조회 제거와 짧은 메모로 대체
  3. 3단계
    폐기 공개본 정리되돌린 1차 엔진의 공개본 파티션을 업무 외 시간에 나눠 지우며 회차마다 잠금 대기를 감시
  4. 4단계
    배치 정비전처리 판정 조각을 공유 모듈로 글자 그대로 옮기고 동등성 하네스로 동작이 같음을 확인. 원문 키 관측 달 색인 갱신, 검수 항목 생산, 점검⁠·보정 실행 작업 추가
  5. 5단계
    관리자 API 재배선접수⁠·묶음⁠·즉시 실행⁠·예약 설정⁠·키워드 사전을 새 구조에 연결하고, 옛 경로는 '없어진 기능' 응답(410)으로 닫음
  6. 6단계
    운영 파일럿묶음 처리 시작 → 공개 1개월분 91초⁠·4개월분 328초. 읽기 전용 대조로 의도하지 않은 데이터 변동이 없는지 확인
  7. 7단계
    사람 계정의 보정 표 쓰기 권한 회수모든 변경이 묶음 이력과 영향월 재처리를 거치게 함
  8. 8단계
    폐기 엔진 객체 삭제표 73개⁠·함수 154개 삭제. 운영 스키마 덤프로 격리 DB 리허설, 되돌릴 수 없는 단계마다 보관본 해시 대조. 확정 뒤 첫 평일 새벽 처리와 월마감 통과

권한⁠·감사

직원 비밀번호와 인증은 사내 SSO가 소유하고, 백오피스는 서버 세션만 가집니다(BFF). 브라우저에는 토큰 원문을 주지 않습니다.

  • 권한 판정: 검증된 토큰 역할과 중앙 DB의 현재 부여가 둘 다 있을 때만 통과하고, 한쪽에만 남은 권한은 거절
  • 권한 부여⁠·회수: 접수 후 운영자 동기화 도구가 SSO 역할과 맞춤. 서비스 프로세스에는 SSO 관리자 자격 없음
  • 감사: 인증된 변경 요청은 실패까지 감사 기록. 감사 조회는 범위 밖 기록의 존재 여부를 숨김
  • 동기화 도구가 수명이 짧은 관리자 토큰을 갱신하지 않아 중간에 멈춘 일을 겪은 뒤, 실행 중 재인증 래퍼와 멈춘 지점별 복구 절차 추가

매출 다시 받기

새벽 수집이 실패하거나 오류 없이 0건으로 끝난 날의 매출을, 다음 새벽 자동 보충을 기다리지 않고 그날 다시 받는 기능입니다. 낮 재수집에는 위험이 셋 있었습니다. 멈춘 작업이 보정을 막을 수 있고, 대량 삭제가 고객 캐시를 밀어낼 수 있으며, 고객 알림에 재수집분이 섞일 수 있었습니다. 이 위험을 먼저 정리하고 설계했습니다.

  • '그날 원천 행이 없음'을 두 번 증명한 날만 적재 → 낮에 삭제 없음
  • 두 개의 시각: 엑셀 다운로드는 원천을 바로 읽어 받은 직후 바뀌고, 화면은 공개 표시 뒤 바뀜. 화면 상태 문구와 운영 문서로 안내
  • 멱등 재전송⁠·하루 상한⁠·연속 실패 시 자동 꺼짐. 원인 메모를 남겨야 다시 켜짐
  • 재수집 날짜는 고객 영향 계산⁠·알림에서 제외
  • 고객 API⁠·관리자 API⁠·배치 세 저장소 병행 구현, 저장소별 전체 시험 통과를 배포 관문으로 삼음. 설계 착수 4일 만에 운영 켜기, 스모크 요청 → 완료 약 32초
  • 버튼 화면은 FE 개발자. 기능 제안과 정책 결정은 본인

오픈 대응과 감시

현업에 연 뒤에는 요청을 빨리 처리하는 것과 '조용한 실패'를 줄이는 데 집중했습니다.

오픈 첫날 현업 요청 18항목

현업에 연 첫날 불편⁠·누락 18항목(질문 1건 포함)이 들어왔습니다. 항목마다 누락⁠·불일치⁠·설계상 정상으로 당일 판정하고, 17항목을 그날 운영 배포했습니다. 스키마⁠·권한 변경 없이 새 조회 경로와 보류 해제 동작을 더했고, 느려지면 끌 수 있는 기능 스위치를 두었습니다.

FE 화면 개선 계약

프론트엔드의 개선 요청을 코드 근거로 대조해 결정안 16개로 정리했습니다. 실수를 고치려면 여러 검수자가 함께 쓰는 예약 묶음을 통째로 취소해야 하는 구조였습니다. 이 부분은 '이 접수만 취소'를 두고, 앞 값이 아직 반영되지 않았으면 409로 거절하는 규칙으로 원안과 다르게 합의했습니다. 서버⁠·배치 변경은 3일 만에 운영에 반영했습니다. 스테이징이 없어 시험 자료 요청은 운영 스키마 단계 통합 시험으로 대신했고, 세부 2건은 합의대로 보류했습니다.

보정 반영 알림

보정이 고객 데이터에 반영되면 어드민과 영향받은 계약사에 알림을 만듭니다. 고객 조회 경로 밖의 확인 작업이 끝난 묶음을 읽고, 조회 연결에 대기가 있으면 그 회차를 건너뜁니다. 꺼짐 → 로그만 → 어드민만 → 전체 순서로 켰습니다.

경보와 처리 상태 점검

경보 규칙 14종(가상 시계 시험 41개)과 알림 라우팅 안전 적용 도구를 만들었습니다. 보정마다 울리던 측정 오경보는 원인을 찾아, 과거 18개 창 재생 기준 8건 → 0건↓으로 줄였습니다(1단계 수정 기준). 감시는 처리 상태 점검⁠·작업별 실패 알림⁠·지표 경보의 세 층으로 정리했습니다. 경보 없이 지나갈 수 있는 실패는 목록으로 만들어 매일 확인 항목으로 두었습니다.

분석 제외 키워드 사전

현업이 의약외품을 분석에서 빼 달라고 요청했습니다. 읽기 전용 실측으로 대상 대부분이 이미 검토 완료 목록에 있음을 확인하고, 데이터를 바꾸지 않는 축소안을 택했습니다. 등록⁠·해제는 재처리 없이 바로 반영됩니다. 검토 중에는 NOT (A OR K) 형태의 실행 계획 회귀를 병합 전에 잡았습니다.

한국어 문서화 게이트

1차 구축 때 docstring⁠·DB 주석⁠·OpenAPI 설명을 한국어로 강제하는 AST 기반 CI 게이트를 넣었습니다. 지금도 전체 시험이 문서화 누락과 DB 주석⁠·모델 설명의 불일치를 함께 검사합니다.

폐기 엔진 정리

되돌린 1차 엔진의 표 73개⁠·함수 154개를 마이그레이션으로 지웠습니다. 운영 스키마 덤프를 격리 DB에 넣어 리허설하고, 되돌릴 수 없는 단계마다 보관본을 해시로 대조했습니다.

CI 시간 원인 계측

백엔드 빌드가 오래 걸리는 원인을 계측해, 시험 DB가 CPU 상한에 걸려 느려지는 것과 문서 시험이 명세를 반복 생성하는 것을 찾았습니다. 시험을 빼는 대신 운영 스키마 단계 통합 시험을 더하고, 시험 단계를 우회하는 파이프라인 변경을 막는 계약 시험을 붙였습니다.

성과

보정 반영을 다음 날 새벽에서 접수 당일로 옮겼고, 지금은 접수부터 고객 화면 반영까지 10분 이내에 끝납니다. 낮 재처리는 영향받은 달만 짧게 돕니다.

  • 보정 반영: 다음 날 새벽 재처리 → 접수 당일(낮 예약 묶음⁠·즉시 실행)
  • 운영 확인: 영향 계약사가 있는 보정 묶음에서 고객 반영 알림 실제 발송, 다시 받기로 빈 날 복구, 측정 경보는 전용 카운터 기준으로 측정
  • 실사용 운영(하루 평균): 표준코드 보정 2~5건, 주소 보정 1~2건, 검토 완료 처리 10건, 채널 변경 1~2건. 즉시 실행⁠·예약 접수 처리 8분 이내, 고객 화면 반영까지 10분 이내
  • 재계산 범위: 1차 엔진안 전 기간 약 3.5시간 → 영향받은 달만(1개월분 91초). 설계안별 범위를 비교한 값이며, 같은 작업의 전후가 아님
  • 금액 항등식 '원천 = 정상 + 반려' 33개월 실측 차이 0 → 낮 재처리 자동 롤백 가드
  • 폐기 엔진 표 73개⁠·함수 154개 삭제
  • 다시 받기: 설계 착수 4일 만에 운영 켜기, 스모크 요청 → 완료 약 32초, 3개 저장소 전체 시험 실패 0
  • 오픈 첫날 현업 요청 18항목 당일 판정⁠·17항목 당일 운영 배포, FE 요청은 결정안 16개⁠·3일 만에 서버 반영
  • 경보 규칙 14종(가상 시계 시험 41개), 측정 오경보 8건 → 0건↓(과거 18개 창 재생, 1단계 수정 기준)

  • 현업이 지난 달 보정을 회신해도 고객 화면에 미반영

  • 새벽 전처리는 대상일이 속한 달만 다시 생성

  3. 금액 항등식 '원천 = 정상 + 반려' 실측, 33개월 차이 0 확인
  4. 항등식을 낮 재처리 자동 롤백 가드로 채택, 파일럿 대조 뒤 운영 전환

결과

당일 반영
  • 보정 접수 당일 반영(낮 예약 묶음⁠·즉시 실행)
  • 파일럿 처리 시작부터 공개까지 1개월분 91초⁠·4개월분 328초
  • 금액 항등식 33개월 실측 차이 0
전체 설명 보기
문제 상황

현업이 지난 달 데이터에 대한 보정을 회신해도 고객 화면에 반영되지 않는 경우가 있었습니다. 반영은 다음 날 새벽 재처리에 기대고 있었습니다.

원인 분석

새벽 전처리는 대상일이 속한 달만 다시 만들고, 보정 표는 실행 시점에 조인됩니다. 그래서 지난 달은 다시 전처리되지 않아 보정이 반영될 기회가 없었습니다.

해결 과정
  1. 원문 키(제품⁠·배송처)가 관측된 달을 담는 색인을 월 전처리 트랜잭션 안에서 갱신해, 보정 키로 영향받은 달을 정확히 계산
  2. 보정 표 쓰기와 영향받은 달 재처리를 한 트랜잭션으로 묶고, 떨어진 달도 한 번에 처리
  3. 전 기간 금액 항등식 '원천 = 정상 + 반려'를 읽기 전용으로 실측해 33개월 차이 0 확인
  4. 이 항등식을 낮 재처리의 자동 롤백 가드로 채택
  5. 파일럿에서 읽기 전용 대조로 의도하지 않은 변동이 없는지 확인한 뒤 운영 전환
결과

보정 접수 당일 반영(낮 예약 묶음⁠·즉시 실행), 파일럿 묶음 처리 시작 → 공개 1개월분 91초⁠·4개월분 328초, 금액 항등식 33개월 실측 차이 0

배운 점

CASE 03 / 04오경보

보정할 때마다 울리던 '측정 실패' 오경보원인 규명과 전용 카운터

문제 현황

오경보
  • 고객 조회 시간 초과 시 예약 처리 자동 중지 장치 운영
  • 보정 묶음 실행마다 '측정 실패' 경고가 팀 메신저로 발송
  • 트래픽이 적은 시기라 소음이지만, 끄면 진짜 고장도 숨음

원인 분석

원인 규명
  • 요청 지표(Micrometer) 고객 경로 계열은 첫 요청 때 생성
  • 파드 재기동 뒤 고객 요청 0건이면 계열 자체가 없음
  • 빈 결과를 측정 실패로 읽고 있었음

해결 과정

2단계 수정
  1. 경고 끄기⁠·측정 경고 등급 낮추기 안은 배제
  2. 1단계: 표본이 비면 기준 지표로 다시 질의해 '측정 성공⁠·표본 0' 기록
  3. 2단계: 기동 때 0으로 등록하는 전용 카운터, 롤링 중 파드는 라벨로 짝지음
  4. 운영 지표 재생, 새 시험이 수정 전 코드에서 먼저 실패하는지 확인

결과

해결
  • 측정 오경보 8건 → 0건↓(과거 18개 창 재생, 1단계 기준)
  • 자동 중지 판단 로직은 그대로 유지
  • 전용 카운터로 근본 원인 제거
전체 설명 보기
문제 상황

보정이 도는 동안 고객 조회에 시간 초과가 생기는지 재서, 문제가 있으면 예약 처리를 자동으로 멈추는 장치가 있습니다. 그런데 보정 묶음을 실행할 때마다 이 장치가 '측정 실패, 자동 중지 판단 불가' 경고를 팀 메신저로 보냈습니다. 고객 트래픽이 적은 시기라 소음이었지만, 경고를 끄면 진짜 고장도 숨습니다.

원인 분석

요청 지표(Micrometer)에서 고객 경로 계열은 첫 요청 때에야 만들어집니다. 파드가 다시 뜬 뒤 고객 요청이 0건이면 계열 자체가 없어 빈 결과가 나오는데, 이를 측정 실패로 읽고 있었습니다.

해결 과정
  1. 경고를 끄거나 측정 경고 등급을 낮추는 안은 배제
  2. 고객 요청이 없는 구간에서는 지표 계열이 아예 없다는 원인 규명
  3. 1단계: 표본이 비면 같은 영역의 기준 지표로 한 번 더 질의해 '측정 성공⁠·표본 0'으로 기록
  4. 운영 지표를 읽기 전용으로 재생해, 정상 측정 창은 값이 그대로인지 확인
  5. 2단계: 고객 API가 기동 때 0으로 등록하는 전용 카운터를 두고, 롤링 교체 중인 파드는 파드 라벨로 짝지어 배포 순서와 무관하게 동작
  6. 새 시험이 수정 전 코드에서 먼저 실패하는지 확인
결과

측정 오경보 8건 → 0건↓(과거 18개 창 재생, 1단계 수정 기준). 자동 중지 판단 로직은 그대로 두고, 전용 카운터로 근본 원인을 없앰

배운 점

경고를 끄는 것은 수정이 아닙니다. 경고가 비어 있는 이유(지표가 언제 생기는가)를 알아야 소음과 고장을 가를 수 있습니다.

CASE 04 / 04경보 공백

서비스가 멈춰도 알림이 없던 공백경보 규칙 14종과 안전 적용 도구

문제 현황

경보 공백
  • 백오피스 파드가 재시작하거나 멈춰도
  • 팀 메신저로 알림이 오지 않음

원인 분석

규칙⁠·라우팅
  • 백오피스 전용 경보 규칙 없음
  • 알림 라우터가 등록 안 된 경보를 수신자 없이 버림
  • 라우팅 설정이 Git 밖에 있어 손으로 고치는 경로가 위험

해결 과정

경보 신설
  1. 실제 수집 지표만으로 경보 규칙 14종 작성(멈춤⁠·재시작 반복⁠·5xx 등)
  2. 경보 요약에 무슨 일⁠·영향⁠·할 일⁠·확인할 곳 기재
  3. 가상 시계 시험 41개로 재시작 깜빡임 재현⁠·차단
  4. 라우트 도구: 미리 보기 뒤 지문 일치 시만 변경, 백업⁠·되돌리기 제공

결과

운영 확인
  • 백오피스 경보 규칙 14종 배포(가상 시계 시험 41개)
  • 운영에서 팀 메신저 수신 확인
  • 기존 경보의 수신자는 그대로
전체 설명 보기
문제 상황

백오피스 파드가 재시작하거나 멈춰도 팀 메신저로 알림이 오지 않았습니다.

원인 분석

백오피스 전용 경보 규칙이 없었고, 알림 라우터는 등록되지 않은 경보를 수신자 없이 버리고 있었습니다. 라우팅 설정은 Git 밖에 있어, 손으로 고치는 경로 자체가 위험했습니다.

해결 과정
  1. 운영 Prometheus에 실제로 있는 지표만 골라 경보 규칙 14종 작성(멈춤⁠·재시작 반복⁠·시작 불가⁠·5xx⁠·응답 지연⁠·메모리 과다 등)
  2. 경보 요약에 '무슨 일⁠·영향⁠·할 일⁠·확인할 곳'을 적음
  3. promtool 가상 시계 시험 41개: 재시작 간격이 문턱을 조금 넘으면 해소 알림이 끼어드는 깜빡임을 재현해 막고, 그 장치를 빼면 시험이 실패함을 확인
  4. 라우트 적용 도구: 기본은 미리 보기(바뀔 줄과 지문). 지문이 맞을 때만 설정 키 하나를 바꾸고, 원문 백업⁠·되돌리기 제공
  5. 지난 운영 지표를 재생해 예상 알림량을 미리 확인
결과

백오피스 경보 규칙 14종 배포(가상 시계 시험 41개). 운영에서 백오피스 경보가 팀 메신저로 오는 것을 확인했고, 기존 경보의 수신자는 그대로입니다.

배운 점

경보는 '규칙이 있다'로 끝나지 않습니다. 시험으로 울려 보고, 받는 곳까지 가는지 확인해야 합니다. Git 밖 설정은 사람 손 대신 미리 보기⁠·지문 확인을 거치는 도구로만 바꿉니다.

정리이 프로젝트에서 남긴 것

보정이 고객 화면에 닿는 길을, 사람이 DB를 직접 고치지 않고 묶음 이력⁠·영향받은 달 재처리⁠·금액 항등식 확인을 거치는 한 길로 모았습니다. 1차 엔진을 되돌린 경험에서, 새 부품을 더하기보다 기존 보정 표와 고객 조회 경로를 그대로 두고 되돌리기 쉬운 쪽을 고르는 기준을 얻었습니다.
