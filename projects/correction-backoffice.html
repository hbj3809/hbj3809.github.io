데이터 보정·검수 백오피스

현업 데이터 운영팀이 매출 데이터를 검수하고 보정하는 루프를 엑셀 왕복에서 화면·API 로 옮기고, 보정이 접수 당일 고객 화면에 반영되게 했습니다. 한 번 실패한 뒤 다시 설계했습니다.

문제

보정은 엑셀 회신 → 수기 DB 입력 → 다음 날 새벽 재처리에 기대고 있었습니다. 게다가 지난 달 데이터에 대한 보정은 새벽 재처리에 다시 반영되지 않는 결함도 있었습니다.

1차 시도와 되돌림

처음에는 새 계산 엔진과 공개본을 따로 만드는 큰 구조로 갔고, 고객 조회를 새 공개본으로 전환한 날 보정 계산이 실패했습니다. 약 4시간 만에 기존 경로로 되돌리고 같은 밤 정상 운행을 확인했습니다. 원인은 "좁은 시험 성공을 운영 성능 완료로 일반화한 것"이었습니다. 전환 전 개발 환경 시험에서 이미 일부 조회가 30초 가까이 걸렸는데 그 신호를 가볍게 봤습니다.

다시 설계

  • 정본은 하나: 기존 보정 표 4종을 유일한 정본으로 두고, "보정 쓰기 + 영향받은 달만 재전처리 + 공개 표시"를 한 트랜잭션으로 묶는 경량 구조. 새 표 5개, 함수·트리거 0, 고객 조회 SQL·인덱스·캐시 키는 그대로.
  • 금액 항등식 가드: "원천 = 정상 + 반려" 금액 항등식을 33개월 전 기간 실측(차이 0)해, 낮 재처리가 이 식을 깨면 자동으로 되돌리게 했습니다.
  • 8단계 전환: 4개 저장소에 걸친 변경을 단계마다 통과 조건·되돌리기·보관본을 둔 8단계로 나눴고, 실제 DB 를 띄운 시험으로 마이그레이션 순서와 옛 이미지 기동까지 확인해 되돌리기를 "이미지 태그 교체"로 단순화했습니다.
  • 역할 분리: 코드·PR·읽기 확인은 AI 에이전트가, 병합·운영 SQL·되돌릴 수 없는 단계 실행·결정은 제가 했습니다.

운영에 연 뒤

현업에 연 첫날 들어온 불편·누락 18항목을 당일 판정해 17항목을 그날 저녁 배포했습니다. 수집이 실패한 날 매출을 그날 다시 받는 기능은 설계 착수 4일 만에 켰습니다. 서비스가 멈춰도 알림이 없던 공백은 경보 규칙 14종(가상 시계 시험 41개)으로 메웠고, 보정할 때마다 울리던 "측정 실패" 오경보는 지표가 첫 요청 때에야 생긴다는 원인을 찾아 없앴습니다.
