개요배경·목표·내 역할

약국 업무 데이터와 확정된 계산 결과를 약사가 이해하기 쉽게 설명하고, 필요한 조회·검색·주문 초안 작성을 정확히 연결하는 서비스입니다. 제품 목표·Kick-off 아키텍처·업무 시나리오·화면 시안은 기획팀이 만들었습니다. 저는 그 위에서 회사의 기존 운영 기반에 맞춘 기술 구성(개발 추진안, 기획팀장 보고)과 두 LLM 을 비교하는 AI PoC 개발 가이드를 작성했습니다. 이번 PoC 의 산출물은 '선택 근거가 있는 실행 가능한 최소 AI 시스템'입니다. 아직 모델 비교를 실행하기 전이라 성능·정확도 숫자는 없습니다.

  • 배경: AWS 관리형 서비스 중심의 기획 구성과, 프론트엔드 외 개발 1인·기존 제품 운영 병행이라는 조건 사이의 간극
  • 목표: 모델 2개·대표 업무 3개(일일 보고 설명·재고 기반 주문 초안·고시·매뉴얼 문서 질의)·공통 도구·평가 실행기부터 구축
  • 내 역할: 기술 구성·개발 추진안 작성, AI PoC 개발 가이드 v1.0 작성, 프론트엔드 외 개발 1인 담당
  • 협업: 업무 시나리오는 기획, 업무 정답·계산 규칙·답변 유용성 기준은 기획과 현업 약사, 화면은 프론트엔드
  • AI 활용: 업무 규칙·리뷰·실행 판단은 개발자, 어댑터·도구 계약·테스트 데이터·평가 실행기 구현은 Codex 와 함께 하는 분담으로 설계. 두 문서 작성에도 Codex 활용

전체 구성기존 운영 기반 위의 에이전트

기획의 역할 구분(정기 보고·Chat·승인 실행 경로 분리, 계산 도구 공통화, 데이터 기준 시각 표시, 승인 전후 재조회와 결과 대사)은 그대로 두고, 구현은 회사가 이미 운영 중인 쿠버네티스 기반에 얹는 구성입니다. 모델은 AWS Bedrock 관리형 호출로 쓰고, 업무 규칙·도구·검색·검증은 제품 코드가 맡습니다. 모델은 도구를 '요청'만 하고, 실행 여부·약국 범위·계산은 서버 정책과 계산 모듈이 정합니다.

제품 출시 단계 제안외부 실행은 완료 조건을 통과한 만큼만

개발 추진안에서 제안한 출시 순서입니다. 확정 일정표가 아니라 순서 제안이며, 각 단계의 완료 조건을 통과해야 다음 단계의 외부 실행 범위를 엽니다. 외부 자료 확보 대기와 기존 제품 운영 시간은 개발 공수와 따로 반영합니다. AI 쪽 '승인 업무 연결'은 2단계의 주문 안전장치가 먼저 갖춰져야 붙입니다.

  1. 0단계
    연동과 정책 검증협력 약국 솔루션의 API·데이터 구조·테스트 계정·비식별 샘플 확보, 중앙 API 와 약국 PC 설치형 커넥터 중 연동 방식 판정, 품목·포장 단위 매핑, 약국·사용자 식별, 데이터 이용 조건, 운영 용량·비용 산정. 완료 조건: 기능별 제공·미제공 판정과 제공 일정 기록, 자료가 부족한 기능은 개발 가능으로 간주하지 않음
  2. 1단계
    조회 중심 보고와 재고 실사동기화·검증·계산 결과 저장, 부족 품목 주문안, 일일 리포트, 운영 상태 화면. 외부 시스템 쓰기는 하지 않음. 완료 조건: 고정 입력·기대 결과로 만든 Golden Set 통과, 원천 건수·합계·단위와 계산 결과 대조, 지연·누락·매핑 실패를 '0건' 결과와 구분하고 기준 시각 표시
  3. 2단계
    약사 수동 승인 주문과 결과 확인품목·수량 수정, 약사 재인증, 승인 계획 버전 검사, 실행 전 재조회, 주문 전송, 결과 대사, 부분 실패, 미확정 건 운영자 처리. 완료 조건: 동시 승인·응답 유실·Worker 재기동·단가 변경·부분 성공 시험, 미확정 상태에서 재전송되지 않음 확인, 제한된 품목부터 개방
  4. 3단계
    제한된 Chat 과 근거 검색지원 질문 목록, 정해진 지표 조회, 업무별 도구 선택, 공개 고시·매뉴얼 검색, 출처·기준 시각 표시, 지원 밖 질문 거절과 되묻기. 주문 요청은 2단계 승인 흐름으로 연결. 완료 조건: 같은 기준 시각에서 보고와 Chat 수치 일치, 약국 간 접근 차단·권한·개인정보 제한·수치 대조 통과
  5. 후속
    처방 화면 대체·조건부 자동 실행·업무 확대서로 다른 의존성과 완료 조건을 가지므로 한 묶음으로 출시하지 않음. 조건부 자동 실행은 무수정 승인 비율만으로 허용하지 않고, 원천 최신성·금액과 수량 한도·약사 동의·즉시 중단 조건을 갖춘 업무만 대상

핵심 흐름에이전트 한 번의 실행

재고 기반 주문 초안을 예로 든 실행 루프입니다. 실행 문맥(약국·역할·기준 시각)은 신뢰된 실행기가 인증 정보로 만들고, 모델이 요청한 도구는 허용 목록 → JSON 스키마 → 품목·단위·기간 의미 검증을 차례로 통과해야 실행됩니다. 반복·시간·토큰 상한을 넘으면 '미완료'로 끝내고, 확인되지 않은 실행을 완료라고 표시하지 않습니다.

주문 초안의 상태 전이승인과 실행을 분리 초안

AI 는 주문안을 만들거나 수정 요청을 전달할 수 있지만, 승인 기록·약사 재인증·계획 버전·실행 전 재조회·외부 전송·결과 대사는 업무 백엔드가 맡도록 역할을 나눴습니다. 대화 속 '승인했다'는 문장은 서버의 승인 이벤트가 아닙니다. PoC 에서는 '승인 대기 초안'까지만 만들고 외부 주문 API 에 연결하지 않습니다. 아래 상태도는 개발 추진안 2단계의 항목을 이어 그린 초안입니다.

  • 계획이 바뀌면 기존 승인 무효, 오래된 승인 재사용 금지
  • 결과가 불명확한 주문은 '미확정'으로 두고 재전송을 잠근 뒤 결과 조회·운영자 판정으로 확정
  • 동시 승인·응답 유실·Worker 재기동·단가 변경·부분 성공을 완료 조건 시험 항목으로 지정

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

RAG 흐름수치는 도구에서, 근거는 검색에서

RAG 는 모델을 학습시키는 것이 아니라 필요한 문서 조각을 그 요청의 근거로 넘기는 것입니다. 주문 수량·매출 같은 정답 수치는 조회·계산 도구에서, 고시·매뉴얼 같은 업무 근거는 문서 검색에서 얻도록 나눴습니다. 두 모델은 같은 검색기와 같은 문서 조각을 받습니다.

  • 검색 성능(Recall@k·MRR)을 먼저 따로 재고, 그다음 검색 결과로 답하는 성능을 측정 — 검색 오류와 생성 오류 분리
  • 첫 비교에서 임베딩·분할·색인 고정, 임베딩을 바꾸면 재색인하고 별도 실험으로 기록
  • 시행 전 고시·폐기 문서·다른 약국 문서는 검색 전에 서버가 필터
  • 검색 문서 속 지시는 자료로만 취급(실행하지 않음), 출처 링크는 서버가 문서 ID 로 매핑
  • 인용 문서 ID 가 존재하는지와 그 문서가 실제 주장을 지지하는지는 별개 검사
  • 질의 재작성은 초기 고정 검색 평가에서 끄고, 켜면 별도 실험으로 분리

개념 데이터 모델평가를 재현할 수 있게 초안

실제 저장소 스키마가 아니라, 설계 문서의 실행 문맥·실행 기록·문서 메타데이터·도구 계약 항목을 개념 단위로 묶은 그림입니다. 평가 결과를 재현하려면 '어떤 사례를, 어떤 모델·프롬프트·데이터 스냅샷·검색 색인으로, 몇 번째 반복에서' 실행했는지가 함께 남아야 합니다.

  • 실행 기록 항목: 모델 ID·엔드포인트·리전·프롬프트 해시·스냅샷 해시·색인 해시·임베딩 ID·도구 호출 요약·최종 상태·토큰·지연·추정 비용·기준별 점수·실패 분류
  • API 가 주지 않는 토큰 수는 0 이 아니라 '미제공'으로 기록
  • 인증 헤더·개인정보·비밀 값은 기록하지 않음
  • 최종 평가셋을 보고 수정한 결과는 '개발 결과'로 표시하고, 다음 판정은 새 보류셋으로

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

구현 순서 P0~P7각 단계가 다음 비교 조건을 고정

AI PoC 개발 가이드의 구현 순서입니다. 문제를 발견하면 모델을 키우기 전에 해당 단계의 원인을 고칩니다. P0~P2 의 최소 비교를 먼저 끝낸 뒤 도구·문서 품질을 보고 이후 일정을 추정하고, 외부 승인·업무 정답 확보·접근 권한 대기는 개발 공수와 분리해 관리합니다.

  1. P0
    범위·평가 초안·호출 경로 확정세 업무의 기대·금지 행동 정의, 합성 테스트 데이터와 호출 확인용 10개 사례, 예산·역할·모델 접근 확인. 민감한 실제 데이터 없이 호출을 시작할 수 있는 상태
  2. P1
    최소 호출과 공통 모델 어댑터텍스트 1회·도구 왕복 1회·오류 처리부터. 메시지·도구 요청·usage·stop reason 을 공통 타입으로 변환, 같은 실행 명령에서 설정만 바꿔 두 후보 호출
  3. P2
    고정 근거 LLM 평가계산 JSON·문서 발췌를 직접 넣고 숫자 보존·인용·되묻기 검사. 검색 성공 여부는 이 단계의 변수에서 제외
  4. P3
    업무 도구와 서버 정책조회·계산·검색 계약, 품목·기간·단위 검증, 약국 권한 검사. 도구는 모델 없이 독립 검증하고, 모델이 약국 범위나 승인 상태를 조작해도 정책을 넘지 못함을 확인
  5. P4
    단일 에이전트 실행 루프입력 → 모델 → 도구 요청 검증 → 도구 실행 → 결과 전달 → 최종 검증. 상한 초과 시 미완료 종료, 두 모델의 도구 경로·실패 원인·완료 상태를 같은 형식으로 기록
  6. P5
    실제 검색과 RAG 연결정제·분할·메타데이터·임베딩·검색, 두 모델이 공통 검색기 사용. 검색 성능을 먼저 재고 그다음 답변 성능
  7. P6
    고정 평가셋 반복 비교조정용 사례로 설정 확정 후 최종셋 실행. 모델·질문 순서를 섞어 반복, 자동 채점과 약사 블라인드 검토, 코드·설정·데이터 해시가 있는 재현 가능한 결과
  8. P7
    EKS 검증과 모델 선택여유 용량 확인 후 제한된 PoC Job 으로 배포, 네트워크·지연·오류·메모리 확인. 종료·롤백 절차와 모델 선택 근거·미해결 실패 기록

평가 설계숫자는 모두 계획값

고유 사례 100개를 5개 업무 유형에 20개씩 나누고, 유형마다 6개(총 30)는 조정용, 14개(총 70)는 최종 평가용으로 씁니다. 같은 템플릿에서 숫자만 바꾼 사례가 양쪽에 섞이지 않도록 업무·문서 계열 단위로 나눴습니다. 최종 실행은 70사례 × 2모델 × 3회 = 420 episode 이며, 반복 3회는 같은 사례의 변동을 보는 것이지 독립 사례가 늘어나는 것이 아닙니다.

  • 지표 12개: 업무 성공률, 수치·단위 보존, 도구 정확성, 출력 계약, 검색 품질(Recall@k·MRR), 근거 일치, 되묻기·보류, 권한·승인, 장애 대응, 한국어 유용성, 속도(중앙값·p95), 성공 업무당 비용
  • 타임아웃·파싱 실패·재시도 초과를 성공률 분모에서 빼지 않음
  • 평균 점수 하나로 중대 오류를 상쇄하지 않고, 유형별 성공률과 실패 원인을 따로 공개
  • 성공 업무당 비용 = 실패·재시도를 포함한 전체 변동비 ÷ 성공 episode 수
  • 통과 게이트(제안·미합의): 타 약국 노출·무승인 외부 실행 0건, 수치·단위 보존 100%, 지원 범위 성공률 95% 이상, 근거 없는 주요 판단 0건

기획 시안을 구현 명세로백엔드 계약 보완안

화면 시안을 구현 명세로 옮길 때 백엔드가 책임질 계약을 화면별 기능 정의서에 공통으로 붙이는 보완안을 개발 추진안에 담았습니다(합의 전 제안).

  • 공통 항목: 원천 데이터와 기준 시각, 요청·응답·오류 코드, 입력 검증, 사용자·약국 권한, 계산 버전, 상태 전이, 승인과 재승인, 외부 처리·대사, 실패 시 다음 행동
  • 원칙: 클릭이나 전송 응답을 처리 완료와 같게 보지 않고, 화면 탐색 탭과 실행 상태를 서로 다른 축으로 관리

기술 스택과 선택 이유

새 기술을 늘리기보다, 이미 운영 중인 기반을 재사용하고 AI 쪽 결정만 근거로 고르는 방향입니다.

  • AWS Bedrock 관리형 호출: 모델 학습·GPU 운영 없이 업무 적합성부터 검증. 자체 호스팅(vLLM 등)은 가중치·라이선스·GPU 용량·장애 대응을 추가로 떠안는 선택이라 별도 결정으로 미룸
  • Qwen3 32B·Claude Sonnet 5: AWS 모델 카드 기준 서울 리전 호출 경로가 있는 후보 조합. 추진안에서는 Qwen 계열 여러 크기를 후보로 올렸고, PoC 첫 비교는 Qwen3 32B 로 좁힘. 계정 권한·쿼터·실제 응답은 실행 시 확인하고, 결과는 '모델 + API + 엔드포인트 + 설정' 조합의 적합성으로 해석
  • Kotlin·Spring Boot·Coroutines: 기존 제품과 같은 언어·패턴으로 도구·실행기 구현. 단, 기존 제품의 공통 모듈·인증에 직접 결합하지 않음
  • Python: 반복 실행·채점·집계 스크립트. LLM 호출·업무 정책의 정본은 하나로 유지
  • PostgreSQL·Flyway: 계산 버전·기준 시각·승인자·주문 상태 관리, 금액·수량은 Decimal 계열로 계산
  • Testcontainers·WireMock: 외부 HTTP 어댑터의 429·5xx·timeout 실패 재현
  • EKS·Jenkins·Argo CD·Prometheus·Grafana·Loki: 기존 배포·관측 재사용, PoC 는 제한된 Job 으로 검증 후 종료·롤백. 대화형 실행 루프는 기존 배치 오케스트레이터(Airflow)와 분리
  • Codex·Claude Code: 어댑터·도구 계약·테스트 데이터·평가 실행기를 에이전트와 함께 구현, 판단과 리뷰는 사람

계산·승인·약국 범위는 왜 모델이 아니라 서버가 정하나

1문제 상황

약국 AI Agent 는 재고를 조회하고 주문 수량을 제안하고 초안을 만듭니다. 여러 약국이 같은 서비스를 쓰므로 다른 약국 데이터가 섞이면 안 되고, 수량·금액이 하나라도 바뀌면 곧 잘못된 주문이 됩니다.

2원인 분석

LLM 출력은 확률적이라 근거가 있어도 수치를 바꿔 말하거나, 도구 인자에 다른 약국 ID 를 넣거나, 실행하지 않은 일을 '발주 완료'라고 안내할 수 있습니다. 대화 속 '승인했다'는 문장은 서버의 승인 이벤트가 아니고, 검색된 문서 속 지시문을 따르면 권한이 바뀔 수도 있습니다. 이 경계를 모델에게 맡기면 모델 품질을 아무리 비교해도 '0건'을 보장할 방법이 없습니다.

3해결 과정
  1. 약국·역할·기준 시각을 담은 실행 문맥은 신뢰된 실행기가 인증 정보로 생성, 모델이 준 인자에서는 약국 범위를 받지 않음
  2. 도구 요청 검증 순서 고정: 도구 이름 허용 목록 → JSON 스키마 → 품목·기간·단위 의미 검증. 모델이 만든 SQL·URL 은 실행하지 않음
  3. 수량·금액은 결정론적 계산 도구(규칙 버전 고정)가 산출, LLM 이 말한 계산값은 정본으로 저장하지 않고 최종 답변 수치를 도구 결과와 구조적으로 대조
  4. 주문 초안 도구는 '승인 대기' 상태까지만, PoC 에서는 외부 주문 API 미연결. 실제 연동 단계는 약사 재인증·승인 계획 버전·실행 전 재조회·결과 대사를 따로 검증하도록 단계 분리
  5. 읽기는 제한된 재시도, 쓰기는 요청 ID·멱등성·상태 확인 없이 재시도 금지. 데이터 없음·권한 없음·도구 장애를 구분하고 실패를 0 으로 바꾸지 않음
  6. 검색 문서는 신뢰하지 않은 입력으로 취급, 권한·시행일 필터는 검색 전에 서버가 강제
  7. 평가셋에 '예외·권한' 유형 20사례(타 약국 조회·미승인·도구 장애·문서 속 프롬프트 공격)를 별도 배치
4결과

설계 단계의 결과입니다. 통과 게이트를 '타 약국 데이터 노출·무승인 외부 실행 0건', '수치·단위 보존 100%', '근거 없는 주요 판단 0건'으로 제안했고, 실행 경계 게이트를 넘지 못하면 모델 점수와 무관하게 다음 단계를 멈추도록 정했습니다. 기준은 기획·약사와 아직 합의 전이며 측정 결과는 없습니다.

배운 점

LLM 서비스의 신뢰는 모델 성능보다 실행 경계에서 나온다는 기준을 세웠습니다. 또 외부 쓰기 도구가 없는 PoC 의 '외부 실행 0건'이 실제 주문 안전성을 증명하지는 못한다는 점, 즉 PoC 통과가 상용 출시 승인이 아니라는 점도 문서에 명시했습니다.

CASE 02 · 설계 결정

모델 비교를 같은 프로그램에서 모델만 바꿔 하는 이유

1문제 상황

기획은 Qwen 계열을 염두에 두었고, 저는 서울 리전 호출 경로가 모델 카드에 명시된 Claude Sonnet 5 를 비교 기준 후보로 함께 두자고 제안했습니다. 그런데 AWS 서울 리전에서 두 모델은 호출 경로부터 다릅니다. Qwen3 32B 는 Bedrock mantle(Chat Completions), Claude Sonnet 5 는 Bedrock runtime(Converse)이고, 구조화 출력·Guardrails 같은 기능 지원도 경로마다 다릅니다.

2원인 분석

모델마다 프로그램을 따로 만들면 결과 차이가 모델 때문인지 프롬프트·도구·코드·서빙 경로 때문인지 가를 수 없습니다. 일반 벤치마크 순위는 약국 업무에 필요한 수치 보존·도구 사용·권한 준수를 재지 못합니다.

3해결 과정
  1. 공통 ModelClient 인터페이스 + 어댑터 2개: 메시지·도구 요청(호출 ID)·usage·stop reason 을 공통 타입으로 변환, 업무 코드에는 SDK 타입을 노출하지 않음
  2. API 가 주지 않는 토큰 수는 0 이 아니라 '미제공'으로 기록, 미지원 기능은 숨기지 않고 표시
  3. 업무 지침·도구·데이터 스냅샷·검색기·출력 계약은 공통, 모델별 설정 차이(thinking·temperature·출력 길이)는 기록
  4. 모델 간 자동 fallback·타 리전 우회 금지, 계정 호출 결과가 리전표와 다르면 원인 확인 후 후보 변경을 기록
  5. 세 관점 분리 측정: 고정 근거를 직접 준 LLM 답변 / 같은 도구·스냅샷으로 끝까지 실행하는 에이전트 업무 / 공통 검색기의 검색 품질
  6. 조정용 30사례로 설정을 고친 뒤 동결, 최종 70사례를 모델별로 짝지어 3회 반복(420 episode), 실행 순서·시각을 섞고 사례마다 상태 초기화
  7. 자동 채점 뒤 모델명을 가린 약사 검토, 실패는 DATA·RETRIEVAL·TOOL·MODEL·POLICY·ADAPTER·RUNTIME 7가지로 분류
4결과

평가 프로토콜 설계까지 마쳤고 실행은 아직입니다. 결과는 '모델 + API + 엔드포인트 + 설정' 조합의 업무 적합성으로 해석하고, 서빙 경로가 다른 두 모델의 지연 차이를 모델 자체의 성능 차이로 단정하지 않도록 했습니다. 비교 결과표는 현재 전부 '미측정'입니다.

배운 점

비교 실험은 한 번에 하나의 변수만 바꿔야 결론을 낼 수 있습니다. 둘 다 기준에 못 미치면 모델 교체보다 데이터·검색·도구·정책 중 어디가 원인인지부터 가르도록 판정 규칙을 미리 정해 두었습니다.

CASE 03 · 설계 결정

기획의 관리형 구성을 왜 기존 운영 기반에 대응시켰나

1문제 상황

Kick-off 아키텍처는 API Gateway·Cognito·ECS Fargate·Step Functions·Bedrock·SageMaker SLM·AgentCore(Memory·Gateway)·Knowledge Bases·Aurora·SNS 등 AWS 관리형 서비스 중심이었습니다. 개발은 프론트엔드 외 1인이 맡고, 기존 제품 운영도 계속해야 하는 조건입니다.

2원인 분석

새 관리형 서비스를 한꺼번에 들이면 익히고 운영할 대상과 비용이 함께 늘어, 1인 개발·기존 제품 운영 병행 조건에서 감당하기 어렵다고 판단했습니다. 일부 기능은 서울 리전 처리 조건과 맞는지도 먼저 확인해야 했습니다. 완전 관리형 Knowledge Base 의 지원 리전 목록에 서울이 없다는 점, mantle 경로의 Converse·통합 Guardrails 미지원, 메모리·평가 기능의 교차 리전 처리 경로가 그 예입니다.

3해결 과정
  1. 역할은 유지하고 구현만 대응: 진입은 기존 Envoy, 업무 API·Worker 는 EKS 의 Kotlin, 정기 실행은 CronJob·DB 상태, 배포·관측은 기존 Jenkins·Argo CD·Prometheus·Grafana·Loki
  2. 계산은 공통 업무 모듈 하나에 두고 보고와 Chat 이 같은 결과를 조회
  3. SLM 학습·장기 메모리·MCP 게이트웨이·다중 에이전트는 필요성과 비용 근거가 생긴 뒤로 미룸
  4. 대화형 실행 루프는 기존 배치 오케스트레이터(Airflow)에 연결하지 않음 — 배치 직렬화 제약과 분리
  5. 시범 출시 범위를 '조회·수동 승인 주문 우선'으로 제안, 처방 화면 대체·조건부 자동 실행은 각각 별도 완료 조건으로 분리
  6. 착수 전 선행 합의 3가지 제시: 시범 범위, 협력 약국 솔루션의 제공 자료·일정, 운영 용량·DB 가용성·예산과 장애 대응 책임
4결과

12개 영역의 대응 표와 출시 단계·화면 시안 보완안을 담은 개발 추진안을 작성해 기획팀장에게 보고했습니다(제안 단계). 범위 조정은 기획과 합의해야 확정되며, 서비스 선정은 비용과 검증 결과로 결정하기로 했습니다.

배운 점

'역할 유지'와 '특정 관리형 서비스 도입'을 별도 결정으로 나누니, 기획 의도를 지키면서도 1인 개발로 실행 가능한 순서를 만들 수 있었습니다.

CASE 04 · 설계 결정

업무별 Agent 를 서비스마다 따로 만들지 않은 이유

1문제 상황

Kick-off 구성은 Supervisor 가 업무별 Agent(1차 범위는 주문·재고손실·리포트, 이후 업무도 Agent 단위로 구상)에 일을 나누는 형태입니다. 이 구상은 기획의 것이고, 구현 방식을 정하는 것이 제 몫이었습니다.

2원인 분석

Agent 를 '별도 모델·별도 서버'로 읽으면 배포·운영·평가 대상이 업무 수만큼 늘어납니다. 역할을 나눠야 품질이 좋아진다는 근거도 아직 없습니다.

3해결 과정
  1. 에이전트 = 업무 지침 + 허용 도구 + 문맥·상태 + 실행 루프로 정의. 주문·재고·리포트는 같은 LLM 을 쓰는 역할 설정
  2. 단일 AgentRunner: 입력 → 모델 → 도구 요청 검증 → 도구 실행 → 결과 전달 → 최종 검증
  3. 반복·시간·토큰 상한(예시 시작값 모델 5회·도구 8회, 업무별 조정), 넘으면 '미완료'로 종료하고 확인되지 않은 실행을 완료로 표시하지 않음
  4. Supervisor 는 단순 라우팅으로 시작, 의도 분류 SLM 은 LLM 과 규칙으로 먼저 대신함
  5. 관리형 실행 루프(AgentCore)는 개발량을 줄인다면 같은 도구·평가셋으로 검증하는 비교안으로 남김
  6. 역할별 다중 에이전트는 단일 에이전트의 반복 오류가 줄고 비용·지연·운영 부담을 감당할 수 있을 때 추가
4결과

AI 개발 순서를 '단일 에이전트 → 승인 업무 연결 → 역할 분리 → 최적화'로 정리했습니다(설계). 같은 업무를 두 모델로 실행해도 도구 경로·실패 원인·완료 상태가 같은 형식으로 남도록 실행 기록을 설계했습니다.
