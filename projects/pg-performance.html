분석 조회 30초 타임아웃 해결

반복 벤치에서는 1초 남짓인데 실사용에서는 30초 타임아웃이 나던 매출 분석 화면을, 측정으로 원인을 좁혀 앱 코드 변경 없이 고쳤습니다.

문제

월 파티션으로 나눈 수천만 건 규모의 원본 테이블을 직접 조회하는 분석 API 가 실사용에서만 크게 느렸습니다. 같은 쿼리를 반복하면 웜 캐시라 1.4초 정도였고, 검토 중이던 대안은 컬럼형 DB(ClickHouse) 도입이었습니다.

측정으로 좁히기

  • track_io_timing 과 EXPLAIN (BUFFERS) 로 실행 시간의 84%가 IO 대기임을 분리했습니다. 전날 "DB CPU 포화"로 본 제 판단은 이 측정으로 바로 정정했습니다.
  • 콜드와 웜을 따로 재자, PK 선두 컬럼이 조회 조건과 어긋나 조회 한 번이 버퍼풀을 통째로 밀어내고, 그 바람에 관계없는 화면까지 늘 콜드가 되는 구조가 드러났습니다.

조치

  • 커버링 인덱스 2종을 운영 DB 에 잠금 없이(CONCURRENTLY) 먼저 적용하고, Index Only Scan 을 유지하도록 테이블 단위 autovacuum·IO 설정·파드 자원을 맞췄습니다.
  • 요청당 원본을 여러 번 다시 읽던 추이 쿼리는 GROUPING SETS 로 한 번에 묶고, 신·구 결과를 EXCEPT 로 대조해 차이 0 을 확인했습니다.
  • 받은 성능 개선 로드맵(복제본 추가·권한 분리 등)은 실측으로 검증해 과잉 처방 5건을 기각했고, 그 과정에서 특정 제품을 고를 때만 평균 14초가 걸리는 숨은 쿼리를 찾아 월 파티션 무락 인덱스(파티션별 CONCURRENTLY → ON ONLY → ATTACH)로 고쳤습니다.

결과

지표전후
콜드 조회(월별 기관 수, 12개월)11.9초1.5초
콜드 조회(제품 수)11.7초0.18초
콜드/웜 격차9.7배1.6배
최대 고객사 12개월 KPI4.5초0.94초
숨은 쿼리(완전 웜 실행 계획)약 4초3.4ms

컬럼형 DB 도입은 추정 36~57 사람-일이었고, PostgreSQL 튜닝은 추정 약 1.5 사람-일이었습니다. 이후 개발 환경 부하 시험 하네스(20계정 동시, 5xx·타임아웃 0 하드 게이트)로 목록 API 의 30초 컷도 찾아 고쳤습니다.

배운 것

반복 벤치는 웜만 잽니다. 실사용 지연은 콜드에서 나오고, 콜드는 다른 쿼리가 캐시를 어떻게 쓰는지에 달려 있습니다. "느리다"를 "무엇을 기다리는가"로 바꿔 물으면 처방이 달라집니다.
