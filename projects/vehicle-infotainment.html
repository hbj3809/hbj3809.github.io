프로젝트 개요
무엇을, 왜 만들었나

국내 완성차 브랜드의 차량용 디스플레이 오디오 2세대 플랫폼에 들어가는 인포테인먼트 애플리케이션을 C++·Qt/QML 로 개발했습니다. 기존에 만들어진 개발자 모드를 고도화했고, 이 기능은 당시 신차부터 이후 출시된 전 차종에 탑재돼 디자인 리뉴얼 뒤에도 현행 플랫폼까지 유지되고 있습니다. 인도향 기도 방향(키블라) 안내 기능은 직접 개발했습니다. 구면 삼각법 알고리즘을 구현하고 Kalman Filter 로 위치 오차를 보정해, 방위각 오차를 360° 대비 1% 미만(약 3.6° 이내)으로 맞췄습니다. 북미향 전 차종의 GPS(NMEA) 데이터 수집·추적 서비스도 직접 개발하고, 미국 현지에서 3개월간 품질 확인·양산 대응을 맡았습니다.

프로젝트 개요

인포뱅크 iMotors 사업부 Media팀 연구원으로, 국내 완성차 브랜드의 차량용 디스플레이 오디오 2세대 플랫폼에 들어가는 애플리케이션을 개발했습니다. 차종·시장마다 필요한 기능을 헤드유닛 안에 넣고, 양산 전에 현지에서 품질 확인까지 마치는 일이었습니다.

  • 기간: 2018.11 ~ 2019.06
  • 소속·직급: iMotors 사업부 Media팀 · 연구원
  • 담당: 기존 개발자 모드 고도화, 기도 방향(키블라) 안내 기능 직접 개발(방위각 알고리즘 포함), 북미향 GPS(NMEA) 데이터 수집·추적 서비스 직접 개발, Connectivity 기능 개발
  • 현지 대응: 미국 현지 3개월 품질 확인·양산 대응
  • 성격: 차량 헤드유닛에서 동작하는 임베디드 애플리케이션 — GPS 위치 데이터를 앱에서 직접 보정·계산

담당 기능

담당한 기능은 대상 시장과 목적이 서로 다릅니다.

개발자 모드

기존에 만들어진 개발자 모드를 C++·Qt/QML(Signal-slot) 로 고도화. 당시 신차부터 이후 출시된 전 차종에 탑재, 디자인 리뉴얼 뒤에도 같은 기능이 현행 플랫폼까지 유지.

기도 방향(키블라) 안내

인도향 전 차종. 직접 개발. C++ Vector 기반 구면 삼각법 알고리즘을 구현하고 Kalman Filter 로 위치 오차를 보정, 방위각 오차 360° 대비 1% 미만(약 3.6° 이내).

GPS(NMEA) 수집·추적

북미향 전 차종. 내비게이션 영역에서 차량 위치 데이터를 수집·추적하는 서비스 직접 개발. 현지에서는 실종·유기 아동을 찾는 데에도 쓰였다고 전해 들음.

북미 현지 검증

미국 현지 2개 지역에서 3개월. 양산 전 품질 확인과 양산 대응. 현지 설정·언어·지역 차이와 실차 환경 호환·성능 이슈를 현지에서 확인해 대응.

아키텍처헤드유닛 앱 구성 초안

헤드유닛 앱을 화면(QML)·기능(C++/Qt)·플랫폼 세 계층으로 나눠 그린 개념도입니다. 화면과 기능은 Signal-slot 으로 이어지고, GPS 수신기에서 들어온 NMEA 문장이 위치 보정·방위각 계산·수집 기록으로 흘러갑니다.

  • 화면 계층: 개발자 모드·기도 방향 안내 화면(QML)
  • 기능 계층: 개발자 모드 기능, NMEA 파서, Kalman Filter 위치 보정, 구면 삼각법 방위각 계산(C++)
  • 플랫폼 계층: Linux Embedded 실행 환경, Android NDK 네이티브 모듈
  • 외부: GPS 수신기(입력), 북미향 위치 수집·추적 서비스(출력)

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

핵심 흐름 ① 기도 방향 방위각 계산

직접 개발한 기도 방향 안내 기능에서, 위치 한 건이 들어와 화면의 방향 표시가 바뀌기까지의 흐름입니다.

  • GPS 위치는 Kalman Filter 로 보정한 뒤 방위각 계산에 사용
  • 지구를 구로 보고 현재 위치에서 성지(메카) 방향의 방위각 계산 — 먼 거리 방향 계산에 일반적으로 쓰는 구면 삼각법
  • 계산 결과는 Signal 로 QML 안내 화면에 전달
  • 방위각 오차는 360° 대비 각도 오차로 검증 — 1% 미만(약 3.6° 이내)

핵심 흐름 ② GPS(NMEA) 수집·추적

직접 개발한 북미향 차종의 위치 수집·추적 흐름입니다. GPS 수신기의 NMEA 문장을 받아 위치 기록으로 남기고 위치 추적 서비스로 연동합니다. 검사·추출 단계는 NMEA 표준의 일반적인 처리 순서로 그렸습니다.

  • GPS 수신기에서 표준 NMEA 문장으로 위치 데이터 수신
  • 일반적인 NMEA 처리 순서: 체크섬·형식 검사 → 시각·위치·속도 필드 추출 → 위치 기록 저장
  • 기록은 위치 추적 서비스로 연동

현지 검증 이슈 처리 흐름

미국 현지 2개 지역에서 3개월간 품질을 확인하며 실제로 만난 이슈는 크게 두 유형이었습니다. 현지 설정·언어·지역 차이에서 생기는 문제와, 실차 환경에서만 드러나는 호환·성능 문제입니다. 두 유형 모두 현지 조건에서 재현·확인한 뒤 대응했습니다.

CASE 01 · 알고리즘구현

흔들리는 GPS 위치에서 기도 방향 방위각 계산하기

1문제 상황

인도향 전 차종에 들어가는 기도 방향(키블라) 안내 기능을 직접 개발했습니다. 차량의 현재 위치에서 성지(메카) 방향의 방위각을 계산해 화면에 보여 줘야 했고, 차량은 계속 움직이며 GPS 위치에는 측정 잡음이 섞입니다.

2원인 분석

방위각은 입력 위치를 그대로 따라가므로, 일반적으로 GPS 원값을 바로 쓰면 위치가 튈 때 방향 표시도 함께 흔들릴 수 있습니다. 또 멀리 떨어진 목적지는 평면 지도처럼 계산하면 방향이 어긋나기 쉬워, 이런 계산에는 보통 구면 계산을 씁니다.

3해결 과정
  1. C++ Vector 기반 구면 삼각법 방위각 계산 직접 구현 — 지구를 구로 보고 두 지점 사이 방향을 구하는, 먼 거리 방향 계산에 일반적으로 쓰는 방식
  2. Kalman Filter 로 GPS 위치 오차 보정 — 이전 추정과 새 측정을 함께 반영하는, 잡음 섞인 위치 데이터에 일반적으로 쓰는 방식
  3. 보정된 위치로 방위각을 계산하고, 결과는 Signal-slot 으로 QML 안내 화면에 전달
  4. 방위각 오차를 360° 대비 각도 오차로 검증
4결과

인도향 전 차종 기도 방향 안내 기능 직접 개발 완료, 방위각 오차 360° 대비 1% 미만(약 3.6° 이내).

배운 점

CASE 02 · 현지대응

북미 현지 3개월 품질 확인·양산 대응

1문제 상황

북미향 차종에 들어가는 애플리케이션을 양산 전에 현지에서 확인해야 했습니다. 미국 현지 2개 지역에서 3개월간 품질 확인과 양산 대응을 맡았습니다.

2원인 분석

현지 설정·언어·지역 차이와 실차 환경은 국내 시험 환경과 다르기 때문에, 이런 조건에서만 드러나는 문제는 국내 시험만으로 다 확인하기 어렵습니다.

3해결 과정
  1. 미국 현지 2개 지역에서 3개월간 품질 확인 시험 대응
  2. 현지 설정·언어·지역 차이: 지역 설정·언어 표시 차이로 생기는 문제를 현지 환경에서 재현해 고침
  3. 실차 환경 호환·성능: 실차에서만 드러나는 호환·성능 문제를 현장에서 확인해 대응
  4. 품질 확인을 마친 뒤 양산 대응
4결과

북미향 전 차종 GPS(NMEA) 수집·추적 서비스 직접 개발, 미국 현지 3개월 품질 확인·양산 대응. 현지 설정·언어·지역 차이와 실차 환경 호환·성능, 두 유형의 이슈를 현지에서 확인해 대응했습니다.

진행 순서

  1. 출장 전

  2. 현지 체류 중
    품질 확인 시험 대응미국 현지 2개 지역에서 품질 확인
  3. 현지 체류 중
    현지 이슈 대응현지 설정·언어·지역 차이, 실차 환경 호환·성능 문제를 현장에서 재현·확인해 대응
  4. 양산 단계
    양산 대응북미향 전 차종 적용
배운 점

원인은 문제가 나는 자리에서 재현해야 좁혀진다 — 국내 시험 환경과 다른 현지 설정·실차 조건이 그랬습니다. 이후 운영 중인 시스템에서 장애를 격리하고 재처리 경로를 먼저 만드는 방식으로 이어졌습니다.

CASE 03 · 임베디드개발

디자인이 바뀌어도 남는 개발자 모드 초안

1문제 상황

차량 인포테인먼트에 기존에 만들어진 개발자 모드를 고도화했습니다. 당시 신차부터 이후 전 차종에 들어가는 기능이라, 플랫폼 세대 교체와 디자인 리뉴얼을 계속 거칠 수밖에 없었습니다.

2원인 분석

화면 코드와 기능 코드가 섞여 있으면 디자인을 바꿀 때마다 기능까지 다시 만들고 다시 검증해야 합니다.

3해결 과정
  1. 기존 개발자 모드의 기능 고도화
  2. 고도화하는 기능도 화면(QML)과 기능(C++) 경계를 지켜 반영 — 두 계층은 Qt Signal-slot 으로 연결
  3. 화면 교체가 기능 계층에 영향을 주지 않도록 경계 유지
4결과

고도화한 개발자 모드가 당시 신차부터 이후 출시된 전 차종에 탑재. 리뉴얼 뒤 디자인 변경을 빼면 현행 플랫폼까지 같은 기능이 유지되고 있습니다.

숫자로 본 변화

탑재 범위
전 차종

배운 점

화면의 수명보다 기능의 수명이 길다. 경계를 지키면 기능은 살아남는다는 기준이 백엔드에서 API 계약과 내부 구현을 나누는 습관이 됐습니다.
