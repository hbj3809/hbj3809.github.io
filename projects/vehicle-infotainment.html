인포뱅크 프로젝트

국내 완성차 브랜드 차량 인포테인먼트 애플리케이션 개발

C++⁠·Qt/QML 헤드유닛 앱 개발(개발자 모드 고도화⁠·기도 방향 안내⁠·GPS 수집)과 북미 현지 3개월 품질 검증

프로젝트 개요
무엇을, 왜 만들었나

국내 완성차 브랜드의 차량용 디스플레이 오디오 2세대 플랫폼에 들어가는 인포테인먼트 애플리케이션을 C++⁠·Qt/QML로 개발했습니다. 기존에 만들어진 개발자 모드를 고도화했고, 이 기능은 당시 신차부터 이후 출시된 전 차종에 탑재돼 디자인 리뉴얼 뒤에도 현행 플랫폼까지 유지되고 있습니다. 인도향 기도 방향(키블라) 안내 기능은 직접 개발했습니다. 구면 삼각법 알고리즘을 구현하고 Kalman Filter로 위치 오차를 보정해, 방위각 오차를 360° 대비 1% 미만(약 3.6° 이내)으로 맞췄습니다. 북미향 전 차종의 GPS(NMEA) 데이터 수집⁠·추적 서비스도 직접 개발하고, 미국 현지에서 3개월간 품질 확인⁠·양산 대응을 맡았습니다.

개요배경⁠·내 역할

인포뱅크 iMotors 사업부 Media팀 연구원으로, 국내 완성차 브랜드의 차량용 디스플레이 오디오 2세대 플랫폼에 들어가는 애플리케이션을 개발했습니다. 차종⁠·시장마다 필요한 기능을 헤드유닛 안에 넣고, 양산 전에 현지에서 품질 확인까지 마치는 일이었습니다.

  • 담당기존 개발자 모드 고도화, 기도 방향(키블라) 안내 기능 직접 개발(방위각 알고리즘 포함), 북미향 GPS(NMEA) 데이터 수집⁠·추적 서비스 직접 개발, Connectivity(차량 간 신호 송수신) 기능 개발
  • 현지 대응미국 현지 3개월 품질 확인⁠·양산 대응
  • 성격차량 헤드유닛에서 동작하는 임베디드 애플리케이션으로, GPS 위치 데이터를 앱에서 직접 보정⁠·계산

담당 기능

담당한 기능은 대상 시장과 목적이 서로 다릅니다.

개발자 모드

기존에 만들어진 개발자 모드를 C++⁠·Qt/QML(Signal-slot)로 고도화. 당시 신차부터 이후 출시된 전 차종에 탑재, 디자인 리뉴얼 뒤에도 같은 기능이 현행 플랫폼까지 유지.

기도 방향(키블라) 안내

인도향 전 차종. 직접 개발. C++ Vector 기반 구면 삼각법 알고리즘을 구현하고 Kalman Filter로 위치 오차를 보정, 방위각 오차 360° 대비 1% 미만(약 3.6° 이내).

GPS(NMEA) 수집⁠·추적

북미향 전 차종. 내비게이션 영역에서 차량 위치 데이터를 수집⁠·추적하는 서비스 직접 개발.

Connectivity

차량 간 신호(signal) 송수신 기능 개발.

북미 현지 검증

미국 현지 2개 지역에서 3개월. 양산 전 품질 확인과 양산 대응. 현지 설정⁠·언어⁠·지역 차이와 실차 환경 호환⁠·성능 이슈를 현지에서 확인해 대응.

아키텍처헤드유닛 앱 구성

헤드유닛 앱을 화면(QML)⁠·기능(C++/Qt)⁠·플랫폼 세 계층으로 나눠 그린 개념도입니다. 화면과 기능은 Signal-slot으로 이어지고, GPS 수신기에서 들어온 NMEA 문장이 위치 보정⁠·방위각 계산과 위치 수집⁠·추적으로 흘러갑니다. 위치 기록은 헤드유닛 안 내비게이션 영역의 위치 추적에 씁니다.

  • 화면 계층개발자 모드⁠·기도 방향 안내 화면(QML)
  • 기능 계층개발자 모드 기능, NMEA 파서⁠·위치 수집⁠·추적, Kalman Filter 위치 보정, 구면 삼각법 방위각 계산(C++)
  • 플랫폼 계층헤드유닛 임베디드 실행⁠·네이티브 개발 환경
  • 외부GPS 수신기(입력)

핵심 흐름 ① 기도 방향 방위각 계산

직접 개발한 기도 방향 안내 기능에서, 위치 한 건이 들어와 화면의 방향 표시가 바뀌기까지의 흐름입니다.

  • GPS 위치는 Kalman Filter로 보정한 뒤 방위각 계산에 사용
  • 먼 거리 방향 계산에 일반적으로 쓰는 구면 삼각법으로, 지구를 구로 보고 현재 위치에서 성지(메카) 방향의 방위각 계산
  • 계산 결과는 Signal로 QML 안내 화면에 전달
  • 방위각 오차는 360° 대비 각도 오차로 검증: 1% 미만(약 3.6° 이내)

핵심 흐름 ② GPS(NMEA) 수집⁠·추적

직접 개발한 북미향 차종의 위치 수집⁠·추적 흐름입니다. GPS 수신기의 NMEA 문장을 받아 위치 기록으로 남기고, 이 기록을 헤드유닛 안 내비게이션 영역의 위치 추적에 씁니다. 검사⁠·추출 단계는 NMEA 표준의 일반적인 처리 순서로 그렸습니다.

  • GPS 수신기에서 표준 NMEA 문장으로 위치 데이터 수신
  • 일반적인 NMEA 처리 순서: 체크섬⁠·형식 검사 → 시각⁠·위치⁠·속도 필드 추출 → 위치 기록 저장
  • 기록은 차 밖으로 보내지 않고 헤드유닛 안 내비게이션 영역의 위치 추적에 사용

현지 검증 이슈 처리 흐름

미국 현지 2개 지역에서 3개월간 품질을 확인하며 실제로 만난 이슈는 크게 두 유형이었습니다. 현지 설정⁠·언어⁠·지역 차이에서 생기는 문제와, 실차 환경에서만 드러나는 호환⁠·성능 문제입니다. 두 유형 모두 현지 조건에서 재현⁠·확인한 뒤 대응했습니다.

  • 현지 설정⁠·언어⁠·지역 차이: 지역 설정⁠·언어 표시 차이로 생기는 문제를 현지 환경에서 재현해 고침
  • 실차 환경 호환⁠·성능: 실차에서만 드러나는 호환⁠·성능 문제를 현장에서 확인해 대응
  • 품질 확인을 마친 뒤 양산 대응

쓴 방식과 그 이유

기능마다 쓴 방식과, 그 방식이 일반적으로 쓰이는 이유입니다.

쓴 방식이 방식을 쓰는 이유(일반 원리)결과

  • 쓴 방식개발자 모드 고도화 때 기존 화면(QML)⁠·기능(C++) 경계를 깨지 않음

    이 방식을 쓰는 이유(일반 원리)
    이미 Signal-slot으로 나뉜 구조라, 그 경계 안에서 기능만 더하면 디자인 교체와 상관없이 유지됨
    결과
    디자인만 바뀌고 같은 기능이 현행 플랫폼까지 유지

  • 쓴 방식방위각 계산을 구면 삼각법으로 직접 구현(C++ Vector 기반)

    이 방식을 쓰는 이유(일반 원리)
    먼 거리의 방향은 평면 근사로 계산하면 어긋나기 쉬워, 일반적으로 구면 계산을 쓰는 방식
    결과
    Kalman Filter 보정과 함께 방위각 오차 360° 대비 1% 미만(약 3.6° 이내)

  • 쓴 방식GPS 위치에 Kalman Filter 보정 적용

    이 방식을 쓰는 이유(일반 원리)
    잡음이 섞인 위치 데이터에 일반적으로 쓰는 방식으로, 이전 추정과 새 측정을 함께 반영
    결과
    보정된 위치를 방위각 계산에 사용

  • 쓴 방식위치 데이터를 표준 NMEA 문장 단위로 수집

    이 방식을 쓰는 이유(일반 원리)
    NMEA는 GPS 수신기가 일반적으로 내보내는 표준 형식이라 같은 방식으로 검사⁠·기록할 수 있음
    결과
    북미향 전 차종 GPS 수집⁠·추적 서비스에 적용

문제 현황

위치 잡음
  • 인도향 전 차종 기도 방향(키블라) 안내 기능 직접 개발
  • 현재 위치에서 성지(메카) 방향 방위각을 계산해 화면에 표시
  • 차량은 계속 움직이고 GPS 위치에 측정 잡음이 섞임

원인 분석

오차 원인
  • 방위각은 입력 위치를 그대로 따라가서, GPS 원값이 튀면 방향 표시도 흔들릴 수 있음
  • 먼 목적지를 평면처럼 계산하면 방향이 어긋나기 쉬움
  • 그래서 이런 계산에는 보통 구면 계산을 씀

해결 과정

직접 구현

문제 상황

인도향 전 차종에 들어가는 기도 방향(키블라) 안내 기능을 직접 개발했습니다. 차량의 현재 위치에서 성지(메카) 방향의 방위각을 계산해 화면에 보여 줘야 했고, 차량은 계속 움직이며 GPS 위치에는 측정 잡음이 섞입니다.

원인 분석

방위각은 입력 위치를 그대로 따라가므로, 일반적으로 GPS 원값을 바로 쓰면 위치가 튈 때 방향 표시도 함께 흔들릴 수 있습니다. 또 멀리 떨어진 목적지는 평면 지도처럼 계산하면 방향이 어긋나기 쉬워, 이런 계산에는 보통 구면 계산을 씁니다.

해결 과정
  1. C++ Vector 기반 구면 삼각법 방위각 계산 직접 구현(지구를 구로 보고 두 지점 사이 방향을 구하는, 먼 거리 방향 계산에 일반적으로 쓰는 방식)
  2. Kalman Filter로 GPS 위치 오차 보정(이전 추정과 새 측정을 함께 반영하는, 잡음 섞인 위치 데이터에 일반적으로 쓰는 방식)
  3. 보정된 위치로 방위각을 계산하고, 결과는 Signal-slot으로 QML 안내 화면에 전달
  4. 방위각 오차를 360° 대비 각도 오차로 검증

CASE 03 / 03임베디드개발

디자인이 바뀌어도 남는 개발자 모드

문제 현황

리뉴얼 반복
  • 기존에 만들어진 개발자 모드 고도화를 맡음
  • 당시 신차부터 이후 전 차종에 들어가는 기능
  • 플랫폼 세대 교체·디자인 리뉴얼을 계속 거칠 수밖에 없음

원인 분석

계층 경계
  • 화면(QML)⁠·기능(C++)이 이미 Signal-slot으로 나뉜 구조
  • 이 경계를 무너뜨리면 디자인 바꿀 때마다 기능까지 다시 손봐야 함

해결 과정

경계 유지
  1. 기존 개발자 모드의 기능 고도화
  2. 화면(QML)⁠·기능(C++) 경계를 깨지 않고 기능을 더함
  3. 두 계층은 원래 구조대로 Qt Signal-slot으로 연결

결과

현행 유지
  • 당시 신차부터 이후 출시된 전 차종에 탑재
  • 리뉴얼 때 화면 디자인만 바뀌고 기능은 그대로
  • 같은 기능이 현행 플랫폼까지 유지되고 있음
전체 설명 보기
문제 상황

차량 인포테인먼트에 기존에 만들어진 개발자 모드를 고도화했습니다. 당시 신차부터 이후 전 차종에 들어가는 기능이라, 플랫폼 세대 교체와 디자인 리뉴얼을 계속 거칠 수밖에 없었습니다.

원인 분석

개발자 모드는 이미 화면(QML)과 기능(C++)이 Signal-slot으로 나뉜 구조였습니다. 고도화하면서 이 경계를 무너뜨리면, 디자인을 바꿀 때마다 기능까지 다시 손봐야 하는 구조가 됩니다.

해결 과정
  1. 기존 개발자 모드의 기능 고도화
  2. 기존 화면(QML)⁠·기능(C++) 경계를 깨지 않고 기능을 더함. 두 계층은 원래 구조대로 Qt Signal-slot으로 연결
결과

고도화한 개발자 모드가 당시 신차부터 이후 출시된 전 차종에 탑재. 리뉴얼 때 화면 디자인만 바뀌고, 기능은 현행 플랫폼까지 그대로 유지되고 있습니다.
