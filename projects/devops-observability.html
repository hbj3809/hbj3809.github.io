프로젝트 개요
무엇을, 왜 만들었나

선진에서 개발·운영하던 사내 업무 시스템의 배포·인증·관제를 하나의 운영 기반으로 정리한 프로젝트입니다. Jenkins·Docker 배포 파이프라인과 Nginx 기반 Blue/Green 전환으로 배포 리드타임을 평균 60분에서 10분↓으로 줄였습니다(실측). ELK·Grafana·APM 통합 관제와 Slack 알림으로는 장애를 현업의 전화보다 먼저 알아채는 구조를 만들었고, 장애 감지 시간은 약 90% 줄어든↓ 것으로 추정합니다. 로그인은 Google Workspace 와 연동한 상용 SSO 제품으로 OAuth 2.0 기반 전사 SSO 를 적용해 SFA/CRM·TMS/WMS·MES·그룹웨어 등을 하나로 묶었습니다.

개요수동 배포와 흩어진 로그를 하나의 운영 기반으로

선진 기술연구소 디지털혁신센터에서 SFA/CRM·TMS/WMS·MES 같은 사내 업무 시스템을 직접 개발하고 운영까지 맡았습니다. 시스템이 늘면서 두 가지 부담이 쌓였습니다. 배포는 작업 예정을 공지하고 사람이 직접 반영한 뒤 정상 여부를 확인하는 방식이라 한 번에 평균 60분이 걸렸고, 수작업 단계마다 반영 실수(휴먼 에러) 위험이 있었습니다. 로그는 시스템마다 따로 쌓여 있어, 장애는 주로 현업의 전화 연락으로 확인했습니다.

목표는 안정적인 운영과 개발 생산성을 함께 높이는 것이었습니다. 수작업 배포를 자동화해 새 버전을 빠르고 안전하게 올리고, 흩어진 로그와 지표를 한곳에 모아 데이터로 시스템 상태를 지켜보고, 여러 시스템의 로그인을 하나의 인증 체계로 묶었습니다.

  • 기간: 2023.03 ~ 2024.04(선진 재직 2022.01 ~ 2024.04 중)
  • 대상: 직접 개발·운영한 사내 업무 시스템(SFA/CRM·TMS/WMS·MES 등)

아키텍처배포·운영·인증·관제 네 축

구성은 네 축입니다. 배포 자동화는 Git→Jenkins(빌드·테스트)→Docker 이미지로 이어지며, 해외 법인 쪽은 커밋하면 파이프라인이 자동으로 돌고 국내는 수동으로 실행합니다. 운영 환경은 개발/운영을 나눈 뒤 Blue/Green 방식으로 버전을 바꾸는데, 새 버전은 자동 헬스체크로 정상 여부를 확인하고 Nginx 에서 트래픽을 넘깁니다. 통합 인증은 로그인을 Google Workspace 와 연동한 상용 SSO 제품에 맡겨 OAuth 2.0 기반 전사 SSO 를 적용했고, 토큰(JWT Access/Refresh)은 직접 만든 Spring Security 공통 인증 모듈이 발급해 각 시스템은 세션 없이 무상태 인증을 씁니다. 통합 관제는 로그를 ELK 로, 지표를 Grafana·APM 으로 모으고 임계치를 넘으면 Slack 으로 알립니다.

네 축을 한 플랫폼으로 묶은 이유는 문제의 뿌리가 같았기 때문입니다. 배포·로그·로그인을 시스템마다 따로 다루면 사람이 직접 챙겨야 할 곳이 시스템 수만큼 늘고, 그 사이에서 반영 실수와 늦은 장애 확인이 생겼습니다. 새 시스템도 같은 파이프라인·SSO·로그 수집에 붙여 같은 기준으로 운영하는 것을 목표로 했습니다.

핵심 흐름 ①Blue/Green 자동 배포

배포 파이프라인의 실행 방식은 해외 법인과 국내를 나눠 정했습니다. 해외 법인 쪽은 ERP 가 가볍고 데이터가 많지 않아, 커밋하면 Jenkins 파이프라인이 자동으로 실행되어 빌드·테스트·Docker 이미지 생성까지 이어지게 했습니다. 국내는 파이프라인을 수동으로 실행하되, 테스트 단계도 거치게 했습니다.

이미지가 준비되면 지금 서비스 중인 버전(Blue)은 그대로 둔 채 새 버전(Green)을 옆에 띄우고, 자동 헬스체크로 정상 여부를 확인합니다. 정상이면 Nginx 에서 트래픽을 Green 으로 넘기고, 이상이 보이면 전환하지 않고 기존 버전을 유지합니다.

배포 한 번의 끝은 정상 작동을 확인하고 현업에 이용을 안내하는 시점으로 잡았고, 도입 후 이 과정이 10분으로 줄었습니다↓.

  • 빌드·테스트·이미지 생성: Jenkins 파이프라인으로 자동화 — 자동·수동 실행 모두 테스트 단계 포함
  • 배포 단위: Docker 이미지 — 사람이 직접 반영하던 단계를 줄임
  • 전환 기준: 자동 헬스체크로 새 버전 정상 확인 뒤 Nginx 에서 트래픽 전환, 이상 시 기존 버전 유지
  • 완료 기준: 정상 작동 확인 후 현업 이용 안내

핵심 흐름 ②OAuth 2.0 SSO 와 무상태 토큰 인증

사용자는 Google Workspace 와 연동한 상용 SSO 제품에서 한 번 로그인하고, SFA/CRM·TMS/WMS·MES·그룹웨어 등 사내 시스템을 다시 로그인하지 않고 씁니다. 로그인(신원 확인)은 상용 SSO 제품에 맡기고, 토큰 발급·재발급은 직접 만든 Spring Security 코드(공통 인증 모듈)가 맡았습니다. 인증은 OAuth 2.0 기반 SSO 와 JWT(Access/Refresh) 기반 무상태(Stateless) 인증으로 처리해, 각 업무 시스템은 세션을 따로 저장하지 않고 요청에 담긴 토큰으로 사용자를 확인합니다. Access Token 이 만료되면 Refresh Token 으로 새 토큰을 받습니다. 업무 시스템 쪽 인증·인가 규칙도 같은 Spring Security 공통 모듈로 묶어, 시스템마다 로그인과 권한 검사를 따로 만들지 않도록 했습니다.

  • 적용 범위: SFA/CRM·TMS/WMS·MES·그룹웨어·기타 사내 시스템
  • 인증 방식: OAuth 2.0 기반 SSO, JWT(Access/Refresh) 기반 무상태 인증
  • 인증 처리: Spring Security 공통 모듈을 여러 업무 시스템이 함께 사용

핵심 흐름 ③로그·지표 수집과 임계치 알림

시스템별 애플리케이션 로그는 ELK(Logstash→Elasticsearch→Kibana)로 모아 한 화면에서 검색합니다. 실시간 트래픽·JVM 힙 메모리·API 응답 속도 같은 지표는 Grafana 와 APM 으로 추적합니다.

오류나 지표가 임계치를 넘으면 Slack Webhook 으로 개발자 채널에 바로 알리고, 개발자는 같은 시간대의 로그와 지표를 한곳에서 보며 원인을 좇습니다.

개념 모델인증·환경·관제

인증(법인·사용자·권한), 운영 환경(시스템·개발/운영 환경·배포), 관제(로그·알림 규칙·알림)를 직접 설계한 관리 DB 로 묶어 관리했고, 여기서는 개념 수준으로 정리했습니다. 실제 테이블 이름이 아니라 역할을 나타내는 일반 이름으로 그렸습니다.

설계 결정왜 이렇게 골랐나

도구를 고르기보다 '사람이 지켜봐야 하는 단계'와 '사용자가 먼저 알게 되는 장애'를 줄이는 쪽으로 결정했습니다.

Blue/Green 배포

공지→수작업 반영→확인 순서는 사람이 모든 단계를 지켜야 했습니다. 새 버전을 기존 버전 옆에 올려 자동 헬스체크로 확인한 뒤 Nginx 에서 트래픽을 넘기면, 확인이 끝날 때까지 기존 버전이 그대로 서비스하고 이상이 보이면 전환하지 않으면 됩니다.

Docker 이미지 단위 배포

빌드 결과를 이미지 하나로 고정해, 사람이 직접 반영하던 단계를 줄이고 그 과정의 반영 실수를 막았습니다.

해외는 커밋 시 자동, 국내는 수동 실행

해외 법인 쪽은 ERP 가 가볍고 데이터가 많지 않아 커밋하면 파이프라인이 바로 돌게 했고, 국내는 수동으로 실행했습니다. 어느 쪽이든 테스트 단계는 거치게 했습니다.

상용 SSO 제품 + 무상태 토큰 인증

로그인은 상용 SSO 제품에 맡겨 보안 기준을 한곳에 모으고 사용자 경험도 단순하게 했습니다. 토큰은 직접 만든 공통 모듈이 발급하고 각 시스템은 세션 없이 이 토큰으로 사용자를 확인하므로, 시스템이 늘어도 같은 방식으로 붙이면 됩니다.

로그는 ELK 로 한곳에

시스템별로 따로 보던 로그를 중앙에 모아, 장애 때 같은 시간대의 기록을 한 화면에서 검색하도록 했습니다.

임계치 알림은 Slack Webhook

현업의 전화보다 개발자가 먼저 알도록, 트래픽·JVM 힙·API 응답 속도가 임계치를 넘으면 개발자 채널로 바로 알림이 가게 했습니다.

환경 분리와 법인 데이터 격리

개발 작업이 운영 데이터·설정에 닿지 않도록 개발/운영 환경을 나눴습니다. 4개국 법인(베트남·필리핀·인도·미얀마) 데이터는 SFA/CRM 에서 법인별 DB·스키마로 나눠 격리했고, 국가별 시간대·통화·언어 차이는 공통 어댑터 패턴으로 처리했습니다.

성과배포 리드타임 60분→10분↓

배포 리드타임은 배포 한 건을 시작해 마칠 때까지의 시간입니다. 도입 전에는 작업 공지부터 정상 확인까지 평균 60분이 걸렸고, 도입 후에는 정상 작동을 확인하고 현업에 이용을 안내하기까지 10분이 걸렸습니다. 장애 감지 시간 단축(약 90%)은 같은 방식으로 잰 전후 기록이 없어 추정치로만 적습니다.

CASE 01 / 03CI/CD

배포 한 번에 평균 60분 → 10분↓

문제 현황

수작업 배포
  • 배포 때마다 작업 예정 공지 후 사람이 직접 빌드·반영
  • 공지부터 정상 확인까지 평균 60분 소요
  • 수작업 단계마다 반영 실수(휴먼 에러) 위험

원인 분석

절차 병목
  • 시간을 잡아먹은 건 코드가 아니라 절차
  • 빌드·반영·확인이 모두 사람 손을 거침
  • 무중단 배포 구조가 없어 미리 공지하고 시간을 따로 잡아야 함

해결 과정

배포 자동화
  1. 빌드·테스트·배포를 Jenkins 파이프라인으로 자동화(해외 커밋 시 자동·국내 수동)
  2. Docker 이미지를 배포 단위로 삼아 수동 반영 단계 축소
  3. Blue/Green: 자동 헬스체크로 새 버전 확인 뒤 Nginx 에서 트래픽 전환
  4. '현업 이용 안내'까지를 완료로 보고 전후 소요 시간 비교

결과

80% 단축↓
  • 배포 리드타임 평균 60분 → 10분↓, 80% 단축↓(실측)
  • 새 기능을 현업에 더 빨리 내놓을 수 있게 됨
전체 설명 보기
문제 상황

배포 때마다 작업 예정을 공지하고, 사람이 직접 빌드·반영한 뒤 정상 여부를 확인했습니다. 공지부터 정상 확인까지 평균 60분이 걸렸고, 수작업 단계마다 반영 실수(휴먼 에러) 위험이 있었습니다.

원인 분석

시간을 잡아먹은 것은 코드가 아니라 절차였습니다. 빌드·반영·확인이 모두 사람 손을 거쳤고, 새 버전을 올리는 동안 기존 버전이 계속 서비스하도록 받쳐 줄 구조(무중단 배포)가 없어 작업 예정을 미리 공지하고 시간을 따로 잡아야 했습니다.

해결 과정
  1. Jenkins 파이프라인으로 빌드·테스트·이미지 생성·배포 자동화 — 해외 법인은 커밋하면 자동 실행(ERP 가 가볍고 데이터가 많지 않음), 국내는 수동 실행하되 테스트 단계도 거침
  2. Docker 이미지를 배포 단위로 삼아 사람이 직접 반영하던 단계 축소
  3. Blue/Green 방식으로 새 버전을 기존 버전 옆에 띄우고, 자동 헬스체크로 정상을 확인한 뒤 Nginx 에서 트래픽 전환
  4. '정상 작동 확인 후 현업 이용 안내'까지를 배포 완료로 보고 전후 소요 시간 비교
결과

배포 리드타임이 평균 60분에서 10분↓으로 줄었습니다(80% 단축↓, 실측). 새 기능을 현업에 더 빨리 내놓을 수 있게 되었습니다.

60분→10분↓
80% 단축↓, 실측 — 도입 전은 평균값

배운 점

배포 시간을 줄인 것은 빠른 도구보다 사람이 지켜봐야 하는 단계를 줄인 결과였습니다. 이후 결제 시스템 MSA 전환에도 같은 Jenkins·Docker Blue/Green 배포를 적용했고, LOGION 에서는 CI/CD 를 기획 단계부터 함께 설계했습니다.

CASE 02 / 03통합 관제

장애를 전화로 알던 구조 → 알림으로 먼저 감지

문제 현황

늦은 감지
  • 로그가 시스템마다 따로 쌓여 있음
  • 장애는 현업의 전화로 먼저 알게 됨
  • 그 뒤 시스템별 로그를 하나씩 찾아보며 원인 추적

원인 분석

로그 분산
  • 로그가 흩어져 한곳에서 볼 수 없음
  • 이상 징후를 개발자에게 먼저 알려 줄 지표·알림이 없음
  • 그래서 감지 시점이 사용자 연락 뒤로 밀림

해결 과정

통합 관제
  1. ELK 로 시스템별 로그를 중앙에 모아 검색·시각화
  2. Grafana·APM 으로 트래픽·JVM 힙·API 응답 속도 추적
  3. 임계치를 넘으면 Slack Webhook 으로 개발자 채널에 자동 알림
  4. 알림 뒤 같은 시간대 로그·지표를 한곳에서 보며 원인 확인

결과

선제 감지
  • 장애를 현업 연락보다 알림으로 먼저 받고 바로 대응
  • 장애 감지 시간 약 90% 단축↓(추정치)
  • 전후를 같은 방식으로 잰 기록이 없어 측정값 아님
전체 설명 보기
문제 상황

로그가 시스템마다 따로 쌓여 있어, 장애가 나면 현업의 전화로 먼저 알게 되고 그 뒤에 시스템별 로그를 하나씩 찾아보며 원인을 좇았습니다.

원인 분석

원인은 두 가지였습니다. 로그가 흩어져 있어 한곳에서 볼 수 없었고, 이상 징후를 개발자에게 먼저 알려 줄 지표·알림이 없었습니다. 그래서 감지 시점이 사용자가 불편을 느끼고 연락한 뒤로 밀렸습니다.

해결 과정
  1. ELK(Logstash → Elasticsearch → Kibana)로 시스템별 로그를 중앙에 모아 검색·시각화
  2. Grafana·APM 으로 실시간 트래픽·JVM 힙 메모리·API 응답 속도 추적
  3. 임계치 기반 자동 알림을 Slack Webhook 으로 개발자 채널에 연결
  4. 알림을 받으면 같은 시간대의 로그와 지표를 한곳에서 보며 원인 확인
결과

장애를 현업 연락보다 먼저 알림으로 받고 개발자가 바로 대응하게 되어, 감지 시간이 약 90% 줄었다고↓ 추정합니다. 도입 전후를 같은 방식으로 잰 기록이 없어 측정값이 아닌 추정치로 적습니다.

숫자로 보기

장애 감지 시간
약 90% 단축↓
추정치 — 측정값 아님

배운 점

관제의 핵심은 대시보드를 늘리는 것보다 누가 먼저 아는가를 바꾸는 것이었습니다. 효과를 숫자로 말하려면 도입 전 기준선부터 남겨야 한다는 점도 함께 남았습니다.

CASE 03 / 03보안 표준화

시스템마다 다른 인증 → 전사 SSO 와 법인 데이터 격리

문제 현황

분산 위험
  • SFA/CRM·TMS/WMS·MES·그룹웨어 등 사내 시스템 증가
  • 베트남·필리핀·인도·미얀마 법인까지 SFA/CRM 사용
  • 인증·데이터 경계를 따로 다루면 보안 기준이 흩어질 위험

원인 분석

규칙 제각각
  • 인증·인가를 시스템별로 만들면 검사 기준이 제각각
  • 개발과 운영, 법인과 법인 사이 경계도 코드마다 다를 수 있음

해결 과정

SSO 통합
  1. Google Workspace 연동 상용 SSO 제품으로 OAuth 2.0 전사 SSO 적용
  2. 직접 만든 Spring Security 공통 모듈로 JWT 발급·무상태 검증
  3. 개발/운영 환경 분리로 운영 데이터·설정 격리
  4. SFA/CRM 4개국 데이터는 법인별 DB·스키마로 격리, 시간대·통화·언어는 공통 어댑터

결과

기준 표준화
  • 로그인·인증 규칙을 하나의 체계로 묶어 보안 기준 표준화
  • 한 번 로그인으로 SFA/CRM·TMS/WMS·MES·그룹웨어 등 이용
  • 이 영역은 따로 잰 숫자 없음
전체 설명 보기
문제 상황

사내 업무 시스템(SFA/CRM·TMS/WMS·MES·그룹웨어 등)이 늘고 베트남·필리핀·인도·미얀마 법인까지 SFA/CRM 을 함께 쓰게 되면서, 인증과 데이터 경계를 시스템마다 따로 다루면 보안 기준이 흩어질 위험이 있었습니다.

원인 분석

인증·인가 규칙이 시스템별로 구현되면 같은 사용자라도 시스템마다 다른 기준으로 검사되고, 개발과 운영, 법인과 법인 사이의 경계도 코드마다 다르게 지켜질 수 있습니다.

해결 과정
  1. 로그인은 Google Workspace 와 연동한 상용 SSO 제품에 맡기고 OAuth 2.0 기반 전사 SSO 적용 — SFA/CRM·TMS/WMS·MES·그룹웨어·기타 사내 시스템 로그인 일원화
  2. 직접 만든 Spring Security 공통 모듈이 JWT(Access/Refresh)를 발급하고 여러 업무 시스템이 같은 모듈로 토큰을 검증 — 각 시스템은 세션을 따로 두지 않음
  3. 개발/운영 환경 분리로 운영 데이터·설정을 개발 작업과 격리
  4. SSO 와 함께, SFA/CRM 에서는 4개국 법인 데이터를 법인별 DB·스키마로 나눠 격리하고 시간대·통화·언어 차이는 공통 어댑터로 처리
결과

로그인과 인증 규칙을 하나의 체계로 묶어 보안 기준을 표준화했고, 사용자는 한 번 로그인으로 SFA/CRM·TMS/WMS·MES·그룹웨어 등 여러 시스템을 쓰게 되었습니다. 이 영역은 따로 잰 숫자가 없습니다.

구조로 보기

배운 점

인증과 데이터 경계는 기능보다 먼저 공통 규칙으로 정해 두어야 시스템이 늘어도 기준이 흩어지지 않았습니다. 이후 LOGION 에서는 인증·권한·테넌트를 Auth 컨텍스트 하나로 먼저 분리했습니다.

정리이 프로젝트에서 남긴 것

시스템마다 따로 챙기던 배포·로그·로그인을 배포 파이프라인·통합 관제·전사 SSO 라는 공통 기반으로 모아, 새 시스템도 같은 방식으로 붙일 수 있는 틀을 남겼습니다. 배포 리드타임은 평균 60분에서 10분↓으로 줄었고(실측), 장애는 현업 전화보다 알림으로 먼저 알게 되었습니다.
