프로젝트 개요
무엇을, 왜 만들었나

물류기기 풀링(Pooling) 기업의 사내 기간계를 Miplatform 기반 모놀리스에서 Nexacro N + Spring Boot 3.4 MSA 구조로 옮긴 고도화 프로젝트입니다. 백엔드와 DevOps를 총괄했고, Nexacro N 화면에서는 피벗·그리드·처리 함수 같은 공통 모듈을 직접 만들었습니다. 솔루션별 Backend·DB 인터페이스는 상용 EAI 솔루션을 도입해 한 경로로 모았고, 용량이 부족하던 파일 서버는 Amazon S3·Java NIO 기반으로 이관했습니다. Jenkins·Docker Compose·K8s 기반 CI/CD를 세우고, 무중단 배포는 애플리케이션 성격에 따라 Blue/Green과 롤링으로 나눠 적용했습니다. 기간계는 Kafka로 일 평균 8만 건의 트랜잭션을 처리했고, EAI 도입 후 인터페이스 장애는 0건이었습니다(고객사 네트워크·방화벽 이슈 제외).

개요배경·과제·내 역할

로지스올시스템즈에 입사하면서 처음 맡은 사내 기간계 고도화 프로젝트입니다. 물류기기 풀링 사업의 업무를 처리하는 기간계가 Miplatform 기반 모놀리스로 운영되고 있었습니다. 파일 서버는 용량이 부족했고, 솔루션별 Backend·DB 인터페이스를 한곳에서 제공하는 통합 경로가 없었습니다.

과제는 세 갈래였습니다. 화면과 백엔드를 Nexacro N + Spring Boot 3.4 MSA 구조로 옮기기, 솔루션별 인터페이스를 상용 EAI 솔루션으로 모아 제공하기, 그리고 나뉜 서비스를 무중단 CI/CD로 배포하기입니다.

저는 백엔드와 DevOps를 총괄했습니다. 백엔드의 MSA 전환, 상용 EAI 솔루션을 통한 인터페이스 통합, Jenkins·Docker Compose·K8s 기반 CI/CD 구축이 여기에 들어갑니다. Nexacro N 화면은 전체를 맡지 않았고, 피벗·그리드·처리 함수 같은 화면 공통 모듈을 직접 만들었습니다. 2024년 11월부터는 LOGION 총괄 PM을 함께 맡아 두 프로젝트를 병행했습니다.

  • 프로젝트 범위: 화면(Miplatform → Nexacro N) · 백엔드(Spring Boot 3.4) · 파일(Amazon S3 · Java NIO) · 연계(상용 EAI · Kafka) · 배포(Jenkins · Docker Compose · K8s)

전환 전 · 후 아키텍처

전환 전에는 화면과 업무 기능 전체가 한 애플리케이션에 묶여 있어서, 일부만 고쳐도 전체를 다시 올려야 했습니다. 파일과 솔루션별 인터페이스도 그 애플리케이션에 붙어 있었고, 파일 서버는 용량이 부족했습니다.

전환 후에는 Nexacro N 화면이 Spring Boot 3.4 서비스들을 호출합니다. 파일은 서버 밖 Amazon S3에 두고, 다른 솔루션으로 보내는 데이터는 Kafka 이벤트와 상용 EAI 솔루션을 거쳐 나갑니다. 서비스 배포는 Jenkins·Docker·K8s 파이프라인이 맡습니다.

업무 처리와 연계의 분리

화면 응답은 업무 DB 반영까지로 끝내고, 다른 솔루션으로 보내는 일은 이벤트로 넘겨 상용 EAI 솔루션이 처리하는 구조입니다. 연계가 늦어지거나 실패해도 사용자의 업무 처리는 막히지 않고, 실패한 건은 EAI에 실패 상태로 남아 재전송 기능으로 다시 보낼 수 있습니다.

연계 건의 상태

연계 한 건은 대기와 전송 중을 거쳐 성공하거나 실패합니다. 기간계에 도입한 상용 EAI 솔루션이 이 상태(대기·전송 중·실패·재전송)를 관리했고, 실패한 건은 EAI의 재전송 기능으로 다시 전송 중 상태가 됩니다. 실패를 지우지 않고 상태로 남겨 두어야 어느 건이 멈췄는지 확인하고 다시 보낼 수 있습니다.

CI/CD 파이프라인

커밋부터 운영 반영까지를 Jenkins 파이프라인으로 묶었습니다. 시험을 통과한 빌드만 Docker 이미지로 만들고, 운영 무중단 배포는 Blue/Green과 롤링 두 방식을 모두 도입했습니다. DevOps 고도화를 막 들여오는 단계라, 한 방식에 고정하기보다 여러 방식을 들여와 써 보는 편이 저와 회사 모두에 더 도움이 된다고 봤습니다. 진행하면서 애플리케이션 성격에 따라 Blue/Green과 롤링을 나눠 배치했습니다. 화면·외부 연동처럼 한 번에 바꿔야 하는 서비스는 Blue/Green, 여러 인스턴스로 도는 내부 서비스는 롤링으로 배포했습니다.

Blue/Green은 새 버전 환경을 따로 띄운 뒤 트래픽을 한 번에 넘기고, 롤링은 인스턴스를 차례로 새 버전으로 바꿉니다. 두 방식 모두 새 버전이 정상으로 확인돼야 트래픽을 넘기므로, 확인에 실패하면 남아 있는 이전 버전이 계속 서비스합니다.

설계 결정왜 이렇게 했나

서비스 분리와 EAI 한 경로는 '한 곳의 문제가 전체로 번지지 않는가'와 '실패한 것을 다시 처리할 수 있는가'를 기준으로 골랐습니다. 파일 저장소는 용량 부족과 컨테이너 배포 때문에, CI/CD는 늘어난 배포 단위 때문에 함께 정했고, 화면 플랫폼은 회사가 정했습니다.

왜 서비스를 나눴나

한 기능이 멈춰도 다른 업무는 계속되는 구조가 필요했습니다. 모놀리스에서는 화면 하나를 고쳐도 전체를 다시 올려야 하고, 한 곳의 장애가 전체로 번집니다. 서비스를 나눠 배포와 장애가 미치는 범위를 줄였습니다.

왜 EAI 한 경로인가

업무 시스템에서는 인터페이스가 핵심이라고 봤습니다. 솔루션별 인터페이스를 상용 EAI 솔루션 한 경로로 모으면, 솔루션이 늘어도 연결 방식은 늘지 않고 연계 건의 상태(대기·전송 중·실패·재전송)와 재전송도 한곳에서 다룰 수 있습니다.

화면 플랫폼은 Nexacro N

화면 플랫폼은 회사가 정한 Nexacro N이었습니다. 저는 그 위에서 피벗·그리드·처리 함수 같은 화면 공통 모듈을 만들었습니다.

왜 파일을 Amazon S3로 옮겼나

파일 서버의 용량이 부족했습니다. 게다가 서비스를 여러 개로 나누고 컨테이너로 배포하면 특정 서버의 디스크에 파일을 두기 어렵습니다. 그래서 파일을 서버 밖 객체 저장소로 옮기고, 파일 입출력은 Java NIO 기반으로 바꿨습니다.

왜 CI/CD를 함께 세웠나

서비스를 나누면 배포 단위도 그만큼 늘어납니다. 사람이 하나씩 올리면 실수할 여지와 중단 시간이 함께 늘기 때문에, 전환과 같은 일정 안에 빌드부터 무중단 배포까지 자동화했습니다.

주요 구현

전환 작업은 화면·백엔드, 연계, 파일, 배포의 네 영역에서 진행했습니다.

  • Miplatform 기반 모놀리스를 Nexacro N 화면 + Spring Boot 3.4 MSA 구조로 전환, 백엔드 총괄
  • Nexacro N 화면 공통 모듈(피벗·그리드·처리 함수) 직접 제작
  • 상용 EAI 솔루션 도입으로 솔루션별 Backend·DB 인터페이스를 통합 제공, 연계 상태(대기·전송 중·실패·재전송) 관리와 재전송
  • Kafka 기반 트랜잭션 처리(일 평균 8만 건)
  • 기존 파일을 Amazon S3로 옮기고 파일 입출력을 Java NIO 기반으로 바꿔 파일 서버 용량 부족 해소
  • Jenkins·Docker Compose·K8s 기반 무중단 CI/CD 파이프라인 구축과 DevOps 총괄, 애플리케이션 성격에 따라 Blue/Green·롤링 배포를 나눠 배치

성과

숫자로 남은 성과는 처리량과 연동 안정성입니다. 기간계는 Kafka로 일 평균 8만 건의 트랜잭션을 처리했고, EAI 도입 후 인터페이스 장애는 0건이었습니다(고객사 네트워크·방화벽 이슈 제외).

단서를 붙인 이유가 있습니다. EAI를 거친 LOGION 연동이 고객사 방화벽 정책 변경으로 끊긴 적이 있었습니다. 원인이 우리 시스템 밖에 있던 이런 경우는 0건에 넣지 않았습니다.

문제 상황

기간계는 주변 솔루션들과 Backend·DB 단위로 인터페이스를 주고받았고, 이를 한곳에서 제공하는 통합 경로가 없었습니다. 통합 경로 없이 솔루션마다 따로 연결하면, 연결 방식도 연계가 실패했을 때 확인할 곳도 솔루션마다 달라집니다.

원인 분석

인터페이스를 솔루션마다 따로 두면, 연계 건이 지금 어느 상태인지와 실패한 건을 어떻게 다시 보낼지를 한곳에서 다루기 어렵습니다.

해결 과정
  1. 상용 EAI 솔루션을 도입해 솔루션별 Backend·DB 인터페이스를 한 경로로 통합 제공
  2. 연계 건마다 대기·전송 중·실패·재전송 상태를 EAI에서 관리
  3. 실패한 건은 EAI의 재전송 기능으로 다시 전송
결과

EAI 도입 후 인터페이스 장애 0건(고객사 네트워크·방화벽 이슈 제외). 이후 LOGION도 Kafka 이벤트와 EAI를 거쳐 기간계·고객사 시스템과 연동했습니다.

배운 점

연동 장애를 없애는 것만큼, 실패했을 때 어느 구간에서 멈췄는지 바로 가릴 수 있는 기록이 중요했습니다. 이후 EAI를 거친 LOGION 연동이 끊겼을 때도 연계 이력과 EAI 로그를 대조해 분류되지 않은 타임아웃 예외를 찾았고, 원인이 고객사 방화벽 정책 변경이라는 것을 가려냈습니다. 인터페이스 장애 0건에 '고객사 네트워크·방화벽 이슈 제외' 단서를 붙이는 이유입니다.

CASE 02 / 03마이그레이션

서버에 묶인 파일을 Amazon S3 · Java NIO로 이관

문제 현황

용량 부족
  • 모놀리스 시절 파일은 파일 서버에서 처리
  • 그 파일 서버의 용량이 부족

원인 분석

서버 종속
  • 파일이 한 파일 서버의 저장 공간에 묶임
  • 그 서버의 디스크 용량이 곧 파일을 둘 수 있는 한계

해결 과정

S3 이관
  1. 파일 저장소를 Amazon S3 객체 저장소로 이관
  2. 파일 입출력을 Java NIO 기반으로 전환
  3. 기존 파일도 Amazon S3로 옮김

결과

용량 해소
  • 파일 서버 용량 부족 해소
  • 특정 서버 디스크가 아닌 서버 밖 객체 저장소에 두는 구조로 전환
전체 설명 보기
문제 상황

모놀리스 시절 파일은 파일 서버에서 다뤘고, 그 파일 서버의 용량이 부족했습니다.

원인 분석

파일이 한 파일 서버의 저장 공간에 묶여 있어서, 그 서버의 디스크 용량이 곧 파일을 둘 수 있는 한계였습니다.

해결 과정
  1. 파일 저장소를 Amazon S3 객체 저장소로 이관
  2. 파일 입출력을 Java NIO 기반으로 전환
  3. 기존 파일도 Amazon S3로 옮김
결과

파일 서버 용량 부족 해소. 파일을 특정 서버의 디스크가 아닌 서버 밖 객체 저장소에 두는 구조로 전환

구조로 보기

배운 점

파일을 서버 밖 객체 저장소에 두면 저장 용량을 서버 디스크와 따로 늘릴 수 있고, 서비스를 나눠 컨테이너로 배포할 때도 특정 서버에 묶이지 않습니다.

CASE 03 / 03DevOps구축

배포를 Jenkins · Docker · K8s 무중단 CI/CD로

문제 현황

배포 부담
  • MSA로 나누면 배포 단위가 서비스 수만큼 늘어남
  • 회사는 DevOps 고도화 초기 단계

원인 분석

수동 반복
  • 사람이 서비스마다 빌드·반영을 반복
  • 배포 시간·실수할 여지가 서비스 수만큼 늘어남
  • 반영하는 동안 서비스가 멈출 수 있음

해결 과정

배포 자동화
  1. Jenkins로 빌드·시험·이미지 생성 자동화
  2. Docker·Docker Compose로 서비스 컨테이너화
  3. DevOps 고도화 초기라 Blue/Green·롤링을 모두 도입
  4. 애플리케이션 성격별로 두 방식 배치, 파이프라인·배포 환경 총괄

결과

전환 완료
  • CI/CD 전환 완료
  • 무중단 배포는 성격별 Blue/Green·롤링으로 나눠 운영
  • 다음 프로젝트 LOGION에선 자동 빌드·배포를 기획 단계부터 설계
전체 설명 보기
문제 상황

MSA로 나누면 배포 단위가 서비스 수만큼 늘어납니다. 회사는 DevOps 고도화를 막 들여오는 초기 단계였습니다.

원인 분석

사람이 서비스마다 빌드와 반영을 반복하면 배포 시간과 실수할 여지가 서비스 수만큼 늘어나고, 반영하는 동안 서비스가 멈출 수 있습니다.

해결 과정
  1. Jenkins로 빌드·시험·이미지 생성 자동화
  2. Docker·Docker Compose로 서비스 컨테이너화
  3. 무중단 배포는 Blue/Green과 롤링을 모두 도입: DevOps 고도화 초기라 여러 방식을 들여와 써 보는 편이 저와 회사에 더 도움이 된다고 판단
  4. 진행하면서 애플리케이션 성격에 따라 Blue/Green과 롤링을 나눠 배치
  5. 파이프라인과 배포 환경을 포함한 DevOps 총괄
결과

CI/CD 전환 완료. 무중단 배포는 애플리케이션 성격에 따라 Blue/Green과 롤링으로 나눠 운영했고, 다음 프로젝트인 LOGION에서는 자동 빌드·배포를 기획 단계부터 함께 설계했습니다.

구조로 보기

배운 점

MSA 전환과 CI/CD는 따로 하는 일이 아니었습니다. 서비스를 나누는 순간 배포가 병목이 되므로, 자동화도 전환과 같은 일정에 넣어야 합니다. 배포 방식도 처음부터 하나로 정하기보다, 도입 단계에서 여러 방식을 들여와 써 본 뒤 애플리케이션마다 맞는 쪽을 고르는 편이 나았습니다.

정리이 프로젝트에서 남긴 것

기간계 전환은 화면·백엔드만이 아니라 연계·파일·배포까지 함께 바꾸는 일이었습니다. 연계는 EAI 한 경로로 모으고, 파일은 서버 밖 Amazon S3로 옮기고, 배포는 무중단 CI/CD로 자동화했으며, 다음 프로젝트 LOGION에서는 자동 빌드·배포를 기획 단계부터 함께 설계했습니다.
