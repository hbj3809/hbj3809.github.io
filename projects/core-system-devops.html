무엇을, 왜 만들었나

물류기기 풀링(Pooling) 기업의 사내 기간계를 Miplatform 기반 모놀리스에서 Nexacro N + Spring Boot 3.4 MSA 구조로 옮긴 고도화 프로젝트입니다. 솔루션별 Backend·DB 인터페이스는 EAI로 모아 통합 제공했고, 파일 서버 문제는 Amazon S3·Java NIO 기반 이관으로 풀었습니다. Jenkins·Docker Compose·K8s 기반 무중단 CI/CD를 구축하고 DevOps를 총괄했습니다. 기간계는 Kafka로 일 평균 8만 건의 트랜잭션을 처리했고, EAI 도입 후 인터페이스 장애는 0건이었습니다(고객사 네트워크·방화벽 이슈 제외).

개요

로지스올시스템즈에 입사하면서 처음 맡은 사내 기간계 고도화 프로젝트입니다. 물류기기 풀링 사업의 업무를 처리하는 기간계가 Miplatform 기반 모놀리스로 운영되고 있었습니다. 파일 서버 문제가 있었고, 솔루션별 Backend·DB 인터페이스를 한곳에서 제공하는 통합 경로가 없었습니다.

과제는 세 갈래였습니다. 화면과 백엔드를 Nexacro N + Spring Boot 3.4 MSA 구조로 옮기기, 솔루션별 인터페이스를 EAI로 모아 제공하기, 그리고 나뉜 서비스를 무중단 CI/CD로 배포하기입니다.

저는 백엔드 전환과 EAI 인터페이스 통합을 맡았고, Jenkins·Docker Compose·K8s 기반 CI/CD 구축과 DevOps를 총괄했습니다. 2024년 11월부터는 LOGION 총괄 PM을 함께 맡아 두 프로젝트를 병행했습니다.

전환 전 · 후 아키텍처 초안

전환 전에는 화면과 업무 기능 전체가 한 애플리케이션에 묶여 있어서, 일부만 고쳐도 전체를 다시 올려야 했습니다. 파일과 솔루션별 인터페이스도 그 애플리케이션에 붙어 있었습니다.

전환 후에는 Nexacro N 화면이 Spring Boot 3.4 서비스들을 호출합니다. 파일은 서버 밖 Amazon S3에 두고, 다른 솔루션으로 보내는 데이터는 Kafka 이벤트와 EAI를 거쳐 나갑니다. 서비스 배포는 Jenkins·Docker·K8s 파이프라인이 맡습니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

업무 처리와 연계의 분리 초안

화면 응답은 업무 DB 반영까지로 끝내고, 다른 솔루션으로 보내는 일은 이벤트로 넘겨 EAI가 처리하는 구조입니다. 연계가 늦어지거나 실패해도 사용자의 업무 처리는 막히지 않고, 실패한 건은 이력에 남아 이벤트를 다시 발생시켜 재처리할 수 있습니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

연계 건의 상태 초안

연계 한 건은 대기, 전송 중, 성공 또는 실패 상태를 거칩니다. 실패한 건은 원인을 확인한 뒤 재전송으로 다시 전송 중 상태가 됩니다. 실패를 지우지 않고 상태로 남겨 두어야 어느 구간에서 멈췄는지 가를 수 있습니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

CI/CD 파이프라인 초안

커밋부터 운영 반영까지를 Jenkins 파이프라인 하나로 묶었습니다. 시험을 통과한 빌드만 Docker 이미지로 만들고, 스테이징에서 QA·현업 확인을 거친 뒤 배포 일정을 미리 알리고 운영에 반영합니다. 운영 배포는 새 버전을 먼저 띄워 헬스 체크를 통과한 뒤 전환하므로, 확인에 실패하면 이전 버전이 그대로 서비스합니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

설계 결정왜 이렇게 했나 초안

기술을 고를 때 '한 곳의 문제가 전체로 번지지 않는가'와 '실패한 것을 다시 처리할 수 있는가'를 기준으로 삼았습니다.

왜 서비스를 나눴나

한 기능이 멈춰도 다른 업무는 계속되는 구조가 필요했습니다. 모놀리스에서는 화면 하나를 고쳐도 전체를 다시 올려야 하고, 한 곳의 장애가 전체로 번집니다. 서비스를 나눠 배포와 장애가 미치는 범위를 줄였습니다.

왜 EAI 한 경로인가

업무 시스템에서는 인터페이스가 핵심이라고 봤습니다. 어떤 데이터든 같은 형식으로 주고받게 표준화해 두면, 솔루션이 늘어도 연결 방식은 늘지 않고 실패 기록도 한곳에 남습니다.

왜 Kafka인가

이벤트 하나를 여러 연계 시스템으로 넓힐 수 있는지, 실패한 데이터를 다시 처리할 수 있는지를 기준으로 봤습니다. Kafka는 토픽에 메시지를 일정 기간 보관하고 컨슈머 오프셋을 조정해 다시 처리할 수 있어서, 처리 후 메시지가 사라지는 RabbitMQ보다 맞았습니다.

왜 Nexacro N인가

Miplatform을 만든 제조사의 후속 UI 플랫폼이라, 기존 업무 화면의 구성 방식을 크게 바꾸지 않고 옮길 수 있는 선택지였습니다.

왜 파일을 Amazon S3로 옮겼나

서비스를 여러 개로 나누고 컨테이너로 배포하면 특정 서버의 디스크에 파일을 둘 수 없습니다. 파일을 서버 밖 객체 저장소로 옮기고, 파일 입출력은 Java NIO 기반으로 바꿨습니다.

왜 CI/CD를 함께 세웠나

서비스를 나누면 배포 단위도 그만큼 늘어납니다. 사람이 하나씩 올리면 실수할 여지와 중단 시간이 함께 늘기 때문에, 전환과 같은 일정 안에 빌드부터 무중단 배포까지 자동화했습니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

CASE 01 · 인터페이스통합

솔루션별 인터페이스를 EAI 한 경로로 초안

1문제 상황

기간계는 주변 솔루션들과 Backend·DB 단위로 인터페이스를 주고받았고, 이를 한곳에서 제공하는 통합 경로가 없었습니다. 연동할 솔루션이 늘수록 연결 방식과 실패 기록이 솔루션마다 달라졌습니다.

2원인 분석

연동마다 데이터 형식과 실패 처리, 기록 위치가 제각각이었습니다. 그래서 실패가 나면 어느 구간에서 멈췄는지 한곳에서 확인할 수 없었습니다.

3해결 과정
  1. EAI 도입으로 솔루션별 Backend·DB 인터페이스를 통합 제공
  2. 어떤 데이터든 같은 형식으로 주고받게 하는 인터페이스 표준화 공통 모듈
  3. 연동 결과를 이력·실패 기록으로 남기고, 실패 건은 이벤트를 다시 발생시켜 재처리
4결과

EAI 도입 후 인터페이스 장애 0건(고객사 네트워크·방화벽 이슈 제외). 이후 LOGION도 Kafka 이벤트와 EAI를 거쳐 기간계·고객사 시스템과 연동했습니다.

인터페이스 장애

EAI 도입 후, 고객사 네트워크·방화벽 이슈 제외

개념도. 솔루션 A·B·C는 예시입니다.

배운 점

연동 장애를 없애는 것만큼, 실패했을 때 어느 구간에서 멈췄는지 바로 가릴 수 있는 기록이 중요했습니다. 이후 EAI를 거친 LOGION 연동이 끊겼을 때도 연계 이력과 EAI 로그를 대조해 분류되지 않은 타임아웃 예외를 찾았고, 원인이 고객사 방화벽 정책 변경이라는 것을 가려냈습니다. 인터페이스 장애 0건에 '고객사 네트워크·방화벽 이슈 제외' 단서를 붙이는 이유입니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

CASE 02 · 스트리밍처리

배치 연계를 Kafka 이벤트로: '다시 처리할 수 있는 큐' 고르기 초안

1문제 상황

Spring Batch·Scheduler·DB 배치잡으로 묶인 연계 처리를 메시지 큐 기반으로 바꾸는 일은 선진·아이디에스앤트러스트·로지스올에서 거듭 맡은 과제였습니다. 기간계에서도 거래 한 건이 여러 연계 시스템으로 전달되어야 했고, 실패한 데이터는 다시 처리할 수 있어야 했습니다.

2원인 분석

정해진 시각에 모아서 도는 배치는 연계 대상이 늘 때마다 처리를 덧붙여야 했고, 실패한 건을 다시 보내려면 별도 경로가 필요했습니다.

3해결 과정
  1. 판단 기준 두 가지: 이벤트 하나를 여러 연계 시스템으로 넓힐 수 있는가, 같은 데이터를 다시 처리할 수 있는가
  2. 후보 Kafka·RabbitMQ·Redis 비교 후 Kafka 채택
  3. 시퀀스·ID 기반 메시지 키 정책으로 처리 순서 보장과 중복 방지(멱등성)
  4. 파티션 단위로 처리되는 특성을 고려해 필요한 범위에만 도입
4결과

기간계 Kafka 일 평균 8만 건 트랜잭션 처리

숫자로 본 변화

Kafka 일 평균 트랜잭션
8만 건
기간계 기준

가설을 하나씩 버린 과정

  1. 1
    기존 배치·스케줄러 유지Spring Batch·Scheduler·DB 배치잡으로 정해진 시각에 모아 처리
    이벤트 하나를 여러 연계 시스템으로 넓히기 어렵고, 재처리 경로를 따로 만들어야 함
  2. 2
    Redis Pub/Sub발행·구독 기능 제공
    Redis는 가벼운 상태 저장 용도로 역할을 먼저 정해 두어 큐 후보로 검토하지 않음
  3. 3
    RabbitMQ큐에서 처리되면 메시지가 사라지는 구조
    재처리를 하려면 별도 로직을 만들어야 해서 제외
  4. 4
    Kafka토픽 로그에 메시지를 일정 기간 보관, 컨슈머 오프셋 조정, 여러 컨슈머 그룹이 같은 이벤트 활용
    채택: 기간계 일 평균 8만 건 처리
배운 점

큐를 고르는 기준은 '이벤트 하나를 여러 시스템으로 넓힐 수 있는가'와 '실패한 데이터를 다시 처리할 수 있는가' 두 가지였습니다. 파티션 단위로 처리되는 Kafka의 특성 때문에 모든 처리를 올리지 않고 순서와 재처리가 필요한 범위에만 둔 것도 같은 판단입니다.

CASE 03 · 마이그레이션

서버에 묶인 파일을 Amazon S3 · Java NIO로 이관 초안

1문제 상황

모놀리스 시절 파일은 파일 서버에서 다뤘고, 파일 서버 문제가 운영 부담이었습니다.

2원인 분석

파일이 특정 서버의 저장 공간에 묶여 있으면, 서비스를 여러 개로 나누고 컨테이너로 배포할 때 같은 파일을 함께 쓰기 어렵습니다.

3해결 과정
  1. 파일 저장소를 Amazon S3 객체 저장소로 이관
  2. 파일 입출력을 Java NIO 기반으로 전환
  3. LightWeight 마이그레이션으로 기존 파일 이관
4결과

파일 서버 문제 해소. 서비스가 특정 서버의 디스크에 의존하지 않는 구조로 전환

개념도

배운 점

서비스를 나누기 전에 파일 같은 상태를 서버 밖으로 빼 두어야 컨테이너 배포와 무중단 전환이 단순해집니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.

CASE 04 · DevOps구축

배포를 Jenkins · Docker · K8s 무중단 CI/CD로 초안

1문제 상황

MSA로 나누면 배포 단위가 서비스 수만큼 늘어납니다. 전환 전에는 빌드와 반영을 사람이 서버마다 직접 처리했습니다.

2원인 분석

사람이 서비스마다 빌드와 반영을 반복하면 배포 시간과 실수할 여지가 서비스 수만큼 늘어나고, 반영하는 동안 서비스가 멈출 수 있습니다.

3해결 과정
  1. Jenkins로 빌드·시험·이미지 생성 자동화
  2. Docker·Docker Compose로 서비스 컨테이너화
  3. K8s에서 새 버전을 먼저 띄우고 확인한 뒤 전환하는 무중단 배포
  4. 스테이징에서 QA·현업 확인 후 운영 반영, 배포 일정은 미리 고지
  5. 파이프라인과 배포 환경을 포함한 DevOps 총괄
4결과

CI/CD 전환 완료. 다음 프로젝트인 LOGION에서는 자동 빌드·배포를 기획 단계부터 함께 설계했습니다.

개념도

배운 점

MSA 전환과 CI/CD는 따로 하는 일이 아니었습니다. 서비스를 나누는 순간 배포가 병목이 되므로, 자동화도 전환과 같은 일정에 넣어야 합니다.

이 부분은 근거 자료가 적어 기술 스택과 당시 환경을 바탕으로 쓴 초안입니다. 게시 전에 사실과 다른 곳이 없는지 확인해 주세요.
