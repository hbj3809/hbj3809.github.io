프로젝트 개요
무엇을, 왜 만들었나

pharmscope 에서 제약사 고객이 국내 대형 의약품 유통사의 매출 데이터를 보는 분석 API 20여 종을 Kotlin·WebFlux·R2DBC 로 설계·구현했습니다. 여러 제약사가 한 DB 를 함께 쓰므로 데이터 범위(스코프) 해석을 한 곳에 모아 조회·검색·다운로드 전 경로에 강제했고, 사전집계 대신 원본 직조회·서빙 풀 세션 튜닝·응답 캐시로 서빙했습니다. 오픈 전 실사용에서 나던 30초 타임아웃은 IO 대기 계측으로 인덱스 선두 컬럼 오배치에 따른 버퍼 축출을 찾아, 앱 코드 변경 없이 콜드 조회를 11.9초에서 1.5초로 줄였습니다.

개요배경·목표·역할

pharmscope 는 제약사 고객이 국내 대형 의약품 유통사의 출고·매출 데이터를 웹에서 보는 분석 서비스입니다. 고객사가 그동안 메일 엑셀로 받던 자료를 대시보드·출고 분석·시장 분석·제품 검색·다운로드로 바꾸는 서빙 API 를 맡았습니다. 여러 제약사가 한 서버와 DB 를 함께 쓰기 때문에 '자기 데이터만 보이게'와 '월 파티션 대형 원본을 빠르게 읽게'가 처음부터 두 축이었습니다.

  • 배경: 메일 엑셀로 받던 유통 매출 자료를 웹 분석 화면으로 전환
  • 목표: 고객사별 데이터 범위 보장 + 대형 원본 직조회의 응답 시간 확보
  • 규모: 분석 API 20여 종(개통 시 22종), 서비스 개통 뒤에도 기획 QA 반영 계속
  • 내 역할: 서빙 API 설계·구현, 성능 진단·튜닝 전담(Claude Code 협업)
  • 다른 사람 몫: 화면 정책(기획), 화면 구현(FE). 원천 수집·전처리는 별도 프로젝트로 진행

아키텍처

기존 백엔드에 매출 도메인 모듈로 합류해 배포 단위를 늘리지 않았습니다. 요청은 인증 → 스코프 해석 → 기간 정책 → 응답 캐시를 거치고, 캐시에 없을 때만 서빙 전용 읽기 풀로 매출 DB 를 직접 집계합니다. 새벽 파이프라인은 고객 조회용 인덱스를 미리 데운 뒤 공개 시각을 남기고, 이 시각이 캐시 키에 들어가 새 데이터에서는 자연스럽게 새로 계산됩니다.

핵심 처리 흐름요청 한 건이 지나는 길

회사 식별자는 요청 본문이 아니라 JWT 에서만 받습니다. 스코프(매입처 × 제외·지정 제품)는 요청마다 새로 해석하고, 그 요약값(스코프 지문)을 캐시 키에 넣어 매핑이 바뀌면 바로 새 계산이 되게 했습니다. 같은 키 요청이 동시에 오면 첫 요청만 DB 를 읽고 나머지는 그 결과를 함께 씁니다.

데이터 모델(개념)

실제 테이블 이름이 아닌 개념 모델입니다. '누가 무엇을 볼 수 있나'는 따로 저장하지 않고, 조회 시점에 매핑과 제품 조건에서 계산합니다. 주 매입처는 제외 제품을 빼고, 첨부 매입처는 지정한 제품만 범위에 넣습니다. 매출 원본은 월 단위 파티션이라 모든 쿼리에 기간 범위를 걸어 필요한 달만 읽습니다. 시장 분석은 일별 ATC 집계를 쓰고, 자사 외 금액은 익명 합계로만 보여 줍니다.

설계 결정왜 이렇게 골랐나

사전집계 대신 원본 직조회

가장 큰 고객사 12개월을 조회 기준별로 미리 묶어 봐도 행이 1.28배밖에 줄지 않아, 집계표를 따로 운영하는 비용이 이득보다 컸습니다. 대신 모든 쿼리에 월 파티션 범위를 걸고 서빙 전용 풀의 세션 설정(JIT 끄기·정렬 메모리)을 조정해 최대 고객사 12개월 KPI 를 4.5초에서 0.94초로 줄였습니다. 이후 묶는 기준을 바꿔 전 고객사로 다시 재니 3.34배여서, 사전집계는 착수 조건을 정해 보류 중입니다.

스코프는 저장하지 않고 조회 시점에 계산

회사 식별자는 JWT 에서만 받고, 매입처 매핑과 제외·지정 제품 조건을 요청마다 WHERE 로 붙입니다. 고객사별 복제 데이터가 없어 범위가 어긋날 곳이 줄고, 매핑을 바꾸면 다음 요청부터 반영됩니다. 조회·제품 검색 후보·다운로드가 같은 해석 한 곳을 지나고, 나중에 분석 엔진을 바꿔도 이 로직은 그대로 옮길 수 있습니다.

캐시 키에 공개 시각과 스코프 지문

데이터는 정해진 때에만 공개되므로 공개 시각을 키에 넣으면 따로 지우지 않아도 새 데이터에서 새 키가 됩니다. 스코프 지문을 넣어 매핑이 바뀌면 바로 새로 계산하고 다른 고객사와 섞이지 않게 했습니다. 같은 쿼리 동시 16건이 8.4초까지 쌓이는 것을 실측한 것이 도입 근거입니다.

캐시는 미리 채우지 않음

미리 채운 키가 고객이 실제로 보낼 기간·조건과 맞을지 알 수 없고, 채우는 일 자체가 공개 직후 DB 부하를 늘립니다. 대신 공개 직전에 고객 조회용 인덱스만 DB 버퍼로 미리 읽어 첫 계산을 빠르게 했습니다.

컬럼형 DB 보다 PostgreSQL 튜닝 먼저

ClickHouse 도입(추정 36~57 사람-일)과 PostgreSQL 튜닝(추정 약 1.5 사람-일)을 비교했고, 지연의 원인은 엔진 한계가 아니라 튜닝되지 않은 설정과 인덱스였습니다. 도입 판단 기준도 '튜닝을 마친 뒤에도 남는 지연'을 전제로 다시 썼습니다.

Kafka 는 쓰지 않음

이전 회사들에서는 거의 모든 프로젝트에 Kafka 를 썼지만, 이 서비스는 데이터가 일 배치로 들어오고 읽기가 대부분인 조회 워크로드라 실시간 스트림이 필요하지 않다고 판단했습니다. 익숙한 도구보다 워크로드 성격을 먼저 봤습니다.

인덱스는 운영 DB 에 먼저, 마이그레이션은 통과만

앱 기동 때 도는 마이그레이션이 데이터가 있는 표에 잠금 인덱스를 만들면 기동 실패가 반복될 수 있습니다. 그래서 운영 DB 에 CONCURRENTLY 로 먼저 만들고, 마이그레이션 파일은 '이미 있으면 통과'로 두고 선적용 순서를 파일에 적었습니다.

30초 상한과 503 계약

무거운 조회 하나가 다른 고객의 연결까지 붙잡지 않도록 서빙 세션에만 30초 상한을 걸었습니다. 넘으면 '조회 기간을 줄이거나 잠시 후 다시 시도'를 안내하는 503 시간 초과 응답으로 계약해, 화면이 실패를 구분해 보여 줄 수 있게 했습니다.

사전집계 vs 직조회결정 흐름

처음 설계 때와 성능 문제를 만났을 때 같은 질문을 두 번 했습니다. '더 큰 장치를 들이기 전에 지금 구조를 끝까지 재 봤는가.' 두 번 모두 실측으로 답을 정했고, 아래 차트는 두 번째 판단에 쓴 작업량 추정입니다.

응답 캐시와 서빙 보호 장치

응답 캐시는 Redis 가 아니라 API 파드 메모리에 있고, 키 칸이 하나라도 다르면 새로 계산합니다. 실패하거나 30초를 넘긴 계산은 저장하지 않아, 같은 조건을 다시 눌러도 잘못된 빈 결과가 남지 않습니다. 캐시 말고도 무거운 요청이 다른 고객을 막지 않도록 몇 겹의 장치를 두었습니다. 아래 차트는 목록 API 에 응답 캐시와 프리필터를 붙이기 전후의 dev 부하 시험 처리량입니다.

  • 응답 캐시: 키 = 화면 종류·회사·스코프 지문·데이터 공개 시각·요청 값(이후 동의 철회 처리 세대도 추가), 키 단위 single-flight, 로더와 요청 수명 분리(요청이 끊겨도 계산은 끝까지)
  • 미리 데우기: 새벽·낮 공개 직전 고객 조회용 인덱스를 DB 버퍼로 다시 읽기(전처리 대량 스캔이 밀어낸 캐시 복구), 응답 캐시는 비운 채로
  • 부하 상한: 서빙 세션 30초, 서빙 전용 읽기 풀 크기 제한, 다운로드는 계약사당 시간당 횟수·파드당 동시 생성·행 수 상한(넘으면 429 와 재시도까지 기다릴 시간 안내)
  • 자동 중지(데이터 보정 백오피스와 연계): 낮 데이터 보정을 반영하는 동안 고객 조회가 시간 초과로 실패하면 낮 예약 처리를 스스로 멈추고, 사람이 원인을 확인한 뒤 재개
  • 관찰: 커넥션 풀 게이지·캐시 적중·합류 대기·미스·데이터 경과 시간 지표와 Grafana 서빙 대시보드

성과

조회 시간은 측정 조건이 서로 다르므로 조건을 이름에 함께 적었습니다. 콜드는 DB 를 재기동해 버퍼가 빈 상태에서 잰 값이고, KPI 는 서빙 풀 세션 튜닝 전후의 웜 벤치입니다. 같은 쿼리를 반복하는 벤치는 웜만 재므로, 콜드는 손대지 않은 고객사 × 기간 조합이나 DB 재기동 직후로 강제하고 합격 조건에 p95 뿐 아니라 최댓값과 30초 컷 0건을 넣었습니다.

  • 같은 쿼리의 콜드/웜 격차 9.7배→1.6배, 시장분석 조회 실행시간의 84%였던 IO 대기를 분리해 원인 규명
  • 숨은 스코프 확인 쿼리: 처방 전 운영 평균 14.3초(최대 20.8초) → 완전 웜 실행 계획 기준 약 4초에서 3.4ms
  • dev 부하 시험(20계정 동시): 목록 API 5xx 17건→0, 웜 rps 18.8→93.2(약 5배), 건수 쿼리 14.5초→1.0~1.3초(유휴 DB 실행 계획)
  • 검토되던 ClickHouse 도입(추정 36~57 사람-일)을 PostgreSQL 튜닝(추정 약 1.5 사람-일)으로 대체
  • 받은 성능 개선 로드맵에서 과잉 처방 5건을 실측 근거로 기각
  • 남은 과제도 기록: 콜드를 없앤 뒤에도 웜 지연과 다수 동시 사용 대기는 남아 후속 인덱스·배치 간섭 차단으로 이어 감

CASE 01 · 성능튜닝

분석 조회 30초 타임아웃 — 'CPU 포화'가 아니라 버퍼 축출

1문제 상황

pharmscope 오픈 전 실사용에서 시장분석·지역·채널 화면이 30초 상한에 걸려 실패하고, 출고 추이도 크게 느렸습니다. 같은 쿼리를 반복하는 벤치는 웜 1.4초라 실사용과 어긋났고, 대안으로 컬럼형 DB(ClickHouse) 도입이 검토되고 있었습니다.

2원인 분석

일별 ATC 집계 테이블의 기본키 선두 컬럼이 조회 축(매입처)과 어긋나, 시장분석 조회가 인덱스 전체를 읽고 극히 일부만 썼습니다. 이 조회 한 번이 버퍼풀을 통째로 밀어내 관계없는 화면까지 늘 콜드가 되는 구조였습니다. 전날 'DB CPU 포화'로 본 제 판단은 IO 대기를 잘못 읽은 것이었습니다.

3해결 과정
  1. track_io_timing 을 켠 EXPLAIN (ANALYZE, BUFFERS)로 IO 대기와 CPU 를 분리, 시장분석 조회 실행시간의 84%가 IO 대기임을 확인
  2. 손대지 않은 고객사 × 기간 조합과 DB 재기동 직후 상태로 콜드를 강제해 콜드와 웜을 따로 측정
  3. 컨테이너 메모리·CPU 실측으로 'CPU 포화' 가설을 배제하고 전날 판단을 스스로 정정
  4. 조회 축에 맞춘 커버링 인덱스 2종을 운영 DB 에 잠금 없이(CONCURRENTLY) 먼저 적용, 마이그레이션 파일은 통과만
  5. Index Only Scan 이 며칠 뒤 조용히 원위치되지 않도록 테이블 단위 autovacuum 임계 조정, IO 동시성·버퍼 크기·DB 파드 자원 재조정
  6. 버퍼를 키운 부작용(대량 스캔 보호가 꺼져 전처리가 캐시를 덮음)을 pg_buffercache 로 실측하고, 전처리 끝에 인덱스 미리 데우기 단계 추가
  7. 컬럼형 DB 도입 기준을 '튜닝 완료 후에도 남는 지연' 전제로 다시 쓰고, 진단 순서를 운영 문서로 정리
4결과

앱 코드 변경 없이 콜드 조회가 11.9초에서 1.5초(월별 기관수 12개월), 11.7초에서 0.18초(ATC 제품수)로 줄었고, 콜드/웜 격차는 9.7배에서 1.6배가 됐습니다. 검토되던 컬럼형 DB 도입(추정 36~57 사람-일)은 PostgreSQL 튜닝(추정 약 1.5 사람-일)으로 대체했습니다. 다만 웜 지연과 다수 동시 사용 대기는 남아 후속 과제로 넘겼습니다.

CASE 02 · 성능검증

받은 성능 개선 로드맵 실측 검증 — 과잉 처방 5건 기각과 숨은 14.3초 쿼리

1문제 상황

콜드 문제를 고친 뒤에도 웜 지연과 동시 사용 대기가 남은 상태에서, DB 권한 분리·읽기 복제본·주기 점검 작업 등을 담은 성능 개선 로드맵을 받았습니다. 그대로 따르면 수십 사람-일이 들고 새 장애점이 생길 수 있었습니다.

2원인 분석

로드맵은 병목을 실측 없이 가정하고 있었고, 제 분석도 병목을 정렬로 잘못 짚었으며 사전집계 압축률은 한 고객사 값을 전체로 외삽한 추정(설계 때 잰 1.28배와는 별개)에 기대고 있었습니다. 실제 병목은 처리하는 행 수였습니다. 관측 중에는 특정 제품을 고를 때만 모든 월 파티션을 heap 으로 읽는 스코프 확인 쿼리가 숨어 있었는데, 대표코드 축 인덱스가 없었던 탓이고 직전 쿼리 개선 작업이 들인 회귀였습니다.

3해결 과정
  1. EXPLAIN 을 단계별로 분해해 병목을 정렬이 아닌 처리 행 수로 재규명
  2. 전 고객사 12개월 실측으로 사전집계 압축률을 3.34배로 정정(한 고객사 값을 전체로 외삽했던 별도 추정을 바로잡음. 설계 때 잰 1.28배는 묶는 기준이 다른 별개 측정)
  3. pg_stat_statements·Prometheus 관측으로 커넥션 풀 대기 가설 기각
  4. 로드맵 처방 5건을 실측 근거로 기각하고 근거와 측정 절차를 문서로 남김
  5. 관측 중 운영 평균 14.3초(최대 20.8초) 스코프 확인 쿼리를 찾아 원인(대표코드 축 인덱스 부재) 규명
  6. 파티션 테이블에는 CONCURRENTLY 를 바로 쓸 수 없어 파티션별 CONCURRENTLY → ON ONLY → ATTACH 3단계 무락 경로로 인덱스 2종 적용, 무효 인덱스 0 확인
  7. 인덱스 빌드가 버퍼 캐시를 덮는 부작용을 실측해 prewarm 으로 복구
  8. 처방 순서를 인덱스 → 배치 버퍼 오염 차단 → 사전집계(보류)로 재배치
4결과

과잉 처방 5건을 기각해 불필요한 투자와 새 장애점을 피했습니다. 숨은 쿼리는 완전 웜 실행 계획 기준 약 4초에서 3.4ms 로 줄었습니다(처방 전 운영 평균 14.3초와는 측정 기준이 다름). 사전집계는 착수 조건을 정해 보류했습니다.

월 파티션 대형 테이블에 쓰기 잠금 없이 인덱스를 거는 3단계 절차와 뒤처리

배운 점

받은 처방도, 제 판단도 실측 전에는 가설입니다. 숨은 회귀는 제 직전 개선 작업에서 왔습니다. 개선을 배포한 직후에도 쿼리 통계를 다시 봐야 합니다. 큰 장치를 더하기 전에 가장 싸고 이득이 큰 처방(인덱스)부터 둡니다.

CASE 03 · 성능개선

동시 요청이 몰릴 때 — 응답 캐시와 20계정 부하 게이트

1문제 상황

같은 쿼리를 동시에 16건 보내면 8.4초까지 쌓였고, 같은 쿼리를 반복하는 벤치로는 여러 고객이 동시에 쓸 때 실패가 나는지 판정할 기준이 없었습니다.

2원인 분석

요청마다 같은 집계를 새로 계산해 동시 요청이 대기열로 쌓였습니다. 목록 API 는 캐시 없이 건수·페이지 대형 쿼리 두 개를 동시에 보냈고, 원천 연결 조인 키에 인덱스가 없어 원천 12개월을 병렬 풀스캔하면서 읽기 풀이 포화돼 30초 상한에 걸렸습니다.

3해결 과정
  1. 응답 캐시 도입: 키 = 화면·회사·스코프 지문·데이터 공개 시각·요청 값, 키 단위 single-flight, 로더와 요청 수명 분리
  2. 보관 상한을 늘리기 전에 '옵션을 안 바꾸면 하루 내내 같은 데이터를 보는가'를 검토해, 달력만으로 바뀌는 기준월·기간·잠정치가 키에 빠진 버그를 배포 전 수정
  3. Python 부하 하네스 구축: 스코프 규약을 지키는 실제 파라미터 사전, 다계정 실동시 부하, 5xx·timeout·인증 실패 0 을 통과 조건으로 둔 하드 게이트
  4. 20계정 동시 부하에서 목록 API 5xx 를 발견하고 실행 계획으로 원천 풀스캔 확인
  5. 목록 응답 캐시(초과 페이지는 쿼리 없이 빈 응답), 새 인덱스 없이 원천 쪽 매입처 프리필터, 파이프라인 코드·행수 대사·실데이터 표본 전수 대조로 결과 동일성 확인
  6. 그래도 남는 컷은 원인 체인에서 쿼리 취소를 판별해 503 시간 초과로 계약, 건수와 첫 페이지를 한 쿼리로 병합
  7. 캐시 미리 채우기 안과 고객사 부분집합 복사 테이블 안은 검토 후 기각하고 근거를 문서화
4결과

dev 부하 시험 재검증을 통과했습니다(5xx·timeout 0). 목록 API 5xx 는 17건에서 0, 웜 rps 는 18.8에서 93.2(약 5배), 건수 쿼리는 14.5초에서 1.0~1.3초(유휴 DB 실행 계획)가 됐습니다. 이후 이 목록 API 는 화면에서 쓰지 않는 것으로 확인됐지만, 30초 상한의 503 계약은 서빙 API 공통 규약으로 남았습니다.

CASE 04 · 장애대응

로컬에서 재현되지 않던 엑셀 다운로드 장애 2건

1문제 상황

매출 엑셀 다운로드를 배포하자 로컬에서는 재현되지 않는 500 오류가 두 가지 났습니다. 하나는 대용량 상세 엑셀을 받는 도중의 메모리 부족이었고, 다른 하나는 시트를 만드는 순간의 폰트 오류였습니다.

2원인 분석

① 컨테이너 이미지 빌드 도구가 JVM direct 메모리 상한을 매우 작게 잡았고, 그 작은 영역을 웹 서버·두 DB 드라이버 체인·Redis 클라이언트가 나눠 쓰다 대용량 스트림에서 부족해졌습니다. ② 엑셀 라이브러리가 시트를 만들 때 폰트 시스템을 불러오는데, 서버 이미지에 폰트가 없었습니다.

3해결 과정
  1. 같은 요청이 로컬에서 정상인 것을 확인하고, 로컬과 컨테이너의 차이(JVM 옵션·이미지 구성)를 목록화해 범위를 좁힘
  2. JVM 옵션으로 direct 메모리 상한을 명시
  3. 폰트 시스템이 없어도 진행하도록 하는 설정을 앱 기동 시점에 한 번 켬
  4. 엑셀은 행을 임시 파일에 흘려 작은 청크로 보내는 SXSSF 구조를 유지해 힙에 쌓지 않음
  5. 코드성 컬럼은 텍스트 서식으로 지정해 긴 코드의 과학표기와 우편번호 앞자리 0 탈락 방지
4결과

두 장애 모두 원인을 규명해 처방했고, 이후 dev 부하 시험의 엑셀 요청에서는 5xx 가 나지 않았습니다. 다운로드에는 계약사당 시간당 횟수·파드당 동시 생성 상한과 감사 이력을 함께 두어, 대용량 요청이 몰려도 다른 고객의 조회를 막지 않게 했습니다.

    확인 — JVM 옵션으로 상한 명시
  3. 3
    원인 2 · 서버 이미지에 폰트 없음시트 생성 때 폰트 시스템을 불러오다 실패
    확인 — 기동 시 폰트 누락 무시 설정

로컬 재현이 안 될 때 실행 환경 차이부터 좁혀 간 순서

배운 점

컨테이너 이미지의 기본값(메모리 계산·폰트)도 코드 밖의 의존성입니다. 로컬에서 재현되지 않으면 코드보다 실행 환경의 차이를 먼저 목록으로 만듭니다.

정리:이 프로젝트에서 남긴 것

느린 원인을 짐작으로 고치지 않고 IO 대기와 CPU, 콜드와 웜, 동시 부하를 따로 잰 뒤, 큰 장치보다 인덱스·설정 조정을 먼저 골랐습니다. 받은 로드맵과 제 첫 판단도 실측으로 다시 확인해 맞지 않는 것은 버렸고, 진단 순서와 버린 이유는 문서로 남겼습니다.
