프로젝트 개요
무엇을, 왜 만들었나

식품·축산 그룹 계열사에서 외주 솔루션으로 운영되던 운송·창고 관리 시스템(TMS/WMS)을 Spring Boot·TreeGrid·Oracle 로 직접 구축했습니다. 유지보수는 SAP RFC 연동 개선만 SI 협력사(외주 40%)에 맡기고 애플리케이션 유지보수는 제가 직접(60%) 하는 체계로 바꿔 연간 4,800만원을 줄였습니다. 같은 기간 육가공 사업부 MES(작업 지시·실적 등 전 과정)와 전자계약도 시스템별로 따로 자체 개발했고, 전자계약은 외주 구축비 3,000만원을 자체 API 개발로 대신했습니다. 퇴사(2024.04) 시점에 TMS/WMS·MES·전자계약 모두 운영 중이었고, 입출고·배차·재고 흐름을 직접 구조화한 경험은 이후 LOGION 설계의 바탕이 됐습니다.

개요외주에 묶인 물류 시스템을 안으로

식품·축산 그룹 계열사인 선진의 운송 관리(TMS)·창고 관리(WMS) 시스템은 외주 솔루션으로 운영되고 있었습니다. 유지보수 비용이 해마다 나가고, 현업이 요청한 커스터마이징은 외주를 거치느라 늦게 반영됐습니다. 전자계약 역시 전자서명 서비스 업체에 연동 구축을 맡기면 3,000만원이 드는 일이었습니다. 그래서 TMS/WMS·MES·전자계약을 시스템별로 자체 구축하고, 유지보수는 SAP RFC 연동 개선만 SI 협력사에 맡기고 애플리케이션은 제가 직접 맡는 체계로 바꿨습니다. 퇴사(2024.04) 시점에는 모두 운영 중이었습니다.

  • 기간: 2023.03 ~ 2024.04 (같은 기간 전사 CI/CD·SSO·로그 관제 구축 병행)
  • 소속: 기술연구소 디지털혁신센터 · 대리
  • 역할: SAP 영역을 제외한 TMS/WMS·MES·전자계약 설계·개발 단독 수행
  • 구성: TMS/WMS·MES·전자계약을 시스템별로 따로 구축, 업무 DB 는 Oracle
  • MES: 육가공 사업부 MES 공정 담당, 작업 지시·실적을 비롯한 MES 전 과정 개발
  • 기여도: TMS/WMS 90%(SAP RFC 연동 개선은 SI 협력사 몫), 전자계약 100%
  • 목표: 외주 유지보수 비용 절감 + 커스터마이징 대응 지연 해소
  • 다른 사람 몫: SAP 측 개발(SAP 담당), 전환 뒤 SAP RFC 연동 개선(SI 협력사, 유지보수 분담 40%)
  • 결과: 퇴사(2024.04) 시점 TMS/WMS·MES·전자계약 모두 운영 중

전체 구성

TMS/WMS·MES·전자계약은 하나의 앱으로 묶지 않고 시스템별로 따로 만들었고, 업무 DB 는 Oracle 을 썼습니다. SAP·SFA/CRM·외부 전자서명 서비스와의 연동은 인터페이스 공통 모듈 한곳으로 모았고, SAP 와는 RFC 로 주고받았습니다. 로그인은 같은 시기 구축한 전사 SSO 를, 배포·로그는 같은 시기 구축한 CI/CD·ELK 관제를 함께 썼습니다.

배차·운송·입출고 흐름

주문이 확정되면 출하 지시 → 운송 주문 → 배차 → 출고 → 도착 확인 → ERP 반영 순서로 흐릅니다. 모든 외부 연동은 인터페이스 모듈을 거치고, 연동이 실패해도 출고 데이터는 남긴 채 실패 이력을 근거로 다시 보냅니다.

출고 상태 전이

출고 상태는 출고(루트) 한 곳에서만 바뀌도록 했습니다. 연동 결과나 관리자 결정도 출고를 거쳐 상태와 이력을 함께 남깁니다.

개념 데이터 모델

운송 주문·배차·차량과 창고·입고·재고를 나누고, 출고는 품목·상태 이력·연동 기록을 거느리는 묶음(애그리거트)으로 잡았습니다. 실제 테이블 이름이 아닌 개념 이름입니다.

설계 결정왜 이렇게 만들었나

기술을 고르기 전에 업무 경계와 데이터의 주인을 먼저 정했습니다.

업무 성격별로 도메인부터 분리

출고·입고·재고는 같은 물류 시스템 안에 있어도 업무 맥락이 다릅니다. 기능을 만들기 전에 경계를 먼저 나눠, 기능이 늘어도 어디에 무엇을 둘지 흔들리지 않게 했습니다.

출고를 하나의 묶음(애그리거트)으로

출고 품목은 출고 없이 생기지 않고, 이력·출력물도 출고 한 건을 기준으로 관리됩니다. 연동 결과나 관리자 결정으로 상태가 바뀔 때도 하위 데이터를 함께 처리해 출고 업무의 무결성을 지켰습니다.

연동은 공통 모듈 한곳으로

SAP 모듈과 외부 인터페이스가 기능마다 흩어지지 않도록, 어떤 데이터든 같은 형식으로 주고받는 연동 공통 모듈을 만들었습니다.

유지보수 분담 — 연동은 협력사, 애플리케이션은 직접

유지보수를 외주에 모두 맡기지 않고 나눠 맡았습니다. SAP 와 맞닿은 RFC 연동 개선은 SI 협력사(40%)가, 화면·업무 로직 등 애플리케이션 유지보수는 제가 직접(60%) 맡는 분담입니다. 현업의 화면·업무 변경 요청은 애플리케이션 쪽에서 내부가 바로 처리할 수 있어 외주 일정을 기다리지 않게 됐고, 연간 유지보수 비용 4,800만원을 줄였습니다.

외주 구축 대신 자체 API

전자계약은 전자서명 서비스 업체에 연동 구축비 3,000만원을 주는 대신, 계약 API 를 직접 개발하고 인터페이스 공통 모듈로 연동해 외주비를 전액 절감했습니다.

전자계약 서명 흐름

전자계약은 영업 담당이 대리점·거래처와 맺는 판매 계약에 쓰는 시스템으로, 사내 계약 데이터와 외부 전자서명 서비스를 잇는 계약 API 를 직접 만들었습니다. 전자서명 서비스에 보내는 서명 요청과 돌아오는 완료 알림은 인터페이스 공통 모듈을 거칩니다. 서명이 끝나면 완료 알림을 받아 계약 상태를 바꾸고, 서명본을 사내에 내려받아 보관합니다.

MES 생산 흐름육가공 사업부

육가공 사업부의 MES 공정을 맡아, 작업 지시·실적을 비롯한 MES 전 과정을 직접 만들었습니다. MES 도 TMS/WMS 와 따로 만든 시스템이고 업무 데이터는 Oracle 에 둡니다. 아래 흐름과 단계 설명은 육가공 MES 의 표준 흐름에 맞춰 정리한 것으로, 단계 이름은 업계에서 일반적으로 쓰는 이름을 따랐습니다.

  • 생산 계획 수신: ERP(SAP) 의 생산 계획을 받아 MES 작업의 출발점으로 삼음
  • 작업 지시: 계획을 라인·품목·수량 단위의 작업 지시로 내림
  • 원료육 투입·이력(로트): 투입한 원료육을 로트로 묶어, 어떤 원료가 어떤 제품이 됐는지 거슬러 찾을 수 있게 연결
  • 공정별 실적: 가공·포장·계근 단계마다 실적을 남기고, 계근으로 실제 중량을 확정
  • 품질 검사: 검사 결과를 공정 실적과 함께 기록
  • 완제품 입고·출하 연계: 검사를 마친 완제품을 입고 처리하고 출하로 넘김
  • 실적 집계·SAP 반영: 작업 지시별 실적을 집계해 인터페이스 공통 모듈을 거쳐 SAP 에 반영

성과외주에서 자체 구축으로 바꾼 비용

이 프로젝트에서 줄인 외주 비용은 연간 유지보수 4,800만원과 전자계약 구축비 3,000만원(일회성)으로 합계 7,800만원입니다. 선진 재직 중 외주→자체 전환으로 줄인 비용을 모두 더하면 2억 2,800만원이며, 견적 기준·연간·일회성 금액이 섞인 합입니다.

외주 TMS/WMS 의 유지보수 비용과 느린 커스터마이징

1문제 상황

운송·창고 관리 시스템이 외주 솔루션이라 유지보수 비용이 해마다 나가고, 현업의 화면·업무 변경 요청은 외주를 거쳐 늦게 반영됐습니다.

2원인 분석

시스템이 외주 솔루션이어서 작은 변경과 유지보수까지 모두 외주 일정과 비용에 묶여 있었습니다.

3해결 과정
  1. 출고·입고·재고 등 업무 성격별로 도메인을 먼저 나누고 출고를 루트 애그리거트로 설계
  2. Spring Boot·TreeGrid 기반으로 TMS/WMS 를 직접 구축(SAP 영역 제외)
  3. SAP·외부 인터페이스는 연동 공통 모듈로 표준화
  4. 유지보수는 SAP RFC 연동 개선만 SI 협력사(외주 40%)에 맡기고, 애플리케이션 유지보수는 직접(본인 60%) 맡는 체계로 전환

CASE 02 · 도메인모델링

출고 한 건에 얽힌 품목·이력·출력물·연동·상태의 무결성

1문제 상황

출고 한 건에는 품목, 이력, 출력물, 내부·외부 연동, 상태가 함께 얽혀 있습니다. 연동 결과나 관리자 결정으로 상태가 바뀔 때 일부만 바뀌면 출고 데이터가 서로 어긋날 수 있었습니다.

2원인 분석

하위 데이터를 각자 따로 만들고 바꿀 수 있으면 상태 변경 규칙이 여러 곳에 흩어집니다.

3해결 과정
  1. 출고를 루트 애그리거트로 정의
  2. 출고 품목·이력·출력물·내부 연동·외부 연동·상태를 하위로 묶음
  3. 출고 품목은 출고 없이 단독으로 생성할 수 없게 제한
  4. 상태 변경은 루트를 거쳐 하위 데이터와 일괄 처리
4결과

출고 업무 규칙이 한곳에 모여 무결성 확보. 같은 원칙을 이후 LOGION 출고 설계에도 적용(수치 지표는 없음)

출고 애그리거트 구조(개념도)

배운 점

애그리거트 경계를 먼저 정하면 '누가 상태를 바꿀 수 있는가'가 코드 구조로 드러난다는 것을 배웠습니다.

CASE 03 · 비용절감

전자계약 외주 구축비 3,000만원

1문제 상황

계약 업무를 전자계약으로 바꾸려 했으나, 전자서명 서비스 업체에 연동 구축을 맡기면 3,000만원이 드는 상황이었습니다.

2원인 분석

실제로 필요한 것은 사내 계약 데이터와 외부 전자서명 서비스를 잇는 연동이었는데, 이를 통째로 외주 구축 범위로 맡기는 구조였습니다.

3해결 과정
  1. 계약 생성·서명 요청·완료 알림 수신·상태 관리 API 를 직접 설계
  2. 외부 전자서명 서비스와의 연동은 인터페이스 공통 모듈을 거치도록 구성
  3. 거래처·계약 정보는 사내 데이터에서 채워 넣도록 구성
  4. 서명 완료 알림을 받으면 계약 상태를 바꾸고 서명본을 사내에 내려받아 보관
  5. 사내 사용자 접근은 전사 SSO 로 통제
4결과

외주 구축비 3,000만원 전액 절감(일회성), 기여도 100%, 운영 전환 완료(퇴사 시점 운영 중)

숫자로 본 변화

전자계약 구축 외주비
3,000만원→전액 절감
업체 제시 비용·일회성

외주 구축안과 자체 개발 구조(개념도)

배운 점

외주 범위를 그대로 받기 전에 실제로 만들어야 하는 부분을 나눠 보면, 내부에서 감당할 수 있는 일이 보인다는 것을 배웠습니다.
