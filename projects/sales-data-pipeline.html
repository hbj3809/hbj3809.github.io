프로젝트 개요
무엇을, 왜 만들었나

국내 대형 의약품 유통사의 ERP 매출을 받아 제약사 분석 서비스 pharmscope 에 공급하는 데이터 파이프라인(수집 → 전처리 → 공개 → 서빙)을 AI 코딩 에이전트(Claude Code)와 함께 설계·구현했고, 그 작업을 주도했습니다. 새벽에만 호출할 수 있는 원천 API 와 약 2년 반 치 과거 파일을 원본 원장 하나로 모았습니다. 월 상태 원장·정본 서열·원장 대사를 둬서 몇 번을 다시 돌려도 결과가 같습니다. 2026년 9월부터는 정기 작업 7종이 매일 새벽 사람 손 없이 돌기 시작했습니다.

설계·구현 주도 · 스타트업 개발팀. 연동 API 개발은 유통사, 전처리 기준·검수는 현업 데이터 운영팀, 화면 기획은 기획팀이 맡음

개요배경·목표·역할

pharmscope 는 제약사 고객이 쓰는 의약품 유통 데이터 분석 서비스이고, 국내 대형 의약품 유통사의 ERP 매출을 원천으로 씁니다. 처음에는 원천에 연동 API 가 없었습니다. API 가 생긴 뒤에도 호출은 새벽 3시간 동안만 가능했습니다. 과거분 약 2년 반 치는 월별 수 GB 단위 JSON 파일로 따로 받았습니다. 유통사는 월마감 뒤에도 전월을 보정했고, 매입처마다 마감 시점이 달랐습니다. 명세는 진행 중에도 계속 바뀌었습니다.

목표는 두 가지였습니다. 하나는 수집부터 공개까지를 몇 번 다시 돌려도 결과가 같은 원장 구조 위에서 자동화하는 것입니다. 다른 하나는 실패한 행을 조용히 버리지 않는 것입니다.

  • 기간: 2026.06 ~ 현재, 운영 중
  • 내 역할: 설계·구현 주도. 연동 명세, 수집·백필·전처리·월마감 작업, 전용 DB·스케줄러 구축, 운영 경보
  • 다른 사람 몫: 연동 API 개발은 유통사, 전처리 기준과 검수는 현업 데이터 운영팀, 화면 기획은 기획팀
  • 이어지는 프로젝트: 매출 분석 서빙 API·성능 튜닝과 사내 데이터 보정·검수 백오피스는 별도 페이지
  • AI 활용: Claude Code 로 설계·구현. 자주 바뀌는 결정은 설계 정본 문서와 작업 메모리에 남겨 세션 사이에 이어 감. 주요 변경은 다중 에이전트 적대 리뷰를 거쳐 반영(파이프라인·API 주요 변경 5건에서 확정 결함 62건을 배포 전에 고침)

아키텍처원천 셋, 원장 하나

원천은 셋입니다. 유통사 ERP API(매출·재고·수신 설정), 과거 원본 파일, 공공 의약품·약국 마스터. 세 원천 모두 전용 PostgreSQL 의 원장으로 모입니다. 변환·검증·집계는 DB 안의 집합 SQL 이 맡고, Airflow 는 순서·재시도·시간 창만 관리합니다. 서빙 API 는 같은 DB 를 읽기 전용으로 읽습니다.

  • 전용 PostgreSQL 17: 매출·약품 마스터·스케줄러 메타 DB 를 서로 분리, 볼륨은 지워지지 않는 정적 볼륨
  • Airflow 3: 작업마다 파드를 띄우는 KubernetesExecutor, DAG 는 git push 뒤 git-sync 로 배포, 기본 관리자 계정 자동 생성은 끔
  • Argo CD·Sealed Secrets 로 GitOps 구성. 사내에 이미 있던 객체 저장소에는 원본 보관 공간과 그 공간 전용 접근 키만 따로 발급
  • 공공 의약품·약국 마스터 수집기는 다른 개발자가 만든 것을 넘겨받아 컨테이너로 만들고 매일 정례 실행으로 올림
  • 서빙 앱에 매출 DB 용 두 번째 마이그레이션·R2DBC 체인을 붙여 스키마를 코드로 관리
  • 플랫폼은 이후 AWS EKS 로 이관(별도 프로젝트 페이지)

새벽 체인단계마다 바뀌는 것

매일 새벽 정해진 작업이 차례로 돌고, 마지막 단계가 끝나야 '공개 완료 기록'이 찍힙니다. 고객 화면은 이 기록을 신호로 삼아 새 값을 보여 줍니다. 엑셀 다운로드는 원본을 바로 읽기 때문에 수집 직후부터 바뀝니다. 같은 데이터에 시계가 둘인 셈이어서, 고객 문의가 오면 이 차이부터 확인합니다.

  • DB 를 무겁게 쓰는 작업은 한 칸짜리 풀로 직렬화해 서로 DB 를 다투지 않게 하고, 실측 소요 시간을 바탕으로 새벽 시각표를 다시 확정
  • 두 시계: 엑셀은 원본 원장을 캐시 없이 읽어 수집 직후에 바뀌고, 화면은 공개 완료 기록 뒤 캐시 키가 바뀌면서 새 값을 보여 줌
  • 공개 완료 기록은 DB 행을 한꺼번에 바꾸는 장치가 아니라 '이제 새로 계산하라'는 신호. 전처리 확정과 공개 기록 사이에 옛 값과 새 값이 섞여 보이는 짧은 창이 있다는 점을 운영 문서에 남김
  • 수집 실패 뒤 긴 공백이 알림 없이 지나간 일을 계기로 Teams 지연 점검 경보 추가, 기존 경보 웹훅 형식을 재사용

하루치 수집다시 돌려도 같은 결과

전일분 수집은 대상일 데이터를 지우고 다시 넣습니다. 그래서 같은 날을 몇 번 다시 받아도 결과가 같습니다. 쓰기 전에는 잠금과 월 상태를 확인하고, 쓴 뒤에는 원천 총건수와 맞춰 보고 원장에 성공 또는 실패를 남깁니다.

  • HTTP 대기 시간을 긴 트랜잭션 밖에 두려고 페이지마다 커밋하고, 마지막에 원천 총건수로 대사
  • 연동 명세: 매출·재고·수신 설정 API 의 연동 컬럼 82개 영문 명세를 작성해 유통사 API 개발 기준으로 제공, 실호출로 명세와 실서버의 차이 3건 점검·2건 보정
  • 수신 설정 수집: 일부만 받은 데이터로 고객사 조회 범위가 통째로 바뀔 수 있는 위험을 자체 점검에서 발견, 페이지·건수 대사가 하나라도 어긋나면 실패로 처리하도록 엄격화하고 한 트랜잭션으로 전량 교체
  • 재고 수집: 원천이 업체·제품 조합의 유일성을 보장하지 않아 원천 행 번호를 붙여 모든 필드를 보존, 급감 가드·페이지 단위 커밋·중단 지점 재개
  • 원천 API 전체가 오류를 내던 기간에는 자동 실행을 끈 채 수집 작업별 최근 성공·경과 시간을 한 화면에서 보는 대시보드를 구성

개념 데이터 모델

실제 테이블·컬럼 이름 대신 개념 이름으로 다시 그린 모델입니다. 원본·정제·리젝트는 월 파티션입니다. 모든 쓰기의 앞뒤를 수집 원장과 월 상태 원장이 지킵니다.

  • 원본 한 행은 정제 매출과 리젝트 가운데 한쪽에만 들어감. '원본 = 성공 + 리젝트' 대사가 이 구조에 기댐
  • 월 상태 원장에 그 달을 마지막으로 확정한 경로(월마감본·과거 파일·전일분)를 기록해 정본 서열을 강제
  • 월마감 교체 때 행 지문으로 추가·삭제된 행을 남겨 '무엇이 바뀌었는지'를 데이터로 보관
  • 정보 제공에 동의하지 않은 매입처는 판정 식을 한 곳에 정의해 모든 인입 경로에서 승격 전에 거름
  • 계약사의 조회 범위는 매입처 단위로 해석되고, 서빙 API 가 조회 시점에 적용

전처리원본 = 성공 + 리젝트

ERP 원문에는 표준코드 결측, 의료기기 혼입, 자릿수가 다른 코드, 주소 표기 불일치, 행정구역 개편이 섞여 있어서 그대로 집계할 수 없었습니다. 실패한 행을 조용히 버리면 매출이 사라집니다. 그래서 매월 '원본 = 성공 + 리젝트' 항등식과 '한 행에 사유 하나' 규칙을 강제했습니다. 무엇을 리젝트할지는 현업 데이터 운영팀이 정했습니다. 저는 구현을 맡았고, 기준 초안에 빠져 있던 약품 매핑 단계를 보완했습니다.

  • 리젝트를 사유별로 전수 분해: 자릿수가 다른 코드는 의료기기 자체 바코드(정당한 리젝트)로 확정, 표준코드 결측분은 현업에 판정 요청
  • 주소 파서를 네 번째 버전까지 개선(광역시 접두형·세종 특례·분구 소급·시도 오타 허용)해 주소 파싱 실패 99% 이상 감소. 현업 보정을 반영한 뒤 주소 결측 리젝트도 99% 이상 감소
  • 병렬 처리의 데드락 위험: 무거운 스캔은 임시 테이블에서 락 없이, 전역 advisory lock 은 작은 upsert 에만 잡도록 분리. 약 2년 반 치 전 기간 재처리 1시간 4분, 통과율 97.42%(2026.07 스냅샷)
  • 이후 매일 도는 당월 재처리는 중앙값 약 14분
  • 제품명 대조의 자동 승격이 다른 품목을 추천한 사례가 실제로 나오자 승인 게이트로 바꿨고, 이후 그 단계를 없앰

달 단위로 바뀌는 것월 상태·월마감·시장 선정·재고

화면과 다운로드를 크게 바꾸는 월 단위 작업은 셋입니다. 첫째는 월마감으로, 유통사가 확정한 한 달치로 그 달 전체를 교체합니다. 둘째는 ATC 시장 선정으로, 매월 시장 목록을 다시 고릅니다. 셋째는 매출과 따로 도는 재고 적재입니다. 세 작업 모두 월 상태 원장을 기준으로 움직입니다.

  • 월마감: 매일 새벽 전월·전전월의 마감 여부를 확인해 마감된 달 하나만 다시 받아 교체하고, 마감 전이면 건너뜀. 재시도 기본값을 '실패'로 둬 실행이 오래 붙잡히지 않게 함
  • 교체 방식: 별도 테이블에 락 없이 적재하고 파티션 경계 CHECK 를 미리 붙여 부착 시 검증 스캔을 없앰. 짧은 트랜잭션에서 분리·부착하고, 행 지문 대사로 추가·삭제 행을 기록. 급감 가드로 빈 마감본이 정본을 덮지 못하게 함
  • 마감 뒤 규칙: 엑셀은 마감월에만 유통사 원문처럼 반품·도매를 포함하고, 마감 전 달은 제외
  • ATC 시장 선정: 고정된 상위 목록을 매월 1일 기준 컷오프로 다시 고르는 선정 원장으로 전환. 기준은 현업이 확정했고, 실데이터 영향 측정·질의서 작성·구현은 본인 몫. 시장 실금액이 노출될 위험을 질의서에서 짚었고, 회신에 따라 목록에서 순위·금액을 빼고 자사가 유통한 시장만 보이게 구현
  • 재고: 매출과 따로 도는 월 스냅샷. 매일 마감 여부를 확인하고 마감된 달만 적재
  • 정보 제공 미동의 매입처 제외: 전 기간 정리는 월마감 교체 기계를 재사용(시험 실행 기본, 확인 문자열, 감사 기록). 약 400만 행을 계획과 일치하게 제거했고 잔존 0, 소요 약 19분

낮에 바뀌는 것매출 다시 받기와 보정 연계

새벽 수집이 실패하거나 0건으로 끝난 날은 같은 날 다시 받을 수 있게 했고(매출 다시 받기), 현업의 보정 요청은 낮 묶음으로 재전처리해 공개합니다. 두 기능 모두 이 파이프라인의 원장·월 상태·정본 서열 규칙 위에서 돕니다.

  • 다시 받기의 판정 흐름·안전장치·성과는 사내 데이터 보정·검수 백오피스 페이지에 자세히 적었습니다
  • 엑셀 다운로드는 원천을 바로 읽어 받은 직후 바뀌고, 화면은 낮 보정 묶음의 공개 표시 뒤 바뀝니다

설계 결정왜 이렇게 했나

원천이 느리고, 명세가 바뀌고, 같은 달이 여러 경로로 들어오는 조건이었습니다. 이 조건에서 '다시 돌려도 같은 결과'와 '조용히 버리지 않기'를 가장 먼저 지키는 쪽으로 골랐습니다.

결정고른 이유버린 대안·대가
원본을 먼저 전량 적재(영속 원본 원장)전처리 기준이 확정되기 전에도 원천을 잃지 않고, 기준이 바뀌면 원본에서 다시 만들 수 있음. 엑셀 다운로드도 유통사 원문 그대로 이 원장을 읽음(원본 우선 적재는 팀 의견으로 결정)전처리 확정 뒤 적재: 기준이 바뀔 때마다 다시 받아야 함
변환·검증·집계는 PostgreSQL 집합 SQL, Airflow 는 순서·재시도·시간 창만행 단위 왕복이 없고, 기준이 바뀌면 해당 월만 다시 실행해 회수. 전 기간 재처리도 1시간 4분작업 코드에서 행 단위 처리: 느리고 대사 지점이 흩어짐
수집 원장·월 상태 원장을 스케줄러 메타DB 가 아니라 매출 DB 에 둠화면의 '데이터 업데이트 일시', 멱등 검증, 신선도 판정이 한 곳의 기록에서 나옴스케줄러에 상태 보관: 서빙 앱이 읽을 수 없음
월 단위 무조건 삭제 후 재적재 + 원장 대사 강제증분 upsert 보다 단순하고 재실행 결과가 같음. 대사가 어긋나면 그 달을 실패로 남기고 공개하지 않음증분 upsert: 원천에서 사라진 행이 남는 위험
정본 서열(월마감본, 과거 파일, 전일분 순) + advisory lock같은 달을 여러 경로가 써도 서열이 낮은 데이터가 높은 데이터를 덮지 못함경로별 개별 규칙: 덮어쓰기 사고 가능
월마감은 별도 테이블에 적재한 뒤 짧게 교체교체 중에도 조회가 멈추지 않고, 빈 마감본은 가드에서 걸림한 트랜잭션에서 분리·적재·부착: 긴 배타 락으로 조회 정지
무거운 DB 작업은 한 칸짜리 풀로 직렬화작업끼리 DB 를 다투지 않고 공개 시각을 예측할 수 있음병렬 실행: 원천 호출 창·DB 부하와 충돌
자동 보충은 fail-open보충이 실패해도 정상 전일분 수집은 막지 않음. 보충 실패 때문에 더 큰 공백이 생기면 안 되기 때문보충 실패 시 전체 중단
Airflow 3(KubernetesExecutor·git-sync)·전용 PostgreSQL 17 을 GitOps 로 운영작업마다 파드로 자원 격리, DAG 는 git push 로 배포, 매출·마스터·메타 DB 분리. Airflow 는 처음부터 직접 제안해 채택했다 — 이전 직장들의 데이터 파이프라인을 모두 Airflow 로 운영해 왔고, 이 일에는 작업 사이 의존 순서·실패 재시도·지난 날짜 다시 돌리기(백필)·실행 기록 화면이 기본으로 필요했으며, 원천 API 가 새벽에만 열리는 시간 창도 스케줄로 다루기 쉬웠다. 그 위에 원장·멱등 규약을 맞춤앱 내 스케줄링: 앱 배포와 파이프라인 배포가 묶이고, 재시도·백필·실행 기록을 직접 만들어야 함
분석 전용 엔진을 따로 두지 않고 PostgreSQL 하나로당시 규모에서는 불필요하다고 보고 실측 뒤 재평가하기로 함. 서빙 지연은 인덱스·튜닝으로 해결(서빙 성능 페이지)별도 OLAP 저장소: 동기화·운영 부담 추가

CASE 01 · 대용량처리

멈추던 백필을 끝까지: 18분 정지의 원인은 SQL 밖에 있었다

1문제 상황

약 2년 반 치 원본(수천만 건, 약 100GB 규모)을 월별 수 GB 단위 JSON 파일에서 적재해야 했습니다. 파일을 통째로 파싱할 수 없어서 스트리밍 파서와 COPY 로 적재 작업을 만들었습니다. 그런데 전체 실행이 두 번 모두 18분쯤 멈춘 뒤 실패했습니다.

2원인 분석

먼저 작업 파드 로그로 범위를 좁혔습니다. SQL 오류는 없었고, 작업과 스케줄러 API 서버 사이의 통신 계층에서 멈추고 있었습니다. 원인은 두 가지였습니다. Airflow 3 API 서버의 메타DB 커넥션 풀이 고갈됐고, 제 DB 도구에 열어 둔 미커밋 트랜잭션이 월 파티션 생성을 막고 있었습니다.

3해결 과정
  1. 표준 라이브러리 스트리밍 파서(UTF-8 청크 경계 처리, 깨진 레코드 크기 상한)와 COPY 로 적재
  2. 월 단위 무조건 삭제 후 적재, 원천 총건수 대사(불일치 시 롤백), 기간 겹침 거부, 고아 실행 정리
  3. 파티션을 미리 만들고 API 서버 커넥션 풀을 늘리고, 유휴 트랜잭션에 시간 제한 설정
  4. 운영 규칙을 런북에 기록: 실행 중 화면 그리드 조회 금지, DB 도구는 자동 커밋
  5. 적재 로직은 AI 에이전트 적대 리뷰에서 확정된 결함을 고친 뒤 실행
4결과

세 번째 실행에서 75분 38초 만에 완주했고, 적재 행 수가 원천 총건수와 정확히 일치했습니다. 이 원본 원장은 이후 전처리와 엑셀 다운로드의 정본이 됐습니다.

CASE 02 · 장애대응

건수 검증의 함정: 숫자는 맞았는데 키가 모자랐다

1문제 상황

매일 도는 공공 약국 마스터 동기화가 하룻밤 사이에 평시 하루 삭제량의 수백 배에 이르는 행을 삭제 처리했습니다. 수집 건수 검증은 통과했기 때문에 경보가 울리지 않았습니다. 이 마스터는 매출 전처리가 쓰는 기준 정보라서, 그대로 두면 오류가 하류 데이터로 번질 수 있었습니다.

2원인 분석

로그와 동기화·변경 기록의 숫자를 맞춰 보며 기전을 증명했습니다. 원천 API 가 일부 페이지에 다른 페이지의 내용을 중복으로 보내고 있었습니다. 그래서 건수는 같았지만 고유키가 크게 모자랐고, 목록에 없는 행이 삭제된 것으로 오판됐습니다. 삭제된 행의 분포가 정렬된 페이지 블록 모양이라는 점과, 같은 기전의 이전 사례가 있었다는 점도 확인했습니다. 원인은 외부 공공 API 의 결함이었고, 제가 맡은 일은 원인 규명과 재발 방지였습니다.

3해결 과정
  1. 키 커버리지 가드: 고유키가 모자라면 쓰기 전에 실행 실패
  2. 페이지 중복 감지기: 서로 다른 페이지의 내용이 같으면 즉시 중단
  3. 대량 삭제 가드: 최근 실측한 평시 최대치로 임계값 보정, 우회는 테이블 단위로 수동 1회 주입할 때만 허용
  4. AI 에이전트 적대 리뷰로 가드 자체의 결함을 찾아 고치고, 단위 시험과 실 PostgreSQL e2e 시험을 통과한 뒤 배포
  5. 복구를 확인하기 전까지 하류 전처리를 수동 실행하지 말라고 공지하고 롤백 SQL 준비
4결과

다음 날 정상 수집에서, 기존 복원 로직이 삭제 처리됐던 행을 거의 모두 되살린 것을 확인했습니다(남은 소수는 폐업 추정). 새 가드는 이 정상 실행을 잘못 막지 않았습니다. 두 달 뒤 같은 원천 결함이 다시 생겼을 때는 가드가 쓰기 전에 실행을 멈춰 마스터를 지켰고, 다음 날 정상으로 돌아왔습니다.

숫자로 본 변화

오삭제 행 복구

진행 순서

  1. 사고 밤
    대량 삭제 처리건수 검증 통과, 경보 없음
  2. 같은 날
    기전 증명·3중 가드 배포로그 숫자 맞추기로 페이지 중복·고유키 결손 증명, 적대 리뷰·실 DB e2e 시험 뒤 배포, 하류 전처리 실행 금지 공지
  3. 다음 날 실행
    거의 전량 부활정상 수집에서 기존 복원 로직이 행을 되살림. 남은 소수는 폐업 추정, 가드 오작동 없음
  4. 두 달 뒤
    같은 결함 재발가드가 쓰기 전에 실행을 멈춰 마스터 보존, 다음 날 정상 회복

전후 개념도입니다. 몇 건이 왔는지가 아니라 무엇이 왔는지를 쓰기 전에 검증합니다.

배운 점

건수 검증으로는 커버리지 결손을 잡지 못합니다. 수량이 아니라 고유키 커버리지와 페이지 중복을 검증해야 합니다. 가드 자체도 리뷰와 실 DB 시험을 거쳐야 믿을 수 있습니다.

CASE 03 · 서비스운영

예고된 원천 점검: 자동 보충이 거절된 날 경보가 한 일

1문제 상황

유통사 매출 API 의 야간 점검이 예고됐습니다. 그런데 일 수집은 빠진 날을 스스로 메우지 못했고, 지연 점검은 날짜가 바뀌면 그 날을 더 보지 않았습니다. 그때까지 일 수집 이상은 사람이 발견해서 손으로 다시 받는 방식에 기대고 있었습니다.

2원인 분석

Claude Code 다중 에이전트 조사(반박 검증 포함)로 코드·수집 원장·문서를 맞대어 실제 동작을 확정했습니다. 지연 점검은 '그날 시작한 최신 실행 1건'만 봤기 때문에, 빠진 날은 다음 날이 되면 시야에서 사라졌습니다. 같은 조사에서 응답은 정상인데 0건인 날이 성공으로 적재되는 무음 위험과, 문서와 다르게 동작하는 재시도도 찾았습니다.

3해결 과정
  1. 새벽 자동 보충: 예약 실행이 전일분 수집에 앞서 최근 누락일·0건인 날을 제한된 횟수만큼 다시 받음. 연동 시간 창과 누적 시간 예산을 지키고, 원천에 행이 있으면 지우지 않음
  2. fail-open: 보충이 실패해도 정상 전일분 수집은 막지 않음
  3. 지연 점검의 기준을 전일분 대상일로 바꾸고, 최근 누락일·미공개일이 메워질 때까지 Teams 로 경보
  4. 시각표 문서를 실제 재시도 동작에 맞게 정정
4결과

실제 점검에서는 상대 쪽 일자 배치가 돌지 않아 자동 보충이 거절됐습니다. 누락일 경보로 보충이 실패한 것을 확인한 뒤 상대 쪽에 배치 실행을 요청했습니다. 점검 뒤 첫 평일 오전에 수동으로 재수집해 유통사 건수와 같은 행 수를 적재했고, 데이터를 복구했습니다.

숫자로 본 변화

누락일 인지
사람이 발견→메워질 때까지 울리는 경보

점검 뒤 첫 평일 오전, 재수집 행 수가 유통사 건수와 일치

진행 순서

  1. 점검 예고
    현재 동작 조사다중 에이전트 조사로 코드·원장·문서를 대조해 무음 위험과 판정 공백 확인
  2. 점검 전
    자동 보충·누락일 경보 구현fail-open 보충과, 메워질 때까지 울리는 경보
  3. 점검 뒤 새벽
    자동 보충 거절상대 쪽 일자 배치가 실행되지 않음. 누락일 경보로 보충 실패 확인
  4. 점검 뒤 첫 평일 오전
    수동 재수집으로 복구상대 쪽에 배치 실행을 요청한 뒤 재수집, 유통사 건수와 같은 행 수
배운 점

상대 쪽 배치가 돌지 않은 경우는 자동 보충으로 해결할 수 없습니다. 자동 복구에만 기대지 말고, 메워질 때까지 울리는 경보와 사람이 판단하는 경로를 함께 둬야 합니다.

CASE 04 · 아키텍처설계

몇 번을 다시 돌려도 같은 결과: 정본 서열과 중단 없는 월마감 교체

1문제 상황

같은 달의 매출이 여러 경로로 들어왔습니다. 새벽 전일분 수집, 과거 파일 백필, 유통사 월마감본, 낮 다시 받기. 유통사는 월마감 뒤 전월을 보정했고, 매입처마다 마감 시점이 달라 완료 시각을 예측할 수 없었습니다. 재실행하면 중복이 생기거나, 빈 마감본이 정본을 덮거나, 교체 중에 조회가 멈출 위험이 있었습니다.

2원인 분석

근본 문제는 '누가 그 달의 정본인가'를 정하는 규칙이 없다는 것이었습니다. 처음 떠올린 방식은 한 트랜잭션 안에서 파티션을 분리·적재·부착하는 것이었는데, 적재 내내 배타 락을 잡아 서빙을 멈추게 하므로 쓸 수 없었습니다.

3해결 과정
  1. 월 상태 원장과 정본 서열(월마감본, 과거 파일, 전일분 순) 도입: 마감된 달은 서열이 낮은 경로가 덮지 못함. 모든 쓰기의 앞뒤에 advisory lock·서열 확인·원장 기록을 둠
  2. 월 단위 무조건 삭제 후 재적재와 원장 대사를 강제해 재실행 결과를 고정
  3. 월마감은 별도 테이블에 락 없이 적재하고 파티션 경계 CHECK 를 미리 붙인 뒤, 짧은 트랜잭션에서 분리·부착(락 대기 제한·재시도). 행 지문 대사로 추가·삭제 행을 기록하고, 급감 가드에 걸리면 교체 보류
  4. 마감 감지를 '매일 확인, 마감 전이면 건너뛰기'로 재설계해 월 1회 실행과 반복 재시도 때문에 실행이 오래 붙잡히던 문제를 없앰
  5. 무거운 작업은 한 칸짜리 풀로 직렬화하고, 실측 소요 시간으로 새벽 시각표를 다시 확정
4결과

2026년 9월부터 정기 작업 7종이 매일 새벽 사람 손 없이 돌기 시작했고, 첫 무개입 운행일에는 03:28~03:29 에 데이터가 공개됐습니다. 정보 제공에 동의하지 않은 매입처의 데이터를 전 기간에서 빼야 했을 때도 같은 교체 기계를 재사용했습니다. 약 400만 행을 계획과 일치하게 제거했고(잔존 0), 약 19분이 걸렸습니다.

전후 개념도입니다. 교체하는 동안에도 조회가 멈추지 않고, 빈 마감본은 가드에서 걸립니다.

배운 점

자동화를 맡기려면 먼저 '다시 돌려도 같은 결과'가 보장돼야 합니다. 정본 규칙과 대사를 먼저 세워 두면 새 요구(데이터 제외, 전 기간 정리)도 같은 기계로 받아낼 수 있습니다.

정리:이 프로젝트에서 남긴 것

실패 지점은 데이터가 아니라 주변 계층(스케줄러 메타DB, 내가 쓰던 DB 도구)에 있을 수도 있습니다. 매번 같은 시점에 멈추면 먼저 로그로 어느 계층인지 좁히고, 내 작업 환경도 원인 후보에 넣어야 합니다.

건수 검증으로는 커버리지 결손을 잡지 못합니다. 수량이 아니라 고유키 커버리지와 페이지 중복을 검증해야 합니다. 가드 자체도 리뷰와 실 DB 시험을 거쳐야 믿을 수 있습니다.

상대 쪽 배치가 돌지 않은 경우는 자동 보충으로 해결할 수 없습니다. 자동 복구에만 기대지 말고, 메워질 때까지 울리는 경보와 사람이 판단하는 경로를 함께 둬야 합니다.
