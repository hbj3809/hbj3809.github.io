의약품 유통 매출 데이터 파이프라인

국내 대형 의약품 유통사의 매출 데이터를 받아, 제약사 고객이 보는 분석 서비스에 공급하는 파이프라인(수집 → 전처리 → 공개 → 서빙)을 설계·구현했습니다.

문제

  • 원천에는 연동 API 가 없었고, 생긴 뒤에도 새벽 몇 시간만 호출할 수 있었습니다.
  • 과거 2년 반 치는 월별 수 GB 짜리 JSON 파일로 따로 받았습니다.
  • 유통사는 월마감 뒤에도 전월을 보정하고, 매입처마다 마감 시점이 다릅니다. 명세는 진행 중에도 계속 바뀌었습니다.

설계

  • 연동 명세를 먼저: 매출·재고·수신 설정 API 의 연동 컬럼 82개를 영문 정의서로 직접 작성해 유통사의 API 개발 기준으로 제공했고, 실호출로 명세와 다른 점을 찾아 보정했습니다.
  • 하나의 원장: 원본 원장 → 전처리 결과·리젝트 → 일 집계 → 공개 경계 → 서빙 API 계층. 월 상태 원장과 정본 순서(월마감 > 백필 > 전일분), 잠금, 원장 대사로 몇 번을 다시 돌려도 결과가 같게 했습니다.
  • 조용히 버리지 않기: 매월 "원본 = 성공 + 리젝트" 항등식과 "한 행에 사유 하나" 규칙을 강제했습니다.
  • 중단 없는 마감 교체: 마감 보정분은 별도 테이블에 적재한 뒤 짧은 트랜잭션으로 파티션을 바꿔 끼우고, 행 해시 대사로 무엇이 바뀌었는지 남깁니다.

멈추던 백필을 끝까지

과거분 전체 백필은 처음 두 번 모두 18분쯤 멈춘 뒤 실패했습니다. SQL 이 아니라 작업과 스케줄러 API 서버 사이의 통신 계층으로 범위를 좁혀, 메타DB 커넥션 풀 고갈과 제 DB 도구에 열어 둔 미커밋 트랜잭션이 파티션 생성을 막은 것을 찾았습니다. 파티션 선생성·풀 확장·유휴 트랜잭션 제한과 운영 규칙을 적용한 세 번째 실행에서 수천만 건(약 100GB 규모)을 75분에 원천 총건수와 정확히 맞게 적재했습니다.

건수 검증의 함정

공공 약국 마스터 동기화가 하룻밤에 평소보다 수백 배 많은 행을 삭제 처리했는데, 건수 검증은 통과했습니다. 원천 API 가 일부 페이지에 다른 페이지 내용을 중복으로 보내 고유키가 모자랐던 것입니다. 키 커버리지·페이지 중복·대량 삭제 가드를 세 겹으로 넣었고, 두 달 뒤 같은 결함이 재발했을 때 가드가 쓰기 전에 막았습니다. 교훈: 건수 검증은 커버리지 결손을 잡지 못한다.
