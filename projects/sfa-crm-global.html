프로젝트 개요
무엇을, 왜 만들었나

SFA는 국내 영업 지원 시스템으로 시작했습니다. 현업 요구를 받으면서 SAP ERP의 자재(MM)⁠·생산(PP)⁠·영업물류(SD)⁠·재무회계(FI) 모듈과 연동하는 영업⁠·고객⁠·주문⁠·정산 공통 플랫폼으로 넓혔습니다. 도메인은 DDD 경계 네 개로 나눴고, 국가마다 다른 언어⁠·시간대⁠·통화는 공통 어댑터 한 곳에서 처리했습니다. 이 구조로 베트남⁠·필리핀⁠·인도⁠·미얀마 법인에 배포했습니다. 그룹은 계열사마다 다른 외주사의 CRM을 쓰고 있어 데이터를 모으기 어려웠고, 2024.02에 이 플랫폼을 계열사 공통 ERP 표준 모델로 채택했습니다. 현업 보고 자료를 보면 영업사원 생산성이 30%, 계약 전환율이 15%↑ 올랐습니다. 외주 견적과 비교하면 1억 5,000만원↓을 아꼈습니다.

개요배경⁠·범위⁠·내 역할

그룹 계열사마다 서로 다른 외주사가 만든 CRM을 쓰고 있었습니다. 그래서 그룹 차원에서 영업⁠·운영 현황과 지표를 모을 때마다 연동이 맞지 않았습니다. SFA는 처음에 국내 영업 지원 시스템으로 기획했고, 해외 법인에 제공하는 것도 목표였습니다.

여러 사업부⁠·마케팅⁠·임원의 요구를 받아 주문⁠·고객 관리⁠·여신⁠·미수금까지 넓혔습니다. 그러면서 SFA는 SAP ERP의 자재(MM)⁠·생산(PP)⁠·영업물류(SD)⁠·재무회계(FI) 모듈과 연동하는 공통 플랫폼이 됐습니다. 기획부터 설계⁠·개발⁠·배포까지 혼자 맡았습니다(SAP 영역 제외). 국내 배포 직후 해외 법인에서 사용 요청이 들어와 베트남⁠·필리핀⁠·인도⁠·미얀마 법인에 배포했습니다.

2023년 말 그룹 ERP 통합 프로젝트는 SAP 표준 프로그램을 많이 쓰던 선진의 업무 모델을 통합 기준점으로 삼았습니다. 이 플랫폼은 그 안에서 SAP 4개 모듈 인터페이스의 완성도와 예측 모델 도입 성과를 인정받았고, 2024.02 그룹 계열사 공통 ERP 표준 모델로 채택됐습니다.

  • 범위영업(상담⁠·활동)⁠·고객(거래처⁠·담당자)⁠·주문(주문서⁠·배송)⁠·정산(청구⁠·여신⁠·미수금)
  • 설계 목표국가마다 다른 업무 규칙과 언어를 유연하게 처리해 4개국으로 넓힐 수 있는 구조
  • 사용자영업사원, 발주⁠·현황 대시보드를 쓰는 고객⁠·대리점, 대시보드와 보고서 자동 추출을 쓰는 영업지원⁠·경영지원 부서, 예측 결과를 보는 본부장⁠·임원
  • 연계별도 예측 모델 프로젝트(DBA 1명과 2인 수행)의 축우 등급⁠·D등급 고객 예측 결과를 화면에 연결
  • 인정2023.02 한국저작권위원회 저작권 등록, 2024.02 그룹 계열사 공통 ERP 표준 모델 채택

아키텍처하나의 플랫폼, 두 개의 관문

사용자는 국가와 상관없이 같은 플랫폼으로 들어옵니다. 국가마다 다른 부분은 현지화 공통 어댑터 한 곳에서 맞춥니다. SAP로 나가는 호출은 모두 공통 연동 모듈 한 곳을 거칩니다. 앞뒤에 이 두 관문을 둔 이유는 도메인 로직이 국가 사정이나 SAP 사정에 덜 묶이게 하기 위해서입니다.

영업⁠·고객⁠·주문⁠·정산은 DDD의 Bounded Context로 나눴습니다. 네 영역은 바뀌는 이유가 서로 다릅니다. 경계를 나누면 한 사업부의 요구가 다른 영역까지 번지는 일을 줄일 수 있습니다.

  • 진입전사 SSO(OAuth 2.0), Access/Refresh Token 기반 무상태 인증
  • 현지화국가별 시간대⁠·통화⁠·언어셋을 맞추는 공통 어댑터
  • 도메인영업⁠·고객⁠·주문⁠·정산 4개 경계
  • 연동견적⁠·주문⁠·정산에서 나가는 SAP MM⁠·PP⁠·SD⁠·FI 호출을 공통 연동 모듈 한 곳으로
  • 저장Oracle, 4개국 법인 데이터는 법인별 DB⁠·스키마로 나눠 격리
  • 예측별도 프로젝트의 축우 등급⁠·D등급 고객 예측 결과를 화면에 연결
  • 운영Jenkins⁠·Docker 배포, Jennifer APM 응답 감시

도메인 모델개념 ERD

영업 과정을 상담에서 정산까지 이어지는 하나의 데이터 흐름으로 보고, 경계마다 핵심 개념을 둘씩 두었습니다. 영업(Deal⁠·Activity), 고객(Partner⁠·Contact), 주문(SalesOrder⁠·Delivery), 정산(Invoice⁠·Credit)입니다. 4개국 확장의 기준점으로 국가 법인과 영업사원을 더했습니다.

아래 그림은 이해를 돕는 개념 모델이며 실제 테이블 구조와 같지 않습니다. 관계와 속성은 업무 흐름을 바탕으로 다시 구성했습니다. 법인 데이터는 법인별 DB⁠·스키마로 나뉘어 있어 실제로는 법인마다 이 구조가 따로 있습니다.

  • 영업상담⁠·기회(Deal)와 영업사원의 활동 기록(Activity)
  • 고객거래처(Partner)와 담당자(Contact)
  • 주문SAP 판매 주문과 연결되는 주문서(SalesOrder)와 배송(Delivery)
  • 정산청구서(Invoice)와 여신 한도⁠·미수금을 담는 여신(Credit)

SAP ERP 연동 구조

SFA/CRM은 영업 화면입니다. 하지만 품목⁠·재고⁠·생산⁠·출하⁠·여신 같은 실제 업무 데이터는 SAP ERP에 있습니다. 그래서 SAP의 네 모듈과 주고받는 인터페이스를 공통 연동 모듈 한 곳에 모았고, 어떤 데이터든 같은 형식으로 주고받도록 표준화했습니다.

2023년 말 그룹 ERP 통합 프로젝트에서 이 플랫폼이 기준 모델로 검토된 이유 중 하나가 이 인터페이스의 완성도였습니다.

  • MM 자재관리품목 마스터 동기화, 실시간 재고 조회⁠·가용성 체크
  • PP 생산관리생산 계획 연동, 주문에 따른 생산 지시 자동화
  • SD 영업⁠·물류견적⁠·주문 생성, 출하 지시, 배송 상태 추적
  • FI 재무회계거래처 여신 한도 실시간 체크, 매출 전기⁠·수금 현황 조회

핵심 흐름주문에서 여신 확인, 출하까지

주문 한 건이 SAP의 여러 모듈을 거치는 순서입니다. 주문은 먼저 SFA에 가주문으로 접수되고, 이때 재고 가용성(MM)과 거래처 여신 한도(FI)를 확인합니다. 여신 한도 안이면 실주문을 SAP로 넘겨 판매 주문(SD)을 만들고, 재고가 모자라면 생산 지시(PP)로 넘어갑니다. 출하 뒤 배송 상태는 SD에서 다시 받아 영업사원과 고객 화면에 보여 줍니다.

여신 한도를 넘은 가주문은 별도 상태로 실패 처리하고 담당자에게 알립니다. 현업이 승인하거나 여신을 처리하면 그때 실주문이 SAP로 넘어갑니다.

4개국 글로벌 멀티테넌시⁠·현지화

국내와 4개국 법인이 같은 플랫폼을 씁니다. 그래서 법인 데이터는 법인별 DB⁠·스키마로 나눠 격리하고, 국가마다 다른 시간대⁠·통화⁠·언어셋은 공통 어댑터에서 맞췄습니다. 요청이 어느 법인 것인지는 법인별 접속 주소⁠·서버, 로그인 토큰의 법인 정보, 로그인한 사용자의 소속 법인 조회를 모두 써서 정했습니다.

국가별 차이를 기능 코드 곳곳에 분기로 흩어 두지 않고 어댑터 한 곳에 모은 이유가 있습니다. 법인이 늘 때마다 모든 기능을 고치지 않으려는 것이었습니다. 법인마다 다른 업무 규칙도 법인별 설정값과 공통 코드 표로 두고 같은 코드가 읽게 했습니다.

언어는 서버 문구를 Spring Message로 관리하고, 화면에서 나중에 그려지는 요소는 MutationObserver로 감지해 번역 문구를 넣었습니다.

  • 격리법인별 DB⁠·스키마 분리
  • 법인 확인법인별 접속 주소⁠·서버, 로그인 토큰의 법인 정보, 사용자 소속 법인 조회
  • 시간대법인별 Timezone
  • 통화법인별 통화
  • 업무 규칙법인별 설정값⁠·공통 코드
  • 언어Spring Message⁠·MutationObserver 기반 다국어

설계 결정왜 이렇게 만들었나

도메인을 4개 경계로

영업⁠·고객⁠·주문⁠·정산은 바뀌는 이유가 서로 다릅니다. 경계를 나눠 응집도는 높이고 결합도는 낮췄습니다. 사업부나 국가의 요구가 한 경계 안에서 처리되게 하는 것이 목표였습니다. 기능은 따로 움직여도 데이터는 상담에서 정산까지 "하나의 흐름"으로 이어지게 했습니다.

SAP 연동은 한 곳으로

MM⁠·PP⁠·SD⁠·FI 호출이 기능마다 흩어져 있으면 SAP 쪽이 바뀔 때마다 플랫폼 전체를 고쳐야 합니다. 그래서 호출을 공통 연동 모듈로 모으고 주고받는 형식을 표준화했습니다. 그룹 ERP 통합에서 이 플랫폼이 기준 모델로 검토된 근거 중 하나도 이 인터페이스였습니다.

국가 차이는 어댑터로

언어⁠·시간대⁠·통화 차이를 공통 어댑터에 모아 두면, 법인을 늘릴 때 도메인 코드를 덜 고쳐도 됩니다. 해외 법인 제공을 처음부터 목표로 두고 다국어 기반으로 설계했습니다. 그래서 국내 배포 직후 해외 법인 요청이 왔을 때 바로 제공할 수 있었습니다.

외주 대신 직접 구축

해외 법인용 디자인 템플릿의 외주 견적이 9,000만원(VAT 별도)이었고, 시스템 전체도 외주로 진행할 예정이었습니다. 외주에 맡기면 장기적으로 유지보수 비용이 늘고 시스템을 우리가 통제하기 어려워진다고 판단했습니다. 그래서 자체 구축을 제안했습니다.

무상태 토큰 인증

전사 SSO로 통합 로그인을 구현해 보안을 강화하고 로그인을 한 번으로 줄였습니다. 인증은 Access/Refresh Token으로 처리해 서버가 세션을 들고 있지 않습니다. 그래서 법인이나 서버가 늘어도 세션 공유를 따로 설계할 필요가 없습니다.

성과영업 지표

도입 뒤 사업 본부(BU)별 월간 영업 보고 자료에 두 지표가 실렸습니다. 영업사원 생산성은 계약⁠·주문 건수와 배차 현황 데이터의 적재량을 도입 전과 비교한 값입니다. 같은 시기에 자체 구축한 MES와 함께 업무가 자동화⁠·일원화된 효과도 들어 있습니다. 계약 전환율은 고객이 직접 발주⁠·현황 대시보드를 쓰게 된 뒤의 추가 계약과 신규 고객 증가를, 수기⁠·전화 주문 시절과 비교해 집계한 값입니다.

같은 시기에 전사 CI/CD를 구축해(별도 프로젝트) 배포 리드타임도 60분→10분↓(80%↓ 단축)으로 줄었습니다.

  • 현업 시스템 만족도 조사업무 중 SFA 사용 시간 비중을 묻는 질문에 '100%'를 고른 응답이 가장 많음
  • 고객직접 발주하고 영업사원과 실시간으로 소통
  • 영업지원⁠·경영지원 부서대시보드로 현황 파악, 보고서 자료 추출 자동화

외주비 절감 구성

SFA/CRM으로 직접 줄인 외주 비용은 해외 법인용 디자인 템플릿 9,000만원과 해외 SFA 구축 6,000만원, 합계 1억 5,000만원입니다. 같은 시기 별도 프로젝트인 외주 물류 시스템 내재화에서도 비용을 줄였습니다. TMS/WMS 유지보수를 외주 40%⁠·자체 60%로 나눠 맡아 연간 4,800만원↓을 줄였고, 전자계약을 자체 개발해 3,000만원을 더 줄였습니다. 네 항목을 합한 선진 재직 중 절감액은 2억 2,800만원입니다.

CASE 01 / 04플랫폼설계

계열사마다 다른 외주 CRM → 그룹 계열사 공통 ERP 표준 모델

문제 현황

연동 불일치
  • 계열사마다 서로 다른 외주사가 CRM을 만들고 운영
  • 그룹 지표를 모을 때마다 인터페이스 불일치, 모기업은 개선 요청
  • 국내 영업 지원용 SFA가 SAP 여러 모듈을 다루는 플랫폼으로 확장 중

원인 분석

기준 부재
  • 시스템마다 데이터 모델⁠·연동 방식이 서로 다름
  • 같은 영업⁠·주문 데이터를 한 기준으로 모을 수 없음
  • 그룹 ERP 통합 기획에 기준 업무 모델⁠·인터페이스가 필요

해결 과정

구조 설계
  1. DDD 경계로 도메인 설계, SAP MM⁠·PP⁠·SD⁠·FI는 공통 연동 모듈로 표준화
  2. 여러 사업부⁠·마케팅⁠·임원 요구 반영, 배포 전 인프라⁠·보안 점검
  3. 해외 법인 요청에 다국어 구조로 대응해 4개국 배포
  4. 별도 프로젝트의 축우 등급⁠·D등급 고객 예측 결과를 플랫폼에 연결

결과

표준 채택
  • 2023년 말 그룹 ERP 통합에서 SAP 인터페이스 완성도⁠·예측 모델 성과 인정
  • 2024.02 그룹 계열사 공통 ERP 표준 모델로 채택
  • 앞서 2023.02 한국저작권위원회에 저작권 등록
전체 설명 보기
문제 상황

그룹 계열사마다 서로 다른 외주사가 CRM을 만들고 운영하고 있었습니다. 그룹 차원에서 영업⁠·운영 현황과 지표를 모을 때마다 인터페이스가 맞지 않았고, 모기업은 개선을 계속 요청했습니다. 제가 만들던 SFA는 국내 영업 지원용으로 시작했지만, 현업 요구에 따라 SAP의 여러 모듈 데이터를 다루는 플랫폼으로 넓어지고 있었습니다.

원인 분석

시스템마다 데이터 모델과 연동 방식이 달라서 같은 영업⁠·주문 데이터를 한 기준으로 모을 수 없었습니다. 그룹 ERP 통합을 기획하려면 기준점이 될 업무 모델과 인터페이스가 필요했습니다.

해결 과정
  1. 영업⁠·고객⁠·주문⁠·정산을 DDD 경계로 나눠, 국가와 사업부가 늘어도 버티는 도메인 모델 설계
  2. SAP MM⁠·PP⁠·SD⁠·FI 인터페이스를 공통 연동 모듈로 표준화
  3. 한 부서가 아니라 여러 사업부⁠·마케팅⁠·임원의 요구를 함께 반영하고, 배포 전 인프라⁠·보안 요구사항 점검
  4. 국내 배포 직후 들어온 해외 법인 요청에 다국어 구조로 대응해 4개국 배포
  5. 별도 예측 모델 프로젝트(DBA 1명과 2인 수행)의 축우 등급⁠·D등급 고객 예측 결과를 플랫폼에 연결
결과

2023년 말 그룹 ERP 통합 프로젝트에서 SAP 모듈 인터페이스의 완성도와 예측 모델 도입 성과를 인정받았습니다. 그 결과 2024.02 그룹 계열사 공통 ERP 표준 모델로 채택됐습니다. 그보다 앞선 2023.02에는 한국저작권위원회에 저작권도 등록했습니다.

CASE 02 / 04비용절감

디자인 템플릿 외주 견적 9,000만원 → 입사 1개월 자체 구축

문제 현황

외주 견적
  • 해외 법인용 디자인 템플릿 외주 견적 9,000만원(VAT 별도)
  • 디자인뿐 아니라 시스템 전체도 외주로 진행할 예정

원인 분석

외주 한계
  • 외주로 가면 장기 유지보수 비용이 늘고 통제가 어렵다고 판단
  • 해외 확장⁠·SAP 연동을 이으려면 구조를 직접 쥐고 있어야 함

해결 과정

자체 구축
  1. 템플릿을 포함해 시스템 전체 자체 구축 방향 제안
  2. 입사 1개월 만에 해외 법인용 디자인 템플릿 직접 구축
  3. Spring Message⁠·MutationObserver로 다국어 지원 설계
  4. 해외 SFA도 외주 없이 같은 플랫폼으로 4개국 법인 배포

결과

비용 절감
  • 디자인 템플릿 외주 견적 9,000만원↓ 절감(전액)
  • 해외 SFA 구축 외주 비용도 6,000만원↓ 절감
  • 외주 견적 대비 합계 1억 5,000만원↓ 절감
전체 설명 보기
문제 상황

해외 법인용 SFA의 전용 디자인 템플릿을 외주사에 요청했더니 9,000만원(VAT 별도) 견적이 나왔습니다. 시스템 전체도 외주로 진행할 예정이었습니다.

원인 분석

외주로 가면 장기적으로 유지보수 비용이 늘고, 시스템을 우리가 통제하기 어려워진다고 판단했습니다. 해외 법인 확장과 SAP 연동을 계속 이어 가려면 구조를 직접 쥐고 있어야 했습니다.

해결 과정
  1. 디자인 템플릿을 포함해 시스템 전체를 자체 구축하는 방향 제안
  2. 입사 1개월 만에 해외 법인용 디자인 템플릿 직접 구축
  3. 다국어 지원(Spring Message⁠·MutationObserver)을 설계해 해외 법인 배포에 대비
  4. 해외 SFA 구축도 외주 없이 같은 플랫폼으로 진행해 4개국 법인 배포
결과

디자인 템플릿 견적 9,000만원을 전액 절감했습니다. 해외 SFA 구축 외주 비용 6,000만원도 추가로 줄여, 외주 견적 대비 모두 1억 5,000만원↓을 절감했습니다.

배운 점

비용을 줄인 것보다 구조를 직접 쥐고 있었다는 점이 더 컸습니다. 그 덕분에 해외 법인 확장, SAP 연동, 그룹 표준 채택까지 이어 갈 수 있었습니다. 이후 모든 프로젝트에서 "단순 구현이 아닌 구조 설계"를 기준으로 삼게 됐습니다.

CASE 03 / 04현지대응

4개국 언어⁠·시간대⁠·통화를 국가마다 다시 만들지 않기

문제 현황

현지화 요청
  • 국내 배포 직후 베트남⁠·필리핀 법인에서 사용 요청
  • 인도⁠·미얀마까지 4개국 법인이 같은 플랫폼 사용
  • 법인마다 언어⁠·시간대⁠·통화와 업무 규칙이 다름

원인 분석

확장 비용
  • 국가별 차이를 기능 코드 분기로 두면 법인 추가 때마다 영업⁠·주문⁠·정산 전부 수정
  • 나중에 그려지는 화면은 서버 문구만 바꾸면 번역이 빠질 수 있음

해결 과정

설정 분리
  1. Timezone⁠·통화⁠·언어셋을 공통 어댑터 한 곳으로 모음
  2. 법인마다 다른 업무 규칙은 법인별 설정값⁠·공통 코드로 관리
  3. 서버는 Spring Message, 동적 요소는 MutationObserver로 번역
  4. 4개국 법인 데이터는 법인별 DB⁠·스키마로 나눠 격리

결과

4개국 배포
  • 해외 법인 요청에 다국어 SFA를 빠르게 제공
  • 베트남⁠·필리핀⁠·인도⁠·미얀마에 같은 플랫폼으로 배포
전체 설명 보기
문제 상황

국내 배포 직후 베트남⁠·필리핀 법인에서 사용 요청이 들어왔고, 인도⁠·미얀마까지 4개국 법인이 같은 플랫폼을 쓰게 됐습니다. 법인마다 언어⁠·시간대⁠·통화가 다르고, 업무 규칙에도 차이가 있습니다.

원인 분석

국가별 차이를 기능 코드 안의 분기로 처리하면, 법인이 늘 때마다 영업⁠·주문⁠·정산 기능을 모두 고쳐야 합니다. 화면 일부는 나중에 동적으로 그려지기 때문에 서버 문구만 바꿔서는 번역이 빠질 수도 있습니다.

해결 과정
  1. 국가별 Timezone⁠·통화⁠·언어셋을 공통 어댑터 한 곳으로 모음
  2. 법인마다 다른 업무 규칙은 법인별 설정값⁠·공통 코드로 관리
  3. 서버 문구는 Spring Message로 언어별 메시지 관리
  4. 화면에서 나중에 그려지는 요소는 MutationObserver로 감지해 번역 문구 적용
  5. 4개국 법인 데이터를 법인별 DB⁠·스키마로 나눠 격리
결과

국내 배포 직후 들어온 해외 법인 요청에 다국어 SFA를 빠르게 제공했고, 베트남⁠·필리핀⁠·인도⁠·미얀마 법인에 같은 플랫폼으로 배포했습니다.

구조로 보기

배운 점

국가 간 차이는 기능이 아니라 설정 문제로 다뤄야 확장 비용이 줄어든다는 것을 배웠습니다.

CASE 04 / 04현지대응

현지 네트워크가 느린 법인을 위한 경량화

문제 현황

네트워크 제약
  • 해외 법인 일부는 현지 네트워크 환경이 좋지 않음
  • 국내 기준 화면⁠·SAP 실시간 조회는 느리게 동작할 수 있음

원인 분석

문제 상황

해외 법인 일부는 현지 네트워크 환경이 좋지 않았습니다. 국내 기준으로 만든 화면과 SAP 실시간 조회를 그대로 쓰면 느리게 동작할 수 있었습니다.

원인 분석

화면을 열 때마다 리소스를 새로 받고 재고⁠·여신 같은 SAP 조회를 화면에서 여러 번 주고받으면, 왕복할 때마다 지연이 쌓입니다. 현지 연결이 불안정해 처리 도중 끊기면, 큰 트랜잭션 하나가 통째로 실패해 주문 같은 핵심 업무가 멈출 수 있었습니다.

해결 과정
  1. 현지 연결 불안정에 대비해 트랜잭션을 업무상 중요한 처리 단위별로 나눠, 일부가 실패해도 핵심 업무 처리에 문제가 번지지 않게 구현
  2. 문제가 생기면 webhook 알림이나 APM 알림을 받아 바로 대응
  3. 모든 법인이 같은 디자인 템플릿을 써서 정적 리소스를 캐시로 재사용
  4. 목록은 TreeGrid로 필요한 만큼만 나눠 불러오기
  5. 재고⁠·여신 같은 SAP 조회는 서버의 공통 연동 모듈에서 모아 한 번에 응답
  6. 무상태 토큰 인증이라 연결이 끊겨도 세션을 복구하지 않고 다시 요청
  7. Jennifer APM으로 법인별 응답 시간 관찰
결과

4개국 법인에 같은 플랫폼을 배포해 운영했습니다. 연결이 끊겨도 처리 단위별로 나눠 둔 덕분에 핵심 업무는 멈추지 않게 했고, 이상이 생기면 webhook⁠·APM 알림을 받아 대응했습니다.

배운 점

현지 환경을 국내 기준으로 가정하지 말고, 설계 단계에서 왕복 횟수와 화면 무게를 줄이는 것을 기본으로 삼아야 한다는 것을 배웠습니다.

정리이 프로젝트에서 남긴 것
