프로젝트 개요
무엇을, 왜 만들었나

공공기관이 보유한 100만 건 이상의 비정형 PDF 를 인터넷 연결이 없는 온프레미스 환경에서 텍스트·메타데이터로 바꾸고, 검색·검수할 수 있는 지식 데이터베이스로 만드는 10주 개인 프로젝트를 설계부터 개발까지 혼자 맡았습니다. PaddleOCR·PP-Structure 로 레이아웃과 글자를 읽고, Qwen3-VL·Qwen3(vLLM)로 구조와 의미를 이해하며, GLiNER 에 규칙을 더해 개체를 뽑고 개인정보를 가렸습니다. 특히 결재 과정에서 손으로 적은 메모·서명·정정 표기와 의미 없는 낙서를 인쇄 본문과 나눠 판정하는 구조를 설계했고, 인식 정확도는 인쇄체 98%·필기체 85% 를 목표로 잡았습니다.

개요

공공기관이 쌓아 온 100만 건 이상의 비정형 문서(PDF)를 OCR·VLM·LLM 으로 디지털 데이터로 바꾸고, 검색·활용할 수 있는 지식 데이터베이스로 만드는 사업이었습니다. 보안 때문에 인터넷 연결 없이 기관 내부 서버에서만 돌아야 했고, 상용 라이선스 비용이 없는 오픈소스 모델을 폐쇄망에 맞게 경량화·양자화해야 했습니다. 외부 의뢰를 혼자 맡은 10주 개인 프로젝트로(발주 기관은 비공개), AI 모델링·파이프라인 설계와 백엔드·대용량 배치·DB·검수 UI 개발을 모두 직접 수행했습니다.

  • 범위: 대용량 PDF 텍스트화, 메타데이터(제목·인물·날짜 등) 자동 추출, 개인정보 비식별화, 검색·검수 전용 Web UI
  • 환경: 폐쇄망 온프레미스(인터넷 연결 없음), GPU 서버(A100 80GB 1장 또는 A6000 48GB 2장 이상 권장), 상용 라이선스 비용이 없는 오픈소스(Apache 2.0·MIT 등)만 사용
  • 목표: 인쇄체 98% 이상·필기체/서명 85% 이상 인식(납품 요구 목표치), 신뢰도가 낮은 구간은 사람이 검수
  • 내 역할: 요구사항 분석부터 파이프라인·모델 최적화·백엔드·DB·검수 UI·운영자 매뉴얼까지 전 범위 단독
  • 납품 형태: 문서 업로드·결과 확인·결과물 내보내기(XML/JSON/PDF) UI 를 갖춘 실행 프로그램
  • 수기 영역이 중요했던 이유: 결재·검토를 거친 공공문서에는 여백 메모·서명·날인·정정 표기·낙서가 인쇄 본문과 겹쳐 있어, 나누지 않으면 본문 텍스트와 메타데이터가 함께 오염됩니다

폐쇄망 온프레미스 전체 구성

모든 구성 요소를 기관 내부 서버 안에 두었습니다. 업로드 API 는 원본을 저장하고 Kafka 에 작업만 넣은 뒤 바로 응답하고, 무거운 인식·추출은 단계별 워커가 큐에서 꺼내 처리합니다. 100만 건을 한꺼번에 올려도 업로드 API 가 처리 속도에 묶이지 않고, 단계마다 워커 수를 따로 늘릴 수 있게 하려는 설계입니다. VLM·LLM 은 vLLM 으로 GPU 서버에 띄우고 워커가 내부 API 로 호출합니다.

문서 처리 파이프라인

문서 하나가 거치는 단계입니다. 각 단계는 Kafka 에서 작업을 받아 처리하고 다음 단계로 넘기도록 해, 실패한 단계만 다시 돌릴 수 있게 했습니다. 핵심은 레이아웃 분석 직후 인쇄 영역과 수기 영역을 나눠 서로 다른 경로로 읽게 하고, 수기 영역은 메모·서명/날인·체크 표시·낙서로 판정한 뒤에야 메타데이터 정규화로 넘긴 것입니다. 정정 표기는 인쇄 블록과 수기 블록이 겹친 곳에서 따로 찾습니다.

문서 상태

문서마다 상태를 PostgreSQL 에 두고 단계가 끝날 때마다 바꿉니다. 100만 건을 처리하는 동안 어느 문서가 어디서 멈췄는지, 무엇을 다시 돌려야 하는지를 상태만 보고 알 수 있게 하려는 설계입니다.

수기 영역 처리

필기 영역 검출로 떼어 낸 블록은 아래 다섯 유형(메모·서명/날인·체크·정정·낙서)으로 나누고, 판정이 엇갈리거나 신뢰도가 낮으면 판정 보류로 둡니다. 유형마다 처리 방식과 저장 위치를 달리했습니다. 어떤 유형이든 원본 이미지는 지우지 않아, 판정이 틀려도 검수에서 되살릴 수 있습니다.

유형예시처리 방식저장 위치
수기 메모결재 의견, 날짜·이름 기입, 수량 정정 메모필기 인식 + Qwen3-VL 판독, 본문과 분리블록(수기) + 추출 필드 '수기 메모', 검색 색인 별도 필드
서명·날인서명란 서명, 기관·개인 도장검출 모델 좌표 + 양식 칸 규칙, 글자로 풀어 읽지 않음메타데이터 '서명 있음' + 좌표
체크 표시확인란 V 표시, 선택지 동그라미확인란·선택지 칸과 겹칠 때만 선택 값으로 해석추출 필드(해당 항목 선택 값)
정정 표기인쇄 글자 위 취소선, 덧쓴 숫자·날짜원문 보존 + 정정 내용 판독·연결수정 이력(원문·정정본·좌표)
낙서줄긋기, 장난 그림, 잉크 번짐본문·메타데이터·색인 텍스트에서 제외블록에 '낙서 있음' 표시와 좌표만
판정 보류VLM·규칙 판정이 엇갈리거나 신뢰도가 임계값 미만자동 확정하지 않음검수 작업(검수 UI 하이라이트)

신뢰도 기반 검수 루프

신뢰도가 낮은 구간은 검수 UI 에서 하이라이트해 사람이 보정합니다. 검수자는 원본 페이지와 인식 결과를 나란히 보고 텍스트와 수기 유형을 고치며, 원본 품질이 나빠 고칠 수 없는 문서는 재처리로 돌립니다. 모든 교정은 기록으로 남겨 이후 프롬프트·규칙 개선의 평가 셋으로 씁니다.

데이터 모델 (개념 ERD)

문서 → 페이지 → 블록으로 내려가는 구조를 기본으로, 블록마다 출처(인쇄·수기)와 수기 유형·좌표·신뢰도를 둡니다. 추출 필드와 개체는 근거가 된 블록을 가리켜 검수 UI 에서 원본 위치로 바로 이동할 수 있고, 정정 표기와 검수 교정은 블록 단위 이력으로 쌓입니다. 마스킹 이력에는 어떤 방식으로 가렸는지만 남깁니다.

하이브리드 검색

문서번호·인물명처럼 글자가 정확히 맞아야 하는 검색은 OpenSearch 전문 검색이, 표현은 달라도 뜻이 같은 문장은 벡터 검색이 잘 찾습니다. 두 결과를 합쳐 순위를 다시 매기고, 응답에는 마스킹이 적용된 텍스트와 원본 페이지 위치를 함께 내보냅니다. 수기 메모는 본문과 다른 필드로 색인해 본문 검색 결과를 흐리지 않으면서 메모 내용으로도 문서를 찾을 수 있게 했습니다.

  • 벡터 저장소 역할 분담: 100만 건 이상 문서의 페이지·블록 임베딩은 Milvus 에 두어 대규모 근사 최근접 검색을 맡기고, pgvector 는 문서 메타데이터와 같은 PostgreSQL 안에서 기관·기간·문서 유형 같은 조건과 함께 쓰는 유사 문서 찾기(검수 화면 등)를 맡김
  • 이렇게 나눈 이유: 조건이 많이 붙는 조회는 같은 DB 안에서 한 번에 거르는 편이 단순하고, 전체 규모의 의미 검색은 전용 벡터 엔진에 맡겨야 색인·검색 부하를 업무 DB 와 떼어 놓을 수 있음

모델·기술 선택과 GPU 자원 배치

폐쇄망에서는 외부 모델 API 를 부를 수 없어, 정해진 GPU 안에 VLM·LLM 을 함께 올려야 했습니다. 그래서 상용 라이선스 부담이 없는 오픈소스 모델(Qwen3·Qwen3-VL 은 Apache 2.0)을 고르고, 양자화로 VRAM 사용량을 줄여 vLLM 으로 서빙하는 구성을 잡았습니다. 모델 파일과 의존성은 인터넷 없이 설치할 수 있도록 미리 묶어 반입했습니다. 영역마다 고른 이유와 서빙·자원 배치를 함께 적었습니다.

영역기술고른 이유서빙·자원 배치
OCR·레이아웃PaddleOCR · PP-Structure · DocTR(백업)한국어 인식과 표·문단 레이아웃 분석을 한 도구에서 쓸 수 있고, Apache 2.0 이라 폐쇄망 설치에 제약이 없음OCR 워커 안에서 페이지 묶음 단위로 추론, DocTR 은 결과가 나쁜 페이지에만
문서 이해·수기 판정Qwen3-VL페이지 이미지를 보고 문서 구조·의미를 이해하고, 수기 블록 유형을 주변 문맥과 함께 판정vLLM 서버로 GPU 상주, 정해진 유형 목록 안에서만 답하도록 출력 형식 고정
메타데이터 정규화Qwen3 8B/14B · vLLMApache 2.0, 한국어 처리, 양자화하면 정해진 GPU 안에서 서빙할 수 있는 크기vLLM 서버, 양자화로 VRAM 사용량 절감, 설치 서버의 VRAM 에 맞춰 8B·14B 중 하나를 올림
개체 인식GLiNER + 규칙라벨 이름만 주면 별도 학습 없이 개체를 뽑는 GLiNER 에, 주민등록번호·전화번호처럼 형식이 정해진 값은 패턴 규칙을 더함NER 워커 프로세스 안에서 처리
대용량 처리Python · FastAPI · Kafka모델 생태계가 Python 이고, 100만 건 업로드 부하를 비동기 큐로 흘려 API 응답과 처리 속도를 떼어 놓음단계별 워커를 큐 소비자로 두고 단계마다 수를 따로 조정
저장·검색PostgreSQL · OpenSearch · Milvus·pgvector정형 메타데이터·검수 이력은 PostgreSQL, 전문 검색은 OpenSearch, 대규모 의미 검색은 Milvus, 조건이 붙는 유사 문서 찾기는 pgvector 로 역할을 나눔원본 PDF·페이지 이미지는 RAID SSD, 색인·DB 는 모두 내부 서버

CASE 01 / 05수기분리

인쇄 본문 위·여백의 수기 메모가 OCR 결과에 섞이는 문제

문제 현황

본문 오염
  • 결재·검토를 거친 스캔본의 줄 사이·여백에 손으로 적은 메모
  • 페이지 전체 OCR 시 인쇄·수기 글자가 한 줄로 섞임
  • 제목·날짜·인물 필드가 틀어지고 메모는 따로 안 남음

원인 분석

단일 경로
  • OCR 은 인쇄·필기를 가리지 않고 위치만 보고 줄을 묶음
  • 인쇄용 설정은 필기를 깨진 글자로 읽음
  • 블록 단위 신뢰도로는 섞인 글자의 오염을 못 잡음
  • 인식률보다 출처가 다른 글자를 한 경로로 처리하는 구조가 문제

해결 과정

경로 분리
  1. PP-Structure 로 문단·표·제목·양식 칸 등 인쇄 영역부터 검출
  2. 필기 영역을 수기 블록으로 떼고, 인쇄와 겹치면 정정 후보로
  3. 인쇄는 PaddleOCR, 수기는 필기 인식 + Qwen3-VL 별도 경로
  4. 수기는 별도 메모 필드·원본 좌표로 저장, 색인도 본문과 분리

결과

차단 설계
  • 메타데이터 추출·본문 색인 입력을 인쇄 영역만으로 제한
  • 수기 글자가 필드에 섞이는 길을 구조적으로 막는 설계
  • 인쇄체 98%·필기체 85% 목표를 영역별로 따로 재는 기준
전체 설명 보기
문제 상황

결재·검토를 거친 공공문서 스캔본에는 인쇄 본문 줄 사이나 여백에 손으로 적은 메모가 남아 있습니다. 페이지 전체를 OCR 한 번으로 읽으면 같은 높이에 있는 인쇄 글자와 수기 글자가 한 줄로 묶여 '본문 문장 + 메모 조각'이 이어진 텍스트가 나옵니다. 이 텍스트가 그대로 메타데이터 추출과 검색 색인으로 흘러가면 제목·날짜·인물 같은 필드가 틀어지고, 정작 메모 내용은 어디에도 따로 남지 않습니다.

원인 분석

OCR 엔진은 글자가 인쇄된 것인지 손으로 쓴 것인지를 구분하지 않고 위치만 보고 줄을 묶습니다. 인쇄 글자에 맞춘 인식 설정은 필기 글자를 깨진 글자로 읽고, 한 블록 안에 신뢰도가 높은 인쇄 글자와 낮은 필기 글자가 섞이면 블록 단위 신뢰도만으로는 오염을 잡아낼 수 없습니다. 문제는 인식률이 아니라 출처가 다른 글자를 한 경로로 처리하는 구조였습니다.

해결 과정
  1. PP-Structure 레이아웃 분석으로 문단·표·제목·양식 칸 같은 인쇄 영역을 먼저 잡도록 처리 순서를 정했습니다.
  2. 인쇄 영역 안팎에서 필기 영역을 따로 검출해 '수기 블록'으로 떼어 내고, 인쇄 블록과 겹치는 수기 블록은 인쇄 인식 결과에 섞이지 않도록 겹침 표시를 남겨 정정 후보로 넘겼습니다(취소선·덧쓴 정정 사례에서 이어서 처리).
  3. 인쇄 블록은 PaddleOCR 경로로, 수기 블록은 필기 인식과 Qwen3-VL 판독을 거치는 별도 경로로 보냈습니다.
  4. 수기 결과는 본문 텍스트와 분리된 '수기 메모' 필드에 저장하고, 블록 좌표로 원본 페이지 위치를 이어 검수 UI 에서 바로 대조할 수 있게 했습니다.
  5. 검색 색인에서도 수기 메모를 본문과 다른 필드로 넣어, 본문 검색 결과를 흐리지 않으면서 메모 내용으로도 문서를 찾을 수 있게 했습니다.
결과

메타데이터 추출과 본문 색인이 인쇄 영역만 입력으로 받도록 경로를 나눠, 수기 글자가 제목·날짜 같은 필드에 섞여 들어가는 길을 구조적으로 막는 설계를 잡았습니다. 인쇄체 98%·필기체 85% 목표를 영역별로 따로 재는 기준도 이 분리에서 나왔습니다.

숫자로 본 변화

수기 메모

배운 점

인식률을 올리기 전에 '무엇을 읽고 있는지'부터 나눠야 합니다. 출처가 다른 글자를 한 엔진·한 필드에 넣으면 뒤 단계는 모두 오염된 입력을 받습니다.

CASE 02 / 05수기판정

의미 있는 수기 메모와 의미 없는 낙서를 구별하는 문제

문제 현황

낙서 섞임
  • 떼어 낸 수기 영역 안에 메모와 낙서가 섞여 있음
  • 결재 의견·날짜·이름·수량 정정은 반드시 남길 메모
  • 낙서를 메모로 읽으면 엉뚱한 글자가 메타데이터·검색에 유입
  • 메모를 낙서로 버리면 결재 의견 같은 기록이 사라짐

원인 분석

단일 신호
  • 같은 펜의 메모·낙서는 획 두께·잉크 색으로 구별 불가
  • 기준은 '읽히는 글자인가'·양식 칸과의 관계 같은 의미 쪽
  • 한 가지 신호만 보면 어느 쪽으로든 오판이 남음

해결 과정

이중 판정
  1. Qwen3-VL 에 블록·주변 문맥을 주고 메모·서명/날인·체크·낙서 중 하나만
  2. 규칙 신호도 계산: 인식 신뢰도·글자 형태 비율·크기·위치·양식 칸
  3. 두 판정이 같으면 확정, 엇갈리면 검수 대기
  4. 낙서는 텍스트에서 빼고 표시·좌표만, 원본 이미지는 보존

결과

검수 선별
  • 낙서는 텍스트로 안 들어가고 메모는 안 버려지는 이중 판정 설계
  • 자동 확정은 두 판정이 일치하는 블록으로 한정
  • 사람이 봐야 하는 영역만 검수로 넘김
전체 설명 보기
문제 상황

수기 영역을 떼어 내도 그 안에는 성격이 전혀 다른 것들이 섞여 있습니다. 결재 의견·날짜·이름·수량 정정처럼 반드시 남겨야 하는 메모가 있는가 하면, 줄긋기·동그라미·장난 그림·잉크 번짐처럼 문서 내용과 관계없는 낙서도 있습니다. 낙서를 메모로 읽으면 엉뚱한 글자가 메타데이터와 검색 결과에 들어가고, 메모를 낙서로 버리면 결재 의견 같은 중요한 기록이 사라집니다.

원인 분석

같은 사람이 같은 펜으로 쓴 메모와 낙서는 획 두께·잉크 색 같은 픽셀 특징으로는 구별되지 않습니다. 둘을 가르는 기준은 '읽히는 글자인가', '양식 칸이나 주변 인쇄 문장과 관계가 있는가' 같은 의미 쪽에 있어서, 한 가지 신호만 보는 방법은 어느 쪽으로든 오판이 남았습니다.

해결 과정
  1. 필기 영역 검출 결과를 블록 단위로 잘라, Qwen3-VL 에 블록 이미지와 주변 문맥(같은 줄의 인쇄 텍스트, 가까운 양식 칸 이름)을 함께 주고 메모 / 서명·날인 / 체크 표시 / 낙서 중 하나만 고르도록 출력 형식을 고정했습니다.
  2. 같은 블록에 대해 규칙 신호를 따로 계산했습니다: 인식 텍스트 신뢰도, 블록 안에서 글자로 읽힌 획의 비율(글자 형태 비율), 영역 크기, 페이지 안 위치(여백·본문 위), 양식 칸(의견란·서명란·확인란)과의 겹침.
  3. VLM 판정과 규칙 판정이 같으면 확정하고, 엇갈리면 자동으로 정하지 않고 검수 대기로 보냈습니다.
  4. 낙서로 확정된 블록은 본문·메타데이터·색인 텍스트에서 빼고 '낙서 있음' 표시와 좌표만 남겼습니다. 원본 이미지는 그대로 두므로 판정이 틀려도 검수에서 되살릴 수 있습니다.
결과

낙서는 본문·메타데이터 텍스트로 들어가지 않고 메모는 버려지지 않도록 하는 이중 판정 구조를 설계했습니다. 자동으로 정하는 범위를 두 판정이 일치하는 블록으로 좁혀, 사람이 봐야 하는 영역만 검수로 넘기도록 했습니다.

가설을 하나씩 버린 과정

  1. 1
    페이지 전체를 OCR 한 번으로 인식
    수기 영역도 인쇄 본문과 같은 설정으로 읽음
    낙서 획이 'ㅡ'·'o' 같은 글자로 읽혀 본문 텍스트에 끼어들 수 있음
  2. 2
    전처리·이진화로 잡음 제거
    명암 기준으로 옅은 획을 지워 낙서를 없애려는 접근
    흐린 연필 메모·옅은 결재 의견까지 함께 지워질 수 있음. 지울 것과 남길 것을 픽셀 명암으로는 가를 수 없음
  3. 3
    VLM(Qwen3-VL) 단독 유형 분류
    블록 이미지만 주고 메모·낙서를 판정
    문맥 판단은 좋지만 짧은 체크 표시·숫자 정정처럼 작은 블록에서는 판정이 흔들리기 쉽고, 판정 근거를 남기기 어려움
  4. 4
    규칙 단독 판정
    인식 신뢰도·글자 형태 비율·영역 크기·위치 기준
    양식마다 칸 위치가 달라 규칙이 계속 늘고, 서명처럼 글자 형태가 약한 정상 수기를 낙서로 판정하기 쉬움
  5. 검출 + VLM 유형 분류 + 규칙 신호 이중 판정
    두 판정이 같으면 확정, 엇갈리면 검수 대기
    채택된 안: 자동 판정은 확신할 수 있는 블록에만 쓰고, 나머지는 사람이 확정

구조로 보기

배운 점

모델 하나의 답을 그대로 믿기보다 성격이 다른 두 판정을 맞춰 보고, 엇갈리는 곳만 사람에게 보내는 편이 안전했습니다. 자동화의 범위는 '확신할 수 있는 곳'까지로 정해야 합니다.

CASE 03 / 05정정추적

취소선·덧쓴 정정을 원문과 정정본으로 나눠 남기는 문제

문제 현황

정정 표기
  • 인쇄된 날짜·수량·이름 위에 줄을 긋고 손으로 정정
  • 그대로 읽으면 원문·정정값이 한 문자열로 이어짐
  • 취소선 때문에 원문 인식 자체가 깨짐
  • 어느 값이 현재 값인지 정해지지 않은 채 메타데이터로 감

원인 분석

블록 겹침
  • 취소선이 인쇄·수기 영역으로 동시에 잡혀 두 블록이 겹침
  • 덧쓴 정정은 작게 써서 원문 줄로 묶이기 쉬움
  • 공공기록은 고쳐진 원문도 기록이라 덮어쓰기 불가

해결 과정

이력 연결
  1. 겹친 곳을 정정 후보로 표시, 취소선·덧쓰기 여부 검출
  2. 취소선 원문은 지우지 않고 취소 표시와 함께 보존
  3. 정정 글자는 Qwen3-VL 로 판독, 원문과 수정 이력으로 연결
  4. 정규화·XML·JSON 에 원문·정정본 함께, 애매하면 검수 대기

결과

원문 보존
  • 원문을 잃지 않으면서 정정 내용은 메타데이터에 반영
  • 무엇이 어떻게 고쳐졌는지 수정 이력으로 따라가는 구조 설계
전체 설명 보기
문제 상황

공공문서에는 인쇄된 날짜·수량·이름 위에 줄을 긋고 위나 옆에 손으로 고쳐 쓴 정정 표기가 나옵니다. 그대로 인식하면 원문과 고친 값이 한 문자열로 이어지거나, 취소선 때문에 원문 글자 인식 자체가 깨집니다. 어느 값을 '현재 값'으로 볼지도 정해지지 않은 채 메타데이터에 들어가게 됩니다.

원인 분석

취소선은 인쇄 글자 위에 겹친 획이라 레이아웃 분석에서는 인쇄 영역으로, 필기 검출에서는 수기 영역으로 동시에 잡혀 같은 자리에 두 블록이 겹칩니다. 덧쓴 정정은 원문 바로 위·옆에 작게 써서 원문 줄로 묶이기 쉽습니다. 무엇보다 공공기록에서는 고쳐진 원문도 기록이라, 정정본으로 덮어쓰고 원문을 지우는 방식은 쓸 수 없었습니다.

해결 과정
  1. 인쇄 블록과 수기 블록이 겹치는 곳을 '정정 후보'로 표시하고, 겹친 획이 인쇄 글자를 가로지르는 선(취소선)인지 글자 위에 덧쓴 글씨인지 검출하도록 했습니다.
  2. 취소선이 그어진 인쇄 원문은 지우지 않고 그대로 인식해 '취소 표시'와 함께 보존했습니다.
  3. 근처의 수기 글자를 Qwen3-VL 로 정정 내용으로 판독하고, 원문 블록과 '수정 이력'으로 연결해 원문·정정본·좌표를 한 쌍으로 저장했습니다.
  4. Qwen3 메타데이터 정규화에는 정정본을 현재 값 후보로 넘기되 원문도 함께 주고, 어느 쪽인지 애매하면 검수 대기로 보냈습니다.
  5. XML·JSON 내보내기에 원문과 정정본을 둘 다 담아, 기관에서 해석 기준을 바꾸더라도 다시 처리하지 않고 쓸 수 있게 했습니다.
결과

원문을 잃지 않으면서 정정 내용이 메타데이터에 반영되고, 무엇이 어떻게 고쳐졌는지를 수정 이력으로 따라갈 수 있는 구조를 설계했습니다.

CASE 04 / 05서명판정

서명·날인·체크 표시를 낙서로 오판하거나 그 반대가 되는 문제

문제 현황

오판 위험
  • 서명·도장·체크 표시가 '글자 아니면 낙서' 규칙에 걸림
  • 여백의 동그라미·사인 연습은 서명·체크로 잘못 태깅 가능
  • '서명 있음'은 문서 효력 판단에 쓰여 오판 비용이 큼

원인 분석

위치 의미
  • 모양만으로는 서명·체크와 낙서를 가르는 기준이 약함
  • 실제 차이는 서명란·날인란·확인란 안에 있는가
  • 검출 모델은 위치만 찾고 양식상 의미는 모름

해결 과정

양식 칸 규칙
  1. 양식 칸 좌표·이름을 미리 뽑고, 서명·날인란 안의 검출은 확정
  2. 체크는 확인란·선택지와 겹칠 때만 선택 값, 칸 밖은 낙서 후보
  3. 칸 밖·양식 없는 문서는 Qwen3-VL 판정, 서명·체크면 검수 대기
  4. 서명·날인은 글자로 안 읽고 좌표와 '서명 있음'만 태깅

결과

서명 태깅
  • 서명·날인 좌표로 '서명 있음' 메타데이터를 남기는 구조
  • 서명이 낙서로, 낙서가 서명으로 가는 길을 양식 칸 규칙으로 막는 설계
전체 설명 보기
문제 상황

서명은 글자 형태가 약한 곡선이고, 도장은 둥근 무늬, 체크 표시는 짧은 V 자 획이라 '글자로 읽히지 않으면 낙서'라는 규칙에 그대로 걸립니다. 반대로 여백에 그린 동그라미나 끄적인 사인 연습은 서명·체크로 잘못 태깅될 수 있습니다. '서명 있음'은 문서의 효력을 판단할 때 쓰는 메타데이터라 오판의 비용이 컸습니다.

원인 분석

모양만 보면 서명·체크와 낙서를 가르는 기준이 약하고, 실제 차이는 '어디에 있느냐', 곧 서명란·날인란·확인란 안에 있는가에 있습니다. 서명·날인 검출 모델은 위치를 찾아 주지만 그 위치가 문서 양식에서 무슨 의미인지는 모릅니다.

해결 과정
  1. 레이아웃 분석 단계에서 양식 칸(서명란·날인란·확인란·선택지)의 좌표와 칸 이름을 미리 뽑아 두었습니다.
  2. 서명·날인 검출 모델(Detection)의 결과 상자를 양식 칸 좌표와 겹쳐 보고, 서명·날인란 안에 있으면 서명·날인으로 확정했습니다.
  3. 체크 표시는 확인란·선택지 칸과 겹칠 때만 해당 항목의 '선택 값'으로 해석하고, 칸 밖의 V 자·동그라미는 낙서 후보로 돌렸습니다.
  4. 칸 밖에 있거나 양식 칸이 없는 자유 서식 문서는 위치 규칙을 쓸 수 없으므로 Qwen3-VL 판정을 거치고, 서명·체크로 보이면 검수 대기로 보내 사람이 확정하게 했습니다.
  5. 서명·날인은 글자로 풀어 읽지 않고, 위치 좌표와 '서명 있음' 여부만 메타데이터로 태깅했습니다.
결과

서명·날인 위치를 좌표로 뽑아 '서명 있음'을 메타데이터로 남기는 구조를 만들고, 서명란 안의 서명이 낙서로 지워지거나 여백 낙서가 서명으로 태깅되는 경로를 양식 칸 규칙으로 막도록 설계했습니다.

구조로 보기

배운 점

모양이 같아도 '어디에 있는가'가 의미를 정합니다. 이미지 모델이 모르는 문서 양식 정보를 규칙으로 보태는 것이 하이브리드 설계의 핵심이었습니다.

CASE 05 / 05검수루프

메모·낙서 판정이 불확실한 수기 블록을 사람이 바로잡고, 그 교정으로 판정을 다듬는 문제

문제 현황

전수 검수 불가
  • 필기체·서명 인식 목표 85%, 인쇄체 98% 보다 낮음
  • 메모·낙서 판정도 자동만으로는 끝낼 수 없음
  • 100만 건 넘는 문서를 사람이 전부 볼 수는 없음
  • 고친 결과를 그 자리에서 버리면 같은 오판이 반복

원인 분석

기준 부재
  • 필기 신뢰도는 글씨체·스캔 품질·펜 색에 따라 크게 흔들림
  • 점수 하나로는 텍스트 오류인지 판정 오류인지 알 수 없음
  • '고치고 끝나는 화면'이면 비교할 기준 데이터가 안 쌓임

해결 과정

선별·기록
  1. 임계값 미만·판정이 엇갈린 수기 블록만 검수 대기로
  2. 검수 UI 에 원본·결과를 나란히, 하이라이트로 한 화면 교정
  3. 교정마다 고치기 전·후·유형·좌표·검수자를 기록
  4. 교정 기록을 평가 셋으로 쌓아 프롬프트·규칙·임계값 비교 후 반영

결과

개선 루프
  • 사람이 볼 수기 블록은 시스템이 고르는 구조
  • 교정이 다시 프롬프트·규칙 개선 근거가 되는 루프 설계
  • 필기체 85% 목표를 검수 데이터로 재는 기준
전체 설명 보기
문제 상황

필기체·서명 인식 목표는 85% 로, 인쇄체 98% 보다 낮게 잡혀 있었습니다. 글자 인식뿐 아니라 '이 블록이 메모인가 낙서인가'라는 판정도 자동만으로는 끝낼 수 없다는 뜻이지만, 100만 건이 넘는 문서를 사람이 전부 볼 수는 없습니다. 어느 수기 블록을 사람이 봐야 하는지를 시스템이 골라야 했고, 사람이 고친 결과가 그 자리에서 버려지면 같은 오판이 계속 반복됩니다.

원인 분석

필기 인식 신뢰도는 글씨체·스캔 품질·펜 색에 따라 크게 흔들리고, 점수 하나만으로는 텍스트가 틀렸는지, 메모·낙서 판정이 틀렸는지 정확히 알 수 없습니다. 또 검수 화면이 '고치고 끝나는 화면'이면, 분류 지시문이나 규칙을 바꿨을 때 실제로 나아졌는지 비교할 기준 데이터가 쌓이지 않습니다.

해결 과정
  1. 수기 블록마다 인식 신뢰도와 VLM·규칙 판정의 일치 여부를 함께 저장하고, 신뢰도가 임계값 미만이거나 판정이 엇갈린 블록만 검수 대기로 올렸습니다.
  2. 검수 UI 에서 원본 페이지와 인식 결과를 나란히 띄우고 해당 블록을 하이라이트해, 검수자가 텍스트 수정과 메모·낙서·서명·체크·정정 유형 변경을 한 화면에서 끝내게 했습니다.
  3. 모든 교정을 교정 기록(고치기 전·후 텍스트와 유형, 블록 좌표, 검수자)으로 남겼습니다.
  4. 교정 기록을 평가 셋으로 쌓아, VLM 분류 지시문(프롬프트)이나 규칙 신호 기준을 바꿀 때마다 같은 셋으로 다시 돌려 비교한 뒤 반영하도록 했습니다.
  5. 임계값도 평가 셋 결과를 보고 '검수량'과 '놓치는 오류' 사이에서 조정하도록 했습니다.
결과

사람이 볼 수기 블록은 시스템이 고르고, 사람이 고친 메모·낙서 판정과 텍스트는 다시 프롬프트·규칙 개선의 근거가 되는 루프를 설계했습니다. 필기체 85% 목표를 검수 데이터로 재는 기준도 이 기록에서 나옵니다.

구조로 보기

배운 점

검수 UI 는 사람이 고치는 화면이 아니라 정답을 모으는 장치입니다. 교정 기록이 쌓여야 모델·프롬프트를 바꿨을 때 정말 나아졌는지 말할 수 있습니다.

정리이 프로젝트에서 남긴 것

인쇄 본문과 수기 영역을 레이아웃 분석 직후 나눠 다른 경로로 읽고, 고쳐진 원문까지 수정 이력으로 남기는 구조를 폐쇄망 안에서 설계부터 납품까지 혼자 만들었습니다. 자동 확정은 두 판정이 같은 블록으로 좁히고, 나머지는 사람이 검수해 그 교정 기록으로 다음 판정을 다듬게 했습니다.
