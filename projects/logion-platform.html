개요대면 입출고를 키오스크 한 대로

운송기사가 출발 센터 사무실에서 신원·상차 정보를 센터 직원과 대면으로 확인하고 출력된 전표에 도장을 찍은 뒤, 도착지에서 다시 담당자를 찾아 내역을 확인해야 끝나던 업무였습니다. 복잡한 현장에서 눈으로 확인하다 보니 잘못된 전표를 수거하거나 담당자가 자리에 없어 업무가 밀리는 일이 잦았고, 야간에는 인력 배치와 피로가 휴먼 에러와 재고 불일치 위험으로 이어졌습니다. 이 과정을 키오스크 앞에서 끝나도록 바꾸는 것이 목표였습니다.

  • 목표: 24시간 무인 운영, 한 업무의 문제가 같은 기기의 다른 업무를 멈추지 않는 구조, 자주 바뀌는 업무 규칙·출력물 양식의 빠른 배포
  • 내 역할: 총괄 PM(기획·설계, 현업·고객사 요구 조율), 아키텍처 결정, 전 범위 백엔드 개발(인증·출고·입고·관리·자산 서비스, Kafka 이벤트, Vision AI 연동)
  • 일정: 기획·설계 2개월 → 구현·환경 구축 2개월 → 현업 요청 반영·고객사 초빙 검증·QA 2개월, 6개월 만에 1차 납품
  • 도입: 국내 대형 물류·식품 기업 10여 곳 도입·납품 진행(시범 도입 포함)
  • 대외: LOGION 특허·저작권 등록(2025~2026), 2025·2026 코리아매트 국제물류산업대전 출품·교육 세션

왜 MSA 였나선택 기준

처음 패키지 구조를 잡을 때, 하나의 서비스로는 이미 출하된 데이터의 상태 변경, 입고 즉시 확정·검토 후 승인·반려 같은 규칙 추가, 출력물 구성 항목 변경을 주기적으로 배포하며 유연하게 감당하기 어렵다고 판단했습니다. 결정적인 기준은 '24시간 무인'이었습니다.

업무 복잡도 격리

입고·출고·자산 관리는 생명주기가 다름. '양방향 물류' 특성상 로직 변경이 잦아 업무별로 따로 바꿀 수 있게 분리

장애 전파 차단

24시간 무인 운영. 입고 쪽 문제가 출고나 자산 관리까지 멈추게 하면 안 됨 → 같은 키오스크에서 다른 업무는 계속되는 구조

서비스 단위 배포

상차지시서·거래명세서·물류기기 이동전표 같은 출력물 구성 항목이 주기적으로 바뀜 → 바뀐 서비스만 서비스 단위 롤링 업데이트(서비스를 하나씩 차례로 올리고, 그동안 그 서비스만 잠시 멈춤)로 반영해 주간 배포가 가능한 구조. CI/CD 는 기획 단계부터 계획

선택적 확장

고객사·기기가 늘 때 부하가 몰리는 입고 검증·인터페이스 모듈만 골라 확장할 수 있도록 경계 설정

분리 순서두 단계로 나눈 경계

컨텍스트를 먼저 정의하고 경계를 나누니, 기능과 서비스가 많아도 책임이 일목요연하게 정리됐습니다. 1단계에서 화면과 공통 백엔드(인증·권한)·연동 영역을 떼어 내고, 2단계에서 출고·입고·관리자·자산관리 업무별로 백엔드를 나눠 공통 인증(Auth)과 함께 5개 컨텍스트가 됐습니다. 자동 빌드·배포도 처음부터 계획해, 초기 구축 때 관리 포인트는 늘었지만 서비스 단위 배포가 가능해졌습니다.

아키텍처5개 Bounded Context 와 이벤트 버스

API Gateway 뒤에 업무 경계별 다섯 서비스를 두고, 서비스 사이 데이터 흐름은 Kafka 이벤트로 이었습니다. 입고·출고 모두 키오스크에서 처리한 결과를 Kafka 이벤트로 넘겨 EAI 를 통해 고객사 ERP 와 내부 기간계 ERP 에 연동했습니다. 전표 인식은 Python·FastAPI 로 만든 Vision AI 연동 서버로 분리하고, 입고 서비스와는 인식 요청과 판독 결과를 Kafka 이벤트로 주고받았습니다. 업무 DB 는 Oracle, AI 관련 데이터는 Amazon Aurora 에 두었습니다.

  • Auth: JWT·키 구성 알고리즘, 외부 API 호출용 암호화, Spring Security 권한, 법인-센터 계정 테넌트
  • Delivery: 차량·도착지 기준 출고 생성, 출력물·인터페이스
  • Receipt: 입고 품목 연동, 전표 촬영 검증, 입고 확정·검토 상태 변경
  • Admin: 계정·공통코드·카테고리·발송지·도착지·출력물 관리
  • WPMS: ERP 가 없는 업체용 자산관리 — 집계·처리 현황·품목 마스터

핵심 흐름출고 한 건이 퍼지는 길

출고가 끝나면 한 이벤트가 기간계·고객사 연동, 자산 집계, 도착지 입고 검증 데이터, 관리자 현황으로 동시에 퍼집니다. '한 이벤트가 여러 연계 시스템으로 확장되는 구조'와 실패 시 재처리 요구가 Kafka 를 고른 이유였습니다. 도착지에서는 기사가 키오스크에서 입고 건을 불러 전표를 검증받고, 전표 인식 요청과 판독 결과도 Kafka 이벤트로 오갑니다.

입고 상태 전이즉시 확정과 검토

고객사마다 입고를 바로 확정할지, 관리자 검토 후 확정할지가 다릅니다. 고객사 설정으로 분기하고, 검토 건은 현장 관리자나 센터 직원이 관리자 페이지에서 알림을 받아 업로드된 전표와 인식된 인감 이미지를 보고 확정하거나 반려합니다.

데이터 모델출고 애그리거트

출고(Delivery)를 루트 애그리거트로 두고 품목·이력·출력물·내부/외부 연동·상태를 그 아래에 묶었습니다. 품목은 출고 없이 생길 수 없고, 이력과 출력물은 한 출고 기준으로 관리되며, 연동 결과나 관리자 결정으로 상태가 바뀔 때도 하위 엔티티와 함께 처리돼야 했기 때문입니다. 출고 업무의 무결성을 가장 오래 고민한 부분입니다. 입고·출고 모두 키오스크 처리 결과를 EAI 를 거쳐 고객사 ERP 와 내부 기간계 ERP 에 보냈고, 연동마다 결과를 따로 남겨 실패 건을 재전송할 수 있게 했습니다.

CASE 01 / 04장애대응

처리는 끝났는데 고객사 시스템엔 없던 출고 — 연동 타임아웃

문제 현황

장애 발생
  • 표준형 키오스크 첫 도입 고객사에서 발생
  • 키오스크 출고 처리는 정상 완료
  • 도착지 인터페이스·고객사 TMS/WMS 에는 미반영
  • 현장은 반영을 기다리며 대기 시간이 늘어남

원인 분석

원인 규명
  • 결과 파일·내부 출고 데이터·인터페이스 요청은 모두 정상
  • EAI 로그: 처리 시간 40초 초과 뒤 단순 실패 코드로 끝남
  • 직접 만든 예외 처리 프레임워크가 분류하지 못한 예외
  • 원인은 고객사 방화벽 정책 변경에 따른 네트워크 타임아웃

해결 과정

복구·보강
  1. 통화 녹음 텍스트화로 범위 산정, EAI 로그까지 단계별로 좁힘
  2. 고객사 IT 담당과 원인 확인 후 정책 업데이트 요청
  3. 관리자 페이지 재전송 기능으로 미반영 데이터 우선 동기화
  4. 예외 분류·로그 적재를 네트워크 영역까지 확장 배포, 고객사에도 예외 처리 요청

결과

당일 해결
  • 원인 규명부터 재발 방지 배포까지 당일 완료
  • 미반영 데이터는 재전송으로 정상화
  • 네트워크 타임아웃을 별도 예외 코드·로그로 분류
  • 서비스 운영 클레임 0건 유지
전체 설명 보기
문제 상황

표준형 키오스크를 처음 도입한 고객사에서, 키오스크 출고 처리는 정상 완료됐는데 도착지 인터페이스와 고객사 TMS/WMS 에는 반영되지 않았습니다. 현장은 반영을 기다리며 대기 시간이 늘었습니다.

원인 분석

결과 파일과 내부 출고 데이터는 정상이었고 인터페이스 요청도 생성돼 있었습니다. 이력·실패 로그와 EAI 로그를 대조하니 인터페이스 처리 시간이 40초를 넘긴 뒤 단순 실패 코드로 끝나 있었고, 직접 만든 예외 처리 프레임워크가 분류하지 못한 예외였습니다. 고객사 IT 담당과 확인한 결과 고객사 인프라·방화벽 정책 변경에 따른 네트워크 타임아웃이었습니다. 이 유형을 가를 예외 분류가 없었던 것이 우리 쪽의 약점이었습니다.

해결 과정
  1. 유선 접수 통화 녹음을 텍스트로 바꾸며 범위 산정 — 출고 업무 문제인지, 내부 처리 실패인지, 실패 결과를 고객사 시스템에 직접 반영할 수 있는지부터 확인
  2. 결과 데이터 → 인터페이스 환경 설정 → 이력·실패 로그 테이블 → EAI 로그 순서로 범위 축소
  3. 고객사 IT 담당과 원인 확인 후 정책 업데이트 요청
  4. 관리자 페이지에 원래 있던 재전송 기능으로 미반영 데이터 우선 동기화
  5. 커스텀 예외 핸들러와 예외 분류별 로그 적재를 네트워크 영역까지 확장, 일정 고지 후 자동화 배포
  6. 원인·조치 내역을 고객사에 공유하고, 고객사 TMS/WMS·ERP 통신 쪽에도 예외 처리 추가 요청
결과

원인 규명부터 우선 복구·재발 방지 배포까지 당일에 마쳤습니다. 미반영 데이터는 재전송으로 정상화했고, 네트워크 타임아웃이 별도 예외 코드와 로그로 분류되도록 바뀌었습니다. 원인은 고객사 쪽 정책 변경이었고 서비스 운영 클레임 0건을 유지했습니다.

CASE 02 / 04이벤트설계

출고 직후 상태가 뒤집히다 — 메시지 순서 역전

문제 현황

상태 불일치
  • 개발·스테이징·운영을 거치는 동안 발견
  • 출고 후 인터페이스·상태 변경이 동시에 일어나는 구간
  • 메시지 처리 순서가 뒤바뀌어 출고 상태 불일치

원인 분석

키 정책
  • Kafka 는 같은 파티션 안에서만 순서를 보장
  • 메시지 키 정책이 출고 단위로 정리되지 않음
  • 연동·상태 이벤트가 성격 구분 없이 함께 흐름
  • 같은 출고가 다른 파티션으로 가 늦은 상태가 먼저 반영될 수 있음

해결 과정

구조 개선
  1. 파티션 수를 늘리는 대신 이벤트 성격별 토픽 분리
  2. 메시지 키를 출고 시퀀스·ID 기반으로 재정의
  3. 같은 키로 중복 메시지를 걸러 멱등 처리
  4. 컨슈머 그룹을 인터페이스·상태·집계 역할별로 분리

결과

순서 보장
  • 같은 출고의 이벤트는 같은 키로 묶여 순서대로 처리
  • 다시 전달된 메시지도 걸러 한 번만 반영
  • 한 처리에 장애가 나도 영향이 그 역할 안에 머묾
전체 설명 보기
문제 상황

개발·스테이징·운영을 거치는 동안, 출고 이후 인터페이스와 상태 변경이 동시에 일어나는 구간에서 메시지 처리 순서가 뒤바뀌어 출고 상태가 어긋나는 문제가 나왔습니다.

원인 분석

Kafka 는 같은 파티션 안에서만 순서를 보장합니다. 메시지 키 정책이 출고 단위로 정리되지 않은 채 연동 이벤트와 상태 이벤트가 성격 구분 없이 흐르자, 같은 출고의 메시지가 서로 다른 파티션에서 처리되며 늦게 발생한 상태가 먼저 반영될 수 있었습니다.

해결 과정
  1. 파티션 수를 늘리는 대신 이벤트 성격별로 토픽 분리
  2. 메시지 키 생성 정책 재정의 — 출고 시퀀스·ID 기반 키로 같은 출고는 같은 파티션에서 순서대로 처리
  3. 같은 키로 중복 메시지를 걸러 멱등 처리
  4. 컨슈머 그룹을 인터페이스·상태·집계 역할별로 분리해 한 처리의 장애가 다른 처리로 번지지 않게 구성
결과

같은 출고의 이벤트는 같은 키로 묶여 순서대로 처리되고, 다시 전달된 메시지도 같은 키로 걸러 한 번만 반영되는 구조가 됐습니다. 컨슈머 그룹을 역할별로 나눠, 한 처리에 장애가 나도 영향 범위가 그 역할 안에 머물도록 했습니다.

구조로 보기

배운 점

순서는 파티션 수가 아니라 메시지 키가 정합니다. Kafka 는 어디까지 이벤트로 만들지 범위를 먼저 정하고, 순서와 재처리가 필요한 곳에 씁니다.

CASE 03 / 04대용량처리

자정마다 몰리는 집계 — 마감 배치를 이벤트로 나누다

문제 현황

부하 집중
  • 한 고객사만 해도 하루 수만 건 출하
  • 매일·월 마감 자정 일괄 집계로 스파이크성 부하
  • 집계가 끝나기 전에는 실시간 현황을 못 봄
  • 같은 마감일 고객사 데이터 동시 처리는 불안정

원인 분석

구조 한계
  • 집계가 마감 시각 한 점에 묶인 구조
  • 부하와 현황 공백이 같은 시각에 몰림

해결 과정

이벤트 집계
  1. Kafka 적용 범위를 연동·전표 인식·원장 집계 반영으로 정의
  2. Kafka Streams 로 이벤트를 받는 즉시 센터별 실시간 집계
  3. 문제가 생기면 다시 집계하는 재집계 경로 제공
  4. 고객사 증가에 맞춰 컨슈머·브로커 확장, 파티션 설계·모니터링

결과

실시간 현황
  • 센터 담당자·법인 관리자가 실시간 현황 확인
  • 문제 시 재집계로 바로잡을 수 있다는 고객 피드백
  • 일 평균 처리량 5만 → 10만 건↑(고객사 증가에 따른 변화)
전체 설명 보기
문제 상황

한 고객사만 해도 하루 수만 건의 출하가 생기는데, 매일 자정과 월 마감 자정에 집계를 몰아 돌리면 스파이크성 트랜잭션으로 부하가 커졌습니다. 집계가 끝나기 전에는 화면에서 실시간 현황을 볼 수 없었고, 같은 마감일을 쓰는 다른 고객사 데이터까지 함께 처리하기에는 불안정했습니다.

원인 분석

집계가 '마감 시각' 한 점에 묶여 있어 부하와 현황 공백이 같은 시각에 몰리는 구조였습니다.

해결 과정
  1. Kafka 적용 범위를 출고 후·입고 확정 후 인터페이스, 전표 인식 요청·판독 결과, 원장 발생 시 집계 반영으로 정의
  2. Kafka Streams 로 출고·원장 이벤트를 받는 즉시 센터별 실시간 집계
  3. 문제가 생기면 다시 집계할 수 있는 재집계 경로 제공
  4. 고객사가 빠르게 늘면서 컨슈머·브로커 확장, 장애 시 대응, 컨슈머 모니터링, 파티션 설계에 시간 투입
결과

센터 담당자와 법인 관리자가 실시간으로 현황을 보고, 문제가 생기면 재집계로 바로잡을 수 있다는 고객 피드백을 받았습니다. 처리량은 도입 초기 일 평균 5만 건에서 10만 건↑으로 늘었습니다.

배운 점

CASE 04 / 04아키텍처설계

나눈 서비스가 다시 엮이지 않게 — 장애 전파 차단

문제 현황

구조 위험
  • MSA 로 나누자 서비스 간 호출이 늘어남
  • 네트워크 지연·한 서비스 장애가 연쇄로 번질 위험
  • 24시간 무인 키오스크라 다른 업무가 멈추면 안 됨

원인 분석

동기 결합
  • 서비스 사이를 동기 호출로 잇는 구조
  • 외부 연동 같은 느린 구간의 지연이 핵심 업무 응답까지 전달

해결 과정

구조 전환
  1. 동기 호출을 줄이고 이벤트 기반 비동기로 전환
  2. 서비스 간 호출에 Circuit Breaker, 외부 연동과 핵심 로직 분리
  3. 헬스체크·APM·별도 로그 관제로 실시간 장애 감지
  4. 정기 업그레이드는 서비스 단위 롤링 업데이트로 진행

결과

클레임 0건
  • 업그레이드 중 그 서비스만 3~5분(헬스체크 포함) 멈추고 다른 업무는 계속
  • 비즈니스 API 응답 1~1.5초 이내(WhaTap APM, 광고 영상 API 제외)
  • 서비스 운영 클레임 0건 유지
전체 설명 보기
문제 상황

MSA 로 나누자 서비스 간 호출이 늘었고, 네트워크 지연이나 한 서비스 장애가 연쇄적으로 번질 수 있는 구조적 위험이 생겼습니다. 24시간 무인 키오스크에서는 한 업무 문제로 다른 업무까지 멈추면 안 됐습니다.

원인 분석

서비스 사이를 동기 호출로 이으면 외부 연동 같은 느린 구간의 지연이 핵심 업무 응답까지 그대로 전달됩니다.

해결 과정
  1. 서비스 간 동기 호출을 줄이고 이벤트 기반 비동기 구조로 전환
  2. 서비스 간 호출에 Circuit Breaker 를 걸어, 한 서비스가 느려지거나 멈춰도 호출하는 쪽까지 묶이지 않게 함
  3. 외부 인터페이스와 핵심 업무 로직을 분리해 연동이 실패해도 핵심 처리는 유지
  4. 서비스별 헬스체크 · APM 모니터링 · 별도 로그 관제로 장애를 실시간으로 감지
  5. 정기 업그레이드는 서비스 단위 롤링 업데이트(서비스를 하나씩 차례로 올리고, 그동안 그 서비스만 잠시 멈춤)로 진행
결과

정기 업그레이드 때 서비스를 하나씩 차례로 올리는 동안 그 서비스만 잠시(헬스체크 포함 3~5분) 멈췄고, 다른 업무는 계속 쓸 수 있었습니다. 서비스 운영 클레임은 0건을 유지했습니다. 납품 뒤 도입한 WhaTap APM 기준 비즈니스 API 응답은 1~1.5초 이내였습니다(광고 영상 API 제외).

배운 점

정리이 프로젝트에서 남긴 것

업무 경계를 먼저 나누고, 경계 사이는 이벤트로 잇고, 외부 연동에는 실패 건을 다시 보낼 경로를 두었습니다. 그 덕분에 정기 업그레이드 중에도 다른 업무는 계속 쓸 수 있었고, 고객사 쪽 연동이 실패했을 때도 출고 처리는 끝난 채로 미반영 건만 재전송으로 바로잡았습니다.
