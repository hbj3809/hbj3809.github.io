프로젝트 개요
무엇을, 왜 만들었나

온프레미스 k3s 와 이후 AWS EKS 위의 사내 플랫폼 층(게이트웨이·SSO·CI·인증서·시크릿·모니터링)을 인프라 담당으로 혼자 맡아 교체하고 하드닝했습니다. 호스트 33개를 Envoy Gateway 로 옮긴 전환은 같은 날 두 번 실패한 원인을 고쳐 세 번째에 중단 23.2초로 마쳤습니다. 30여 개 저장소의 평문 자격증명을 점검한 뒤 SealedSecrets 를 도입해 봉인 시크릿 39개를 만들었고, 인증서·권한·경보는 자동화·코드화한 뒤 검증 관문을 붙였습니다.

문제해결 사례 4개 보기

개요넘겨받은 클러스터의 플랫폼 층을 다시 세우기

입사 전에 구축된 온프레미스 k3s 클러스터를 넘겨받았을 때, 플랫폼 층에는 보안 지원이 끝난 인그레스 컨트롤러, 저장소와 설정에 흩어진 평문 자격증명, 여러 운영 도구가 함께 쓰는 SSO client, 손으로 복사하는 와일드카드 인증서, 지원이 끝난 관측 스택이 남아 있었습니다.

업그레이드 영향도부터 평가해 '고장 나면 전체가 멈추는가'를 첫 기준으로 우선순위를 세웠고, 서비스를 멈추지 않는 범위에서 하나씩 교체하며 모든 변경을 Git 과 검증 관문 위로 옮겼습니다. 이후 AWS EKS 이관(별도 사례) 때 같은 설계를 새 클러스터로 옮겼습니다.

    관측 스택 교체 착수지원이 끝난 로그·메트릭 스택을 7단계로 나눠 교체 시작
  2. 2026.06

  3. 2026.08

  • 목표: 중단을 최소로 한 교체 · 변경은 Git 으로만 · 사고는 재발 방지 장치까지 마무리
  • 내 역할: 조사·설계·실행 단독 수행. 시크릿 정리는 팀장 지시로 시작했고, 권한 대상·사고 복구 범위는 팀장·팀과 함께 결정
  • AI 활용: Claude Code(일부 Codex)로 조사·스크립트·읽기 전용 다중 에이전트 점검, 운영 변경·비밀값 입력·파괴 작업은 본인 승인·실행

플랫폼 구성진입·배포·인증·관측 네 경로

사용자 요청은 DNS 와 게이트웨이를 거쳐 서비스로, 코드 변경은 CI 와 GitOps 저장소를 거쳐 클러스터로 들어갑니다.

운영 도구는 사내 SSO 를 앱별 전용 client 로 쓰고, 권한은 Terraform 코드가 소유합니다. 메트릭과 로그는 공용 관측 플랫폼을 거쳐 팀 알림방 하나로 모입니다.

배포 흐름CI 에서 GitOps 까지

빌드 서버는 이미지를 만들어 올리고 매니페스트의 이미지 태그만 바꿉니다. 클러스터에 적용하는 일은 Argo CD 가 Git 을 보고 합니다.

EKS 로 옮기면서 docker.sock 이 없는 환경에 맞춰 kaniko 로 빌드하고, 레지스트리 접근을 워크로드 신원(Pod Identity)으로 바꿔 이미지 푸시용 정적 클라우드 키를 없앴습니다.

  • CI 서버 이관: 이미 만들어져 있던 신규 인스턴스가 옛 복사본이라 설정·잡이 어긋나 있어 차이분 복사 대신 홈 전체 복사, 도중에 끊기는 전송은 설정·잡 이력 단위로 나눠 전송
  • 인증·인가는 JCasC 로 SSO·역할 기반 인가 선언, 같은 호스트명 유지로 SSO 쪽 변경 0, 잡 45개 이관·첫 빌드 성공
  • EKS 재이관: 에이전트 템플릿에 kaniko 사이드카·Pod Identity 적용, 자사 빌드 잡 6종 전환
  • 자격 정리: Jenkinsfile 20개를 자격 저장소 바인딩으로 전환, 빌드 콘솔의 토큰 트레이스·에이전트 파드 정의 출력 차단
  • 코어 보안 업데이트: EKS 에서는 사전 렌더 대조·JDK 태그 고정·이미지 사전 pull·디스크 스냅샷·롤백 하한·canary 잡을 갖춰 31초 만에 정상 기동, 플러그인 112개 유지
  • 레지스트리 풀 시크릿(k3s): 네임스페이스마다 따로 넣던 것을 소스 한 곳에서 실사용 네임스페이스로 자동 복제하도록 단일화, 컷오버 전 AI 적대 감사로 결함을 먼저 고친 뒤 키 교체

게이트웨이 전환 절차실패를 막는 관문을 상태로

ingress-nginx 가 노드의 80·443 포트를 독점하고 DNS 가 와일드카드라 호스트를 하나씩 옮길 수 없었습니다. 그래서 새 게이트웨이는 다른 포트에서 병행 검증하고, 실제 전환은 포트를 한 번에 맞바꾸되 앞뒤를 관문과 자동 롤백으로 감쌌습니다.

아래 상태 흐름은 1·2차 실패 뒤 고친 3차 절차입니다.

  • 사전 게이트 4항목: 게이트웨이 클래스·리스너 포트·hostPort·데몬셋 존재를 확인하고, 하나라도 어긋나면 nginx 를 건드리지 않고 끝냄
  • 판정 기준: 'API 오브젝트가 사라졌는가'가 아니라 '포트가 실제로 비었는가'(소켓 해제)
  • 대기 시간: 단계마다 독립 예산(앞 단계가 시간을 다 써도 다음 단계가 돌도록)
  • 전환 전 준비: 설정 소스·라이브 값·실트래픽 로그 3단 대조로 외부 호출 경로 확정, 변환 도구(ingress2gateway)의 구현체별 출력을 비교해 Envoy Gateway 선정, 기본 출력이 업로드 크기·IP 허용 목록 같은 설정 일부를 경고 없이 버리는 함정 확인
  • 전환 후: 경로 인코딩(%2F) 정규화로 생긴 CI 화면 회귀 교정, 게이트웨이 지표 수집 신설, 설계는 이후 EKS 게이트웨이로 이식
  • 서비스 외부 공개 전 엣지 점검: 게이트웨이 구성을 병렬 감사해 공개 범위 밖 경로를 경로 단위로 차단하고 HTTPS 강제·HSTS·크롤링 차단·무인증 요청 레이트리밋을 GitOps 로 적용, 커밋 하나로 다시 잠글 수 있게 구성

SSO·접근 권한앱별 client 와 코드로 소유하는 권한

사내 SSO(Keycloak)는 개발 모드 단일 인스턴스로 돌고 있었고, 여러 운영 도구가 OIDC client 하나를 함께 써서 한 앱의 세션 설정이 다른 앱 전부에 번졌습니다. SSO 로 들어와도 Argo CD 권한은 비어 있었고 쿠버네티스 OIDC 권한은 Git 밖에 있었습니다.

client 를 앱마다 나누고, 권한은 Terraform 이 단일 소유하도록 옮긴 뒤 적용 전후 평가로 검증했습니다.

  • 사내 SSO 이관: 서비스 정지창 약 7분으로 전환
  • 앱별 전용 client: SSO 가 없던 Grafana·Airflow 는 전용 client·client role 로 새로 연동, EKS 이관 때 Argo CD·Jenkins·Headlamp 도 분리 → EKS 기준 SSO 연동 앱 5개 모두 전용 client
  • 앱마다 다른 클레임 이름(roles·groups)은 소스로 확인, Airflow 차트가 인증 설정을 마운트하지 않는 함정은 직접 마운트로 해결
  • 세션 끊김 정리: 대시보드가 몇 분마다 다시 로그인을 요구하던 문제는 라이브에만 있던 수동 설정으로 토큰 갱신이 꺼진 것이 원인이라 갱신 주기를 토큰 수명보다 짧게 고쳐 연속 사용 중 재로그인 요구가 사라진 것을 확인, 토큰 만료를 세션 만료로 쓰는 도구는 client 단위로만 수명을 바꿀 수 있어 '앱별 전용 client' 원칙의 계기가 됨
  • 권한 코드화: Argo CD issuer 오설정 수정과 Keycloak 그룹 기반 RBAC 구성 뒤 Terraform 단일 소유로 이전, 쿠버네티스 RBAC 는 라이브에서 떠서 코드화하고 kubectl diff·임퍼소네이션으로 검증, 이후 추가한 앱 한정 역할은 적용 전후 권한 평가 71건 기대 일치·재plan 드리프트 0(이 역할은 뒤의 권한 재편으로 정리)
  • 운영 모드 이관: 이중화·프로브·봉인 시크릿(새 값으로 회전)·관리 콘솔 IP 허용 목록으로 재구성하며 26.4→26.7.2, 컷오버 중 GitOps 자동 복구가 스케일을 되돌려 파드가 복원 전 DB 로 뜬 함정은 마이그레이션 변경 이력 수를 대조해 잡아 재마이그레이션
  • 이어받은 커스텀 확장(SPI): 라이브 jar 와 클래스 구성을 대조해 운영 소스를 특정하고 새 버전 API 변경에 맞춰 재빌드
  • 렐름 하드닝: 읽기 전용 다중 에이전트 검토로 권고 도출 → 계정 잠금이 외부인의 차단 수단이 될 수 있는 점을 반영해 적용 순서 재설계 → 사전 백업 후 단계별 승인 적용, 허용 목록 밖에서 경로별 차단·공개 예외 응답 확인
  • 사람 접근 권한: Terraform 명부 하나로 클라우드·클러스터 두 층에 함께 부여·회수, 재plan 드리프트 0
  • DB 사람 접근: 사람이 쓸 DB 계정이 사실상 없어 앱·관리자 계정을 쓰게 되던 구조를 권한 그룹과 사람별 읽기 전용 계정(타임아웃·연결 상한 포함)으로 바꾸고 로컬 접속 인증도 재시작 없이 강화, 연습 모드 SQL 생성기로 격리 리허설 뒤 운영 실행은 본인·판정은 AI 에이전트

경보 경로공용 관측 플랫폼과 감시 세 층

지원이 끝난 로그·메트릭 스택을 7단계로 나눠 교체해, 각 프로젝트가 라벨만 달면 수집·경보·대시보드가 붙는 공용 플랫폼으로 바꿨습니다.

데이터 파이프라인 쪽은 SLA 점검·작업별 실패 알림·Prometheus 규칙의 세 층이 같은 Teams 연결을 거쳐 알림방 하나로 모입니다. 경보 경로를 시험해 보니 '규칙이 있다'와 '알림이 도착한다'는 다른 일이어서, 경보 없이 지나가는 실패를 따로 목록으로 정리해 매일 확인 절차에 넣었습니다.

  • 7단계 교체: 격리 병행 설치·sidecar 대시보드·PrometheusRule CRD·로그 지표 기반 경보·시험 수신기로 라우팅 선검증·opt-in 컷오버·구 스택 제거
  • 모든 변경은 Argo CD 와 같은 필드 매니저로 서버 측 dry-run 을 통과한 뒤 반영
  • 1단계에서 드러난 결함 6건(무한 sync 루프 포함) 수정, 구 스택 제거 후 새 스택 영향 없음
  • 공용 플랫폼: 전 네임스페이스 감시 + 계약 라벨, 각 프로젝트가 자기 GitOps 에 ServiceMonitor·규칙·대시보드를 두면 자동 연결
  • EKS 이식: '경보 이름 = 라우팅 키' 계약 유지, 로그는 객체 저장소 백엔드 Loki·Alloy 수집, 수신기 시크릿은 Git 미경유, 실제 수신 경로 접수(HTTP 202) 확인
  • 액세스 로그 대시보드는 경로 정규화로 시계열 수를 줄임

공유 DB 사고 대응복구, 원인 규명, 재발 방지

개발용 공유 PostgreSQL 에서 커넥션 고갈로 SSO 가 멈추며 배포·운영 도구 로그인까지 막혔고, 별개로 데이터 디렉터리가 빈 채 초기화돼 SSO·서비스 DB 가 사라졌습니다. 두 사건의 인과는 확정하지 않았습니다.

복구를 주도하고, 원인을 찾아 고친 뒤 같은 일이 조용히 반복되지 않도록 백업과 경보를 붙였습니다. 백업이 없던 첫 소실분은 되살리지 못했고, 그 뒤로 '변경 전 백업'을 기본 절차로 삼았습니다.

  • 복구 범위는 팀이 정했고, 일부 마스터 DB 재생성 스크립트는 팀장이 작성
  • 원인 규명: 마운트 구조 분석으로 컨테이너 이미지가 선언한 볼륨 경로와 데이터 경로가 겹쳐 데이터가 익명 휘발 볼륨에 쓰이던 것을 확인
  • 재발 방지: 전 DB 정기 백업(DB 가 0개면 실패·경보), DB 다운·DB 개수 감소·커넥션 사용률 경보, SSO 설정 주간 백업(첫 실행 검증까지, 복원 리허설은 미실시)
  • 커넥션 진단: 소비자별 풀 상한 × 레플리카로 최악의 커넥션 수를 계산해 미사용 앱 정리·풀 상한 지정, 최악의 경우(추정)에도 한도 아래로 맞춤
  • 연동 로그인 실패는 인증 확장 jar 의 옛 API 호출과 노드별 jar 불일치를 찾아 재빌드·정리(인증 경로 정상 동작은 로그로 확인)

설계 결정왜 이렇게 했나

포트 분리 스왑

와일드카드 DNS 와 80·443 독점 때문에 호스트를 하나씩 옮길 수 없었습니다. 새 게이트웨이는 다른 포트에서 병행 검증하고, 전환은 포트를 한 번에 맞바꾸되 사전 게이트와 자동 롤백으로 감쌌습니다.

라우트가 아니라 게이트웨이에 정책

nginx 는 유휴 시간, Envoy 는 요청 전체 시간으로 타임아웃을 셉니다. 액세스 로그로 오래 걸리는 요청을 실측해 게이트웨이 단위 정책으로 흡수했고, 라우트 33개는 고치지 않고 새 라우트도 안전값을 이어받게 했습니다. 리스너는 와일드카드 하나로 둬 HTTP/2 를 유지했습니다.

라이브를 정본으로 대조한 뒤 GitOps 로

수동 helm values 저장소가 운영 상태와 어긋나 그대로 적용하면 운영 기능이 깨질 수 있었습니다. 운영 값을 정본으로 삼아 서버 측 dry-run diff 로 차이 0 을 확인한 뒤 Argo CD 로 넘겼습니다.

앱별 전용 OIDC client

client 하나를 나눠 쓰면 한 앱의 세션 설정이 다른 앱에 번집니다. 토큰 만료를 세션 만료로 쓰는 도구는 client 단위로만 수명을 바꿀 수 있다는 점도 계기였습니다. 앱마다 client 와 client role 을 따로 둬 설정과 권한의 영향 범위를 앱 하나로 줄였습니다.

권한은 코드가 소유하고 평가로 검증

Git 밖에 있던 권한은 라이브에서 떠서 Terraform 으로 옮겼습니다. 이후 추가한 앱 한정 역할은 적용 전 정책 파일과 적용 후 라이브에 같은 평가 71건을 돌려 기대와 일치하는지 확인했습니다.

DB 를 통째로 옮겨 서명 키 유지

SSO 를 운영 모드로 옮길 때 데이터베이스를 그대로 옮겨 토큰 발급자와 서명 키를 보존했습니다. 연동 앱 설정을 바꾸지 않고 전환하도록 한 설계입니다.

CA 는 길게, 서버 인증서는 짧게 자동 갱신

신뢰 기준(CA)과 갱신 주기를 분리하면 다음 갱신 때 클라이언트를 재시작할 필요가 없습니다.

시크릿 복제는 이미 쓰던 reflector

외부 시크릿 연동(ESO)은 워크로드 신원이 없는 온프레미스에서 이점이 사라졌습니다. 이미 와일드카드 인증서 복제에 쓰던 reflector 를 재사용하고, 소스가 단일 실패점이 되지 않게 갱신 지연 경보를 붙였습니다.

사람은 승인·비밀값, 에이전트는 조사·실행

운영 변경은 본인 승인 뒤 실행했습니다. 관리자 세션은 본인이 비밀번호를 넣어 열고 에이전트는 그 안에서만 실행했고, 노드 접속·자격 UI 변경·삭제는 사람이 직접 했습니다.

성과숫자로 본 결과

성과 숫자는 모두 실측값입니다. 게이트웨이 전환은 실패한 시도까지 함께 적습니다.

  • 게이트웨이: 호스트 33개 전환, 3차 중단 23.2초, 전환 후 40시간 5xx 0.021%(게이트웨이 기인 0건), 게이트웨이 지표 수집 신설
  • 시크릿: 30여 개 저장소 점검, SealedSecret 39개 작성·전환, Jenkinsfile 20개 자격 바인딩, 관리자 자격 3종 회전
  • SSO·권한: EKS 기준 운영 도구 5개 전용 client, 앱 한정 역할 권한 평가 71건 기대 일치·재plan 드리프트 0, Keycloak 26.4→26.7.2
  • 인증서: DNS 이전 검증 23/23, ingress 14건 자동 발급 전환, 기존 만료일보다 약 4개월 앞서 전환, 검색엔진 노드 재시작 0·SSL 오류 0
  • CI: 잡 45개 이관·첫 빌드 성공, LTS 업그레이드 31초 만에 정상 기동·플러그인 112개 유지, 자사 빌드 잡 6종 kaniko 전환
  • 관측: 7단계 교체, 1단계 결함 6건 수정, 구 스택 제거 후 새 스택 영향 없음
  • 공유 DB: 커넥션 99→33, 초기화 재현 때 사전 덤프로 DB 7개 복원, 이튿날 SSO·배포 도구 로그인 복구

CASE 01 · 플랫폼이관

인그레스 교체 — 같은 날 두 번 실패한 전환을 세 번째에 23.2초로

1문제 상황

보안 지원이 끝난 ingress-nginx 가 노드의 80·443 포트를 독점하고 DNS 가 와일드카드라 호스트를 하나씩 옮길 수 없었습니다. 운영 호스트 33개를 한 번에 Envoy Gateway 로 넘겨야 했고, 같은 날 1차·2차 시도가 실패해 자동 롤백됐습니다(계획 외 중단 약 62초·약 2분).

2원인 분석

1차: 게이트웨이를 운영 구성으로 바꿀 때 라이브만 직접 수정하고 매니페스트 생성기는 고치지 않아, 전환 순간 시험 구성으로 되돌아갔습니다(본인 작업 결함). 사전조건이 실패해도 nginx 정지 단계로 넘어가는 게이트가 없었고, 리허설도 실제 명령과 달랐습니다. 2차: nginx 종료 대기와 Envoy 서빙 대기가 같은 시간 예산을 나눠 써 서빙 대기 단계가 한 번도 돌지 못했고, 'API 오브젝트가 사라졌다'를 '포트가 풀렸다'로 오판했습니다. 나중에 재 보니 포트는 이미 비어 있었습니다.

3해결 과정
  1. 설정 소스·라이브 값·실트래픽 로그 3단 대조로 외부 호출 경로 확정, 변환 도구의 구현체별 출력 비교(기본 출력이 설정 일부를 경고 없이 버리는 함정 확인)
  2. 타임아웃 의미 차이(유휴 기준 vs 요청 전체 기준)를 액세스 로그로 실측해 게이트웨이 단위 정책 설계
  3. 1차 후: 생성기에 운영값 고정, nginx 정지 전 4항목 사전 게이트(하나라도 어긋나면 nginx 무접촉 종료), 리허설을 실제 명령과 똑같이
  4. 2차 후: 단계별 독립 대기 예산, 판정 기준을 소켓 실제 해제로 변경
  5. 유휴 노드에서 중단 없이 nginx 포트가 실제로 풀리는 시간을 다시 재 확인(처음 폴링은 매번 같은 값이 나와 측정 도구의 해상도를 잰 것으로 보고 고해상도 폴링으로 다시 잼)
  6. 3차: 중단 23.2초로 전환, 33개 호스트 응답 코드 대조, 40시간 관측 게이트 통과 후 Ingress 33개 정리(롤백 스냅샷 보존)
4결과

3차 시도 중단 23.2초로 호스트 33개 전환, 전환 후 40시간 5xx 0.021%(게이트웨이 기인 0건), 게이트웨이 지표 수집 신설. 설계는 이후 EKS 게이트웨이로 이식.

    우선순위 1순위로 선정·경로 확정업그레이드 영향도 평가에서 1순위, 3단 대조로 외부 호출 경로 확정
  2. PoC
    다른 포트에서 병행 검증타임아웃 의미 차이 실측, 게이트웨이 단위 정책 설계

  5. 실측

배운 점

'파일과 라이브가 같다'는 가정이 1차를, '오브젝트가 사라지면 포트도 풀린다'는 가정이 2차를 무너뜨렸습니다. 리허설은 실제 명령과 똑같이 하고, 판정은 대리 신호가 아니라 실제 상태(소켓)로 합니다. 측정 중 같은 값이 연속으로 나오면 대상이 아니라 측정 도구의 해상도를 잰 것인지 먼저 의심합니다.

CASE 02 · 보안점검

흩어진 평문 자격증명 — 참조 구조부터 바꾼 뒤 회전

1문제 상황

평문 자격증명이 저장소·클러스터 설정·위키에 흩어져 있었고 정본 점검 표는 빈 골격이었습니다. 배포 도구 관리자 비밀번호가 여러 저장소에 박혀 있고 많은 파이프라인이 이를 간접 참조해, 비밀번호만 바꾸면 파이프라인이 한꺼번에 깨지는 구조였습니다. 팀장 지시로 정리를 맡았습니다.

2원인 분석

클러스터에 봉인 수단이 없어 Git 에 시크릿을 둘 방법이 평문뿐이었고, 파이프라인이 자격 저장소 대신 값을 직접 참조하고 있었습니다.

3해결 과정
  1. 저장소마다 읽기 전용 AI 에이전트를 붙여 30여 개 저장소 병렬 스캔, 값은 출력하지 않고 위치·종류만 모으도록 설계(스캔 중 값이 섞인 임시 결과는 삭제)
  2. '공유 자격 재사용' 축으로 우선순위를 묶은 정본 점검 표 작성
  3. SealedSecrets 를 Argo CD 앱으로 도입하고 봉인→Secret 생성 흐름 검증, 데이터 플랫폼·EKS 까지 같은 관례 적용
  4. '자격 저장소 등록 → 바인딩 전환(동작 불변) → 카나리 빌드 → 회전' 순서로 Jenkinsfile 20개 전환
  5. 일괄 변환이 남긴 Groovy 문자열 보간(로그 마스킹 우회 위험)을 검사로 찾아 정리
  6. 관리자 자격 3종 회전 중 두 함정 해결: 비밀번호 환경변수를 첫 기동 때만 적용하는 도구는 DB 값까지 재설정, GitOps 자동 복구가 클러스터 직접 수정을 되돌리는 문제는 Git 경유로 재반영
4결과

30여 개 저장소 점검, SealedSecret 39개 작성·전환, Jenkinsfile 20개 자격 바인딩, 관리자 자격 3종 회전(파이프라인 손상 없음).

Jenkinsfile 자격 참조

카나리 빌드 성공 뒤 회전, 파이프라인 손상 없음

점검 → 봉인 → 참조 전환 → 회전 순서. 회전은 맨 마지막입니다.

배운 점

회전보다 참조 구조를 먼저 바꿔야 회전이 안전합니다. AI 가 한 일괄 변환도 검사 관문 없이 믿지 않습니다. 에이전트에게 시크릿 점검을 맡길 때는 '값 미출력' 규칙을 두되, 실제로 지켜졌는지 산출물을 다시 확인합니다.

CASE 03 · DevOps구축

만료본을 서빙하던 인증서와 '고장 대기' 검색엔진

1문제 상황

손으로 복사하던 와일드카드 인증서가 네임스페이스마다 세대가 갈라져 일부 서비스가 만료된 인증서를 서빙했고, 발급사의 만료 안내도 끊겨 있었습니다. 별도로 사내 검색엔진(Elasticsearch)의 내부 CA 와 서버 인증서가 동시에 만료됐습니다. 기존 연결이 살아 있어 상태는 green 이었지만 새 연결은 모두 실패해, 재시작 한 번이면 클러스터를 이루지 못하는 상태였습니다.

2원인 분석

차트가 기존 인증서 Secret 을 조회해 그대로 재사용하므로 helm upgrade 로는 갱신되지 않았습니다. dry-run 은 조회가 비어 새 인증서가 생기는 것처럼 거짓으로 보였고, CA 개인키가 저장되지 않아 기존 CA 로 서버 인증서만 다시 발급할 수도 없었습니다.

3해결 과정
  1. DNS 를 Route53 으로 이전: 메일 레코드 포함 23항목 검증 게이트 통과 후 네임서버 전환, 기존 레코드는 롤백용 보존
  2. Let's Encrypt DNS-01 와일드카드 발급, 발급 권한은 해당 zone 의 검증용 레코드로 한정, reflector 로 네임스페이스 복제해 ingress 14건 전환
  3. 만료 임박·발급 실패 경보와 인증서 대시보드로 알림 공백 해소
  4. 검색엔진: 같은 규격의 새 CA·서버 인증서로 Secret 을 제자리 교체, 인증서 파일 자동 리로드로 노드 재시작 없이 반영, 기동 때만 신뢰 저장소를 만드는 클라이언트 파드만 순서대로 재시작
  5. 같은 날 CA 키쌍을 SealedSecret 으로 보관하고 cert-manager CA Issuer 로 자동 갱신 이관
  6. 백업이 없던 검색엔진에 일일 논리 백업을 두고 객체 저장소에서 실제 복원까지 검증
4결과

DNS 이전 검증 23/23, ingress 14건 자동 발급 인증서로 전환, 기존 만료일보다 약 4개월 앞서 정리. 검색엔진은 노드 재시작 0·health green 유지·클라이언트 SSL 오류 0건.

  6. 6

배운 점

겉보기 green 은 '기존 연결이 살아 있다'는 뜻일 뿐입니다. dry-run 은 런타임 조회를 반영하지 못하니 판단 근거로 쓰지 않습니다. 신뢰 기준(CA)과 갱신 주기를 분리해 두면 다음 갱신 때는 아무것도 재시작하지 않아도 됩니다.

CASE 04 · 모니터링

경보가 약 32분 끊긴 배포 — '렌더 통과'와 '실제 파싱'의 차이

1문제 상황

관측 스택을 공용 플랫폼으로 교체한 뒤 경보 메일 템플릿을 개선해 배포했습니다. 템플릿은 AI 에이전트가 썼고 렌더 확인을 통과했다는 보고를 받은 상태였지만, 배포 직후 Alertmanager 가 재시작을 반복하며 모든 알림이 약 32분 끊겼습니다. 배포는 본인이 했습니다.

2원인 분석

Go 템플릿 주석 안의 '*/' 가 주석을 일찍 닫아 파싱이 실패했습니다. helm template 은 YAML 렌더만 검증하고 Alertmanager 템플릿 파싱은 검증하지 못합니다. 에이전트의 '렌더 통과' 보고를 배포본 기준으로 다시 확인하지 않은 것이 본질입니다.

3해결 과정
  1. 수정 커밋으로 복구
  2. 템플릿 변경은 배포본 기준 실제 파싱 검사 + 배포 직후 Alertmanager ready·로그 확인을 표준 관문으로 지정
  3. 템플릿 주석에 구분자 문자를 쓰지 않는 규칙 추가
  4. 날짜 조건이 걸린 경보는 promtool 가상 시계 시험으로 배포 전 증명(옛 규칙이 실패하는 것을 음성 대조군으로)
  5. EKS 이식 때도 같은 원칙으로 실제 수신 경로 접수(HTTP 202)까지 확인
4결과

약 32분 끊긴 알림을 수정 커밋으로 복구했고, 이후 템플릿·규칙 변경은 실제 파싱·기동 확인 관문을 거쳐 배포합니다.

배운 점

'검증했다'는 보고를 받으면 무엇을 검증했는지(렌더·파싱·기동)부터 확인합니다. 도구가 통과시킨 것과 운영에서 실제로 돌아가는 것은 다를 수 있어서, 관문은 배포본 기준으로 둡니다.

정리:이 프로젝트에서 남긴 것

실패가 드러난 자리마다 같은 일이 되풀이되지 않도록 관문을 하나씩 더했습니다. 두 번 실패한 게이트웨이 전환에는 사전 게이트와 소켓 기준 판정을, 약 32분 끊긴 경보에는 배포본 기준 파싱 검사를, 되살리지 못한 첫 DB 소실 뒤에는 변경 전 백업을 붙였습니다.
