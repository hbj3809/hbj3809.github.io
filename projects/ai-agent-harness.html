무엇을, 왜 만들었나

스타트업 개발팀에서 백엔드·데이터·인프라를 넓게 맡으며, AI 코딩 에이전트(Claude Code·Codex)가 저장소 관례·보안 규칙·지난 교훈을 지키며 일하도록 작업 규칙 3단·찾기→반박 다중 에이전트 검증·모듈 전체 시험 관문·권한 분리·기억 노트를 설계·운영했다. 2026년 6~10월 다중 에이전트 워크플로를 324회(에이전트 약 4,900개) 돌렸고 약 70%에 독립 반박 검증 단계를 넣었으며, 데이터 파이프라인·API 주요 변경 5건에서는 확정 결함 62건을 배포 전에 고쳤다. 병합과 운영 반영은 사람만 한다.

개요왜 하네스가 필요했나

스타트업 개발팀에서 백엔드·데이터 파이프라인·인프라를 넓게 맡으며 AI 코딩 에이전트(Claude Code·Codex)를 매일 썼다. 에이전트는 빠르지만 저장소의 관례도, 지난 사고도 모른 채 같은 실수를 되풀이할 수 있고, 결과의 질은 요청을 얼마나 자세하고 명확하게 쓰느냐에 따라 크게 갈린다.

그래서 매번 설명하지 않아도 에이전트가 같은 기준으로 일하고, 에이전트의 결론은 다른 에이전트·시험·사람이 다시 확인한 뒤에만 운영에 닿도록 작업 규칙·반박 검증·시험 관문·권한 분리·기억을 먼저 설계했다. 이 묶음을 하네스(harness)라고 부른다.

  • 기간: 2026.04 ~ 현재(다중 에이전트 워크플로는 2026.06부터)
  • 목표: 에이전트가 저장소 관례·보안 규칙·지난 교훈을 기본값으로 지키는 작업 환경, 사람에게는 검증을 통과한 결론만 올라오는 구조
  • 내 역할: 규칙 내용·워크플로 구성·발견 판정·반영 여부·병합 결정. 규칙 문서 본문·워크플로 스크립트·하위 에이전트 실행·기억 노트 기록은 에이전트 몫
  • 팀: 스타트업 개발팀. 기획·프론트엔드·우선순위 결정은 다른 구성원 몫이고, 하네스는 본인 작업 방식
  • 범위: 모델 학습·서빙이 아닌 LLM 에이전트를 활용한 개발·검증 방식 설계
  • 출발점: 이전 직장에서는 대화형 AI를 실패 케이스 시험용 목업 데이터 생성·로그 분석 보조로 주로 썼고, 에이전트에게 구현을 맡기면서 요청의 질이 결과를 가른다는 것을 체감

하네스 구성규칙·기억·실행·관문·사람

에이전트가 일을 시작할 때 읽는 규칙과 기억, 일을 나눠 맡는 실행 단위, 결과가 지나가야 하는 관문, 마지막 결정을 내리는 사람으로 나눴다. 규칙은 위층에서 아래층으로 갈수록 구체적이다.

  • 도구 전역: 역할·안전 수칙·비밀값 취급·응답 언어
  • 작업공간 공통: 기획서 대조 검증·시험 추가 의무·실제 DB·Redis 를 띄운 통합 시험 우선(목 위주 단위 시험보다)·시험 약화 금지·공통 모듈 승격·API 문서화(OpenAPI) 의무·등록/수정 메타 규칙. Claude Code용과 Codex용 파일을 같은 내용으로 두어 두 도구가 같은 규칙을 읽음
  • 저장소별: 모듈 전체 시험 단일 관문·테넌트 격리 체크리스트·외부 호출 서킷브레이커 의무·API 오류 응답 예시 의무·운영 함정 목록. 저장소 안에서 git 으로 관리(주력 저장소 224줄·46회 개정)
  • 기억: 작업 직후 남기는 주제별 노트 90여 개와 색인. 낡은 내용은 표시하고 정정 이력을 남김

핵심 흐름찾기 → 반박 → 종합

에이전트 하나에게 찾기와 검증을 함께 맡기면 그럴듯한 오답과 놓친 것을 거를 수 없다. 관점별 '찾기' 에이전트가 병렬로 발견을 내면, 처음부터 의심하는 독립 '반박' 에이전트가 코드를 다시 읽고 하나씩 판정한다. 살아남은 발견만 사람이 판정한다.

  • 발견 형식 고정: 찾기 에이전트는 정해진 JSON 형식으로만 보고해 판정·중복 정리가 쉬움
  • 판정: 주로 확정·기각·근거 부족(작업에 따라 '일부 성립'을 더함)
  • 종합·비판은 필요한 작업에만(모든 워크플로에 있는 단계는 아님)
  • 설계 작업 형식: 조사 3 → 설계안 3 → 심사 3 → 종합 → 비판
  • 구현 작업 형식: 구현 → 반박 검토 → 고침·PR. PR 단위 작업 폴더(git worktree)로 병렬 구현하고 앞 PR 위에 다음 PR 을 쌓음(stacked PR)
  • 적용 범위: 보안 점검·삭제 가드 사각 전수조사·장애 원인 조사·설계 심사

발견 하나가 거치는 상태

발견은 반박을 거쳐 확정·기각·근거 부족 중 하나가 되고, 확정된 것만 사람의 판정으로 넘어간다. 고칠지 미룰지는 사람이 정하고, 인프라·제품 결정이 필요한 항목은 따로 기록해 둔다.

변경 한 건이 운영에 닿기까지시험 관문과 병합

에이전트가 만드는 변경이 빠르게 늘면 일부 시험만 돌리거나 요약된 결과를 믿고 넘어갈 위험이 커진다. 그래서 변경이 같은 관문을 같은 순서로 지나도록 고정했다.

  • 모호한 점은 에이전트가 먼저 묻기: 사람 확인 질문 215회(남은 세션 기록 기준 하한)
  • PR 전 모듈 전체 시험: 실제 PostgreSQL·Redis 를 띄운 통합 시험(Testcontainers·embedded-redis) 통과, 통과·실패 수 원문을 매 PR 본문에 붙여 기록
  • 개별 커밋에서 관련 시험만 돌렸으면 그 사유와 결과를 커밋 메시지에 기록
  • 시험 약화 금지: 단언 완화·케이스 삭제·비활성화로 빨간 빌드를 넘기지 않음
  • 바뀐 파일만 골라 스테이징: 추적하지 않는 파일이 배포 산출물에 섞이는 것 방지
  • 2026.09부터 주력 저장소는 에이전트가 브랜치·커밋·푸시·PR 작성, 병합은 사람만. 병합 권한 검사는 우회하지 않음

사람과 에이전트의 역할 분리

에이전트의 실수가 그대로 운영에 반영되지 않도록, 되돌릴 수 있는 일과 되돌리기 어려운 일을 기준으로 역할을 나눴다.

  • 하위 에이전트의 일탈(작업 파일 덮어쓰기·저장소 설정 파일 접근·금지된 계산)은 즉시 복구·보고하고, 이후 고유 파일명 사용·하위 에이전트의 저장소 복제 금지 규칙을 추가

왜 이렇게 설계했나

규칙을 3단으로 나눈 이유

규칙이 한 파일에 몰리면 묻히고, 저장소마다 따로 쓰면 서로 어긋난다. 위층에는 어디서나 지킬 안전·비밀값 규칙을, 아래층에는 그 저장소만의 관례와 운영 함정을 두어 에이전트가 필요한 만큼 구체적인 규칙을 읽게 했다.

버그를 규칙으로 올린 이유

다음 세션의 에이전트가 같은 실수를 다시 밟지 않게 하려면 기억보다 규칙이 필요했다. 등록만 했는데 수정일이 채워지던 버그는 '등록 API 는 등록일·등록자만 쓴다'는 작업공간 공통 규칙이 됐고, CSV 한글 깨짐은 UTF-8 BOM 규약이 됐다. 주력 저장소 규칙(46회 개정)의 운영 함정 목록도 같은 방식으로 쌓였다.

반박 에이전트를 따로 둔 이유

평소 '안 되는 경우'부터 생각하며 실패 케이스 시험을 먼저 쓰던 방식과 같은 발상이다. 찾은 에이전트가 자기 발견을 다시 검증하면 의심하는 주체가 없으므로, 판정만 하는 에이전트를 따로 두고 처음부터 의심하게 했다. 반박 판정 2,335건 중 약 27%가 사람에게 오기 전에 기각됐다(판정 기록 기준).

시험을 단일 관문으로 묶은 이유

에이전트는 '통과했다'는 요약을 쉽게 만든다. 요약 대신 모듈 전체 시험의 실제 출력과 통과·실패 수를 남기게 하고, 시험을 느슨하게 고쳐 통과시키는 길은 규칙으로 막았다. 목 위주 단위 시험보다 실제 DB·Redis 를 띄운 통합 시험을 우선한 것도 같은 이유다.

병합을 사람에게 남긴 이유

커밋·PR 작성은 되돌릴 수 있지만 병합과 운영 반영은 영향이 바로 퍼진다. 손이 많이 가는 일은 에이전트에게, 되돌리기 어려운 결정은 사람에게 두었고 병합 권한 검사는 우회하지 않는다.

예약 점검을 읽기 전용으로 둔 이유

새벽 배치 확인을 사람 대신 맡기되, 점검 에이전트가 무언가를 고치기 시작하면 확인과 변경의 경계가 무너진다. 쓰기·배포·비밀값 출력을 금지하고 판정 보고서까지만 쓰게 했다.

주요 구현

기획서 대조 검증 절차

디자인 도구(Figma) 연동으로 기획 화면의 요소·유효성·동작 설명을 읽어 요청 검증·상태 전이·오류 코드·응답 필드·권한 규칙에 1:1로 대응시키고 구현됨·누락·불일치·프론트 소관으로 분류. 첫 적용에서 빠져 있던 기능을 반박 검증으로 확정하고 회귀 시험과 함께 구현.

읽기 전용 예약 점검 에이전트

단계별 운영 반영 기간에 전날 반영분의 기대값(배치 성공·마이그레이션 버전·파드 재시작·오류 로그·발화 경보)을 아침에 읽기 전용으로 확인하고 '기대 / 실측 / 판정' 표와 다음 단계 진행 가능 여부로 보고. 읽기 전용 트랜잭션·쿼리 시간 제한·비밀값 출력 금지·DB 시각 기준 판정이 절대 규칙. 예약 점검 에이전트 4개, 판정 보고서 6건. 한 판정에서는 미리 넣어 둔 대량 삭제 가드가 작동해 데이터가 보존된 것을 확인.

기억 노트와 색인

Claude Code 자동 메모리로 작업 직후 규약·교훈·사고 기록을 주제별 노트 90여 개와 색인으로 남김. 낡은 내용은 표시·정정하고, 진행 상황·도구 설명·하위 에이전트 결과까지 한국어로 통일해 새 세션이 과거 대화 대신 문서와 증거를 읽고 작업을 이어 가게 함.

입사 초 저장소 지도

입사 초 Codex 로 문서가 부족한 사내 저장소들을 읽혀 저장소별 에이전트 규칙 초안(기술 스택·명령·구조·위험 영역)과 저장소 지도·서비스 의존성 지도를 작성. 이 형식이 이후 저장소별 작업 규칙으로 이어짐.

팀과 함께 키우는 하네스

작업 규칙은 혼자 쓰는 설정이 아니라 팀에 공유했습니다. 저장소 규칙은 직접 작성하고 46회 개정했고, 도구의 새 기능과 외부 플러그인·라이브러리는 권장안을 내서 서로 리뷰하고 도입 시험을 한 뒤에 들였습니다.

CASE 01 / 04AI통합

에이전트 하나의 자기 검증을 믿지 않기 — 찾기와 반박을 나누다

문제 현황

검증 공백
  • 사람이 전부 다시 보기엔 범위가 넓음(보안 10개 축·여러 저장소)
  • 에이전트 자기 검증으론 거짓 양성과 누락을 거를 수 없음

원인 분석

역할 혼재
  • 찾기와 판정이 한 에이전트에 있어 의심하는 단계가 없음
  • 발견 형식이 제각각이라 판정·중복 정리가 사람 몫으로 남음

해결 과정

구조 전환
  1. 관점별 찾기 에이전트 병렬 실행, 발견은 정해진 JSON 형식
  2. 독립 반박 에이전트가 코드를 다시 읽어 확정·기각·근거 부족 판정
  3. 필요하면 종합·비판, 살아남은 발견만 사람이 판정해 시험과 함께 수정
  4. 설계는 조사·설계안·심사 세 갈래씩, 구현은 반박 검토 뒤 고침·PR

결과

사전 차단
  • 2026.06~10 워크플로 324회, 약 70%에 반박 단계
  • 반박 판정 2,335건 중 약 27%가 사람에게 오기 전 기각
  • 주요 변경 5건에서 확정 결함 62건 배포 전 반영
  • 공개 전 10개 축 보안 점검: 고위험 2건 포함 10건 수정
전체 설명 보기
문제 상황

에이전트가 만든 코드·설계·조사 결과를 사람이 전부 다시 보기에는 범위가 넓었다(보안 10개 축, 여러 도메인·저장소). 에이전트에게 스스로 검증하게 하면 그럴듯한 오답(거짓 양성)과 놓친 것(누락)을 거를 수 없었다.

원인 분석

찾는 역할과 판정하는 역할이 한 에이전트에 있어 발견을 의심하는 단계가 없었다. 발견 형식도 제각각이라 판정·중복 정리가 사람 몫으로 남았다.

해결 과정
  1. 관점(축·렌즈)마다 '찾기' 에이전트를 병렬로 두고 발견을 정해진 JSON 형식으로 내게 함
  2. 발견마다 처음부터 의심하는 독립 '반박' 에이전트가 코드를 다시 읽어 확정·기각·근거 부족으로 판정
  3. 필요한 작업에는 종합·비판 단계를 붙여 중복을 합치고 빠진 관점을 지적
  4. 살아남은 발견만 사람이 판정하고, 고칠 것은 시험과 함께 수정
  5. 설계 작업은 조사·설계안·심사를 각각 세 갈래로 돌린 뒤 종합·비판, 구현 작업은 구현 → 반박 검토 → 고침·PR 형식으로 정형화
결과

2026.06~10 워크플로 324회, 약 70%에 반박 단계. 반박 판정 2,335건 중 약 27%가 사람에게 오기 전에 기각됨(판정 기록 기준). 데이터 파이프라인·API 주요 변경 5건에서 확정 결함 62건을 배포 전에 반영했고, 서비스 공개 전 10개 축 보안 점검에서는 고위험 2건 포함 10건을 시험과 함께 수정. 다른 패치 리뷰에서도 일부 지적은 반증으로 기각돼 불필요한 수정을 피함.

CASE 02 / 04회고

'렌더 통과' 보고를 믿고 배포 — 경보 약 32분 중단

문제 현황

장애 발생
  • 에이전트의 템플릿 렌더 통과 보고를 믿고 그대로 배포
  • 경보 서버가 템플릿을 못 읽어 재시작 반복
  • 알림 약 32분 중단, 원인은 내 배포 변경

원인 분석

대상 불일치
  • 템플릿 주석 안 닫는 기호(*/)로 주석이 일찍 끝나 파싱 실패
  • Helm 렌더 확인은 설정 형식만 검증, 템플릿 문법은 못 봄
  • '통과' 보고의 검사 대상이 배포본과 같은지 확인 안 함

해결 과정

관문 추가
  1. 경보 서버 로그의 파싱 오류로 원인 확정, 주석 고쳐 복구
  2. 배포 전: 배포본 기준 실제 템플릿 파싱 검증
  3. 배포 직후: 경보 서버 준비 상태·로그 확인을 표준 관문으로
  4. 주석 안 특수 기호 금지 규칙화, '통과' 보고는 검사 범위까지 확인

결과

복구·절차화
  • 알림 약 32분 중단 뒤 주석을 고쳐 복구
  • 경보 템플릿 변경은 배포본 파싱 검증을 거치는 절차로 정리
  • 배포 직후 준비 상태·로그 확인도 같은 절차에 포함
전체 설명 보기
문제 상황

경보 메일 템플릿을 에이전트와 함께 고쳤고, 에이전트가 템플릿 렌더 검사를 통과했다고 보고해 그대로 배포했다. 배포 뒤 경보 서버가 템플릿을 읽지 못해 재시작을 반복했고 알림이 약 32분 끊겼다. 원인은 내 배포 변경이었다.

원인 분석

템플릿 주석 안에 주석을 닫는 기호(*/)가 섞여 주석이 일찍 끝났고, 경보 서버가 템플릿 파싱에 실패했다. 배포 도구(Helm)의 렌더 확인은 설정 형식만 검증하고 경보 서버의 템플릿 문법은 검증하지 못한다. 에이전트의 '통과' 보고가 무엇을 대상으로 무엇을 검사했는지, 배포본과 같은 대상인지 확인하지 않았다.

해결 과정
  1. 경보 서버 로그의 파싱 오류로 원인 확정, 주석을 고쳐 복구
  2. 배포 전: 배포본 기준 실제 템플릿 파싱 검증(Helm 렌더만으로 끝내지 않음)
  3. 배포 직후: 경보 서버 준비(ready) 상태와 로그 확인을 표준 관문으로
  4. 템플릿 주석 최소화·주석 안 특수 기호 금지를 기억 노트에 규칙으로 기록
  5. 에이전트의 '통과' 보고는 검사 대상과 범위까지 확인하는 원칙 추가
결과

알림 약 32분 중단 뒤 복구. 이후 경보 템플릿 변경은 배포본 파싱 검증과 배포 직후 준비 상태·로그 확인을 거치는 절차로 정리.

배운 점

CASE 03 / 04효율화

워크플로를 재개했더니 캐시가 하나도 안 먹었다 — 실행 기록에서 복구

문제 현황

부분 실패
  • 공개 전 대규모 감사 워크플로가 사용량 한도로 일부 실패
  • 재개하니 끝난 검증이 처음부터 다시 돌아 한도만 소모
  • 실패했던 검증엔 끝내 못 닿아 이상 징후를 보고 중단

원인 분석

기록 분석
  • 실행 기록 집계: 재개 때 호출 전부 새 캐시 키(재사용 0건)
  • 재개 캐시는 호출 순서가 같은 앞부분까지만 재생
  • 중첩 병렬 구조라 모든 관점이 동시에 검증 진입, 순서가 바뀜
  • 도구 내부가 아닌 실행 기록에 근거한 추론

해결 과정

기록 복구
  1. 낭비 확인 즉시 중단, 실행 기록의 시작·결과 짝 파싱
  2. 결과 형식으로 발견·판정 구분해 복구, 종합·비판은 직접 통합
  3. 중첩 병렬은 재개 대신 기록에서 복구, 재개 땐 순서 고정·단계 분리
  4. 낭비 징후(캐시 키가 모두 새것)가 보이면 즉시 중단

결과

재실행 회피
  • 재개 때 다시 시작된 호출 재사용 0건, 판정 중복 실행 확인
  • '중지됨·오류'로 보인 워크플로도 전부 완료 확인, 재실행 피함
  • 단순 구조는 재개 정상, 규칙 범위를 중첩 병렬로 좁힘
전체 설명 보기
문제 상황

서비스 공개 전 대규모 감사 워크플로가 사용량 한도에 걸려 검증 일부와 종합·비판 단계가 실패했다. 재개했더니 이미 끝난 검증이 처음부터 다시 돌아 한도만 소모했고, 정작 실패했던 검증에는 끝내 닿지 못했다. '처음부터 다시 도는 것 같다'는 이상 징후를 보고 중단시켰다.

원인 분석

실행 기록(저널)을 세어 보니 재개 때 시작된 호출이 모두 새 캐시 키였다(재사용 0건). 재개 캐시는 에이전트 호출 순서가 바뀌지 않은 앞부분까지만 재생되는데, 단계 안에 병렬을 중첩한 구조에서는 재개 때 정찰 결과가 즉시 캐시로 돌아와 모든 관점이 동시에 검증 단계로 들어가면서 호출 순서가 달라졌다. 도구 내부를 직접 본 것이 아니라 실행 기록에 근거한 추론이다.

해결 과정
  1. 낭비 확인 즉시 중단
  2. 실행 기록의 시작·결과 짝을 파싱해 결과를 형식으로 판별(발견인지 판정인지)하고 복구
  3. 남은 종합·비판은 직접 통합
  4. 규칙화: 중첩 병렬 구조는 재개 대신 실행 기록에서 복구, 재개가 필요하면 단일 병렬로 순서를 고정하거나 단계별로 워크플로를 분리
  5. 낭비 징후(시작 수가 재개 대상보다 훨씬 많고 캐시 키가 모두 새것)가 보이면 즉시 중단
결과

재개 때 다시 시작된 호출 전부가 새 캐시 키였고(재사용 0건) 이미 끝난 판정이 중복 실행된 것을 실행 기록으로 확인. 이후 진행 화면에 '중지됨·오류'로 보인 다른 워크플로도 실행 기록의 시작·결과 짝으로 전부 완료됐음을 확인해 불필요한 재실행을 피함. 구조가 단순한 워크플로는 재개가 정상 동작해 규칙 범위를 중첩 병렬 구조로 좁힘.

진행 순서

  1. 1차 실행
    한도로 일부 실패
    검증 일부·종합·비판 단계 실패
  2. 재개
    검증 단계 통째로 재실행
    정찰 결과만 캐시로 재생, 실패했던 검증에는 끝내 닿지 못함
  3. 중단
    이상 징후 확인 후 중단
    이미 끝난 검증이 다시 도는 것을 확인
  4. 분석
    실행 기록 집계
    재개 때 시작된 호출 전부가 새 캐시 키, 판정 중복 실행 확인
  5. 복구
    기록에서 결과 복구·직접 통합
    결과 형식으로 발견·판정 구분
  6. 규칙화
    재개 대신 복구 규칙
    중첩 병렬 구조 한정, 낭비 징후 시 즉시 중단

배운 점

도구의 재개·캐시를 믿기 전에 실행 기록으로 실제로 무엇이 재사용됐는지 센다. 대규모 작업은 처음부터 복구 가능한 순서로 짠다.

CASE 04 / 04검증설계

에이전트가 본 시각·네트워크가 실제와 다를 때

문제 현황

근접 사고
  • 시각: 로컬 시각 변환이 9시간 어긋나 '새벽'으로 오판
  • 시각: 평일 오후에 전 기간 대량 재처리를 요청
  • 네트워크: 웹 요청이 허용 목록에 든 사무실 네트워크로 나감
  • 네트워크: 사내 전용으로 잠근 주소를 '열림'으로 볼 뻔함

원인 분석

환경 불일치
  • 에이전트 환경(로컬 시각·사무실 네트워크)이 판정 대상과 다름
  • 에이전트는 그 차이를 스스로 알 수 없었음

해결 과정

근거 교체
  1. 시각: 미리 넣어 둔 업무시간 이중 확인 가드가 요청 단계에서 차단
  2. 시각: 판정은 클러스터·DB 시각으로만, 예약 점검 지시문에도 반영
  3. 네트워크: 게이트웨이 접근 로그로 출발지가 사무실 네트워크임을 확인
  4. 네트워크: 외부 도달은 라우트 단위 접근 제어 설정으로, 최종 확인은 사외망

결과

피해 없음
  • 재처리 요청은 실행되지 않아 부작용 없음
  • 외부 공개 판정은 설정 계층·사외망 확인으로 정리
  • 두 교훈 모두 기억 노트 규칙과 예약 점검 지시문에 반영
전체 설명 보기
문제 상황

근접 사고가 두 번 있었다. ① 에이전트가 로컬 시각 변환(TZ)이 9시간 어긋난 값을 보고 '새벽'이라 판단해 평일 오후에 전 기간 대량 재처리를 요청했다. ② 외부 공개 범위를 점검하던 에이전트의 웹 요청이 게이트웨이 허용 목록에 든 사무실 네트워크로 나가, 사내 전용으로 잠가 둔 주소를 '열림'으로 볼 뻔했다.

원인 분석

에이전트가 보는 환경(로컬 시각 변환, 사무실 네트워크)이 판정 대상(운영 시각, 외부 사용자의 위치)과 달랐고, 에이전트는 그 차이를 스스로 알 수 없었다.

해결 과정
  1. 시각: 재처리 요청은 본인이 앞서 운영 안전장치로 넣어 둔 업무시간 이중 확인 가드가 요청 검증 단계에서 차단
  2. 시각: 업무시간·스케줄 판정은 클러스터·DB 시각으로만 하도록 규칙화, 예약 점검 지시문에도 DB 시각 기준 반영
  3. 네트워크: 게이트웨이 접근 로그로 에이전트 요청의 출발지가 사무실 네트워크임을 확인
  4. 네트워크: 외부 도달 여부는 게이트웨이 라우트 단위 접근 제어 설정으로 확정하고, 최종 확인은 사외망에서 하는 원칙 수립
결과

재처리 요청은 실행되지 않아 부작용이 없었다. 외부 공개 판정은 설정 계층 확인과 사외망 확인으로 정리. 두 교훈 모두 기억 노트 규칙과 예약 점검 지시문에 반영돼 이후 작업에서 재사용.

배운 점

에이전트가 보는 시각과 네트워크 위치가 운영의 시각·외부 사용자의 위치와 같은지 먼저 묻는다. 되돌리기 어려운 작업 앞에는 에이전트와 무관하게 동작하는 가드를 둔다.

정리이 프로젝트에서 남긴 것

에이전트의 자기 검증, '통과' 보고, 워크플로 재개, 에이전트가 본 시각과 네트워크를 그대로 믿지 않고, 반박 에이전트·배포본 기준 검사·실행 기록·클러스터와 DB 시각·게이트웨이 설정처럼 바깥에서 다시 확인하는 길을 규칙과 절차로 남겼다. 되돌리기 어려운 병합과 운영 반영은 사람에게 두었다.
