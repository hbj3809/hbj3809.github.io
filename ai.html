How I build with AI

AI에게 맡기고, 사람이 검증합니다

스타트업 개발팀에서 백엔드·데이터·인프라를 넓게 맡으려면 AI 코딩 에이전트(Claude Code·Codex)가 필요했습니다. 그런데 에이전트는 저장소의 관례도, 지난 사고도 모른 채 같은 실수를 되풀이합니다.

그래서 에이전트가 안전하고 정확하게 일하도록 작업 규칙 · 반박 검증 · 시험 관문 · 권한 분리 · 기억을 먼저 설계했습니다. 이 구조를 하네스(harness)라고 부릅니다.

작업 규칙을 3단으로위에서 아래로 갈수록 구체적으로

규칙이 한 파일에 몰리면 묻히고, 저장소마다 따로 쓰면 어긋납니다. 도구 전역 → 작업공간 공통 → 저장소별로 나눠, 아래로 갈수록 구체적인 규칙을 두었습니다.

  • 기획서 대조 검증: 기획 화면의 요소·유효성·동작을 코드 위치에 1:1로 대응시켜 구현됨/누락/불일치로 분류한다.
  • 전체 시험 단일 관문: PR 전에 모듈 전체 시험(실제 DB·Redis·Kafka 를 띄운 통합 시험)을 통과하고 결과 원문을 남긴다. 단언 완화·케이스 삭제·비활성화로 빨간 빌드를 넘기지 않는다.
  • 버그를 규칙으로: "등록만 했는데 수정일이 찍힌다", "CSV 한글이 깨진다" 같은 실제 버그는 다음부터 반복되지 않도록 규칙으로 올렸다.

찾기 → 반박 → 종합그럴듯한 오답을 거르는 순서

에이전트 하나의 자기 검증으로는 그럴듯한 오답을 거를 수 없습니다. 관점별 에이전트가 병렬로 찾고, 처음부터 의심하는 독립 에이전트가 하나하나 반박한 뒤, 살아남은 것만 사람이 판정합니다.

  • 보안 감사·삭제 가드 전수조사·장애 원인 조사·설계 심사에 썼고, 반박 판정 중 약 27%는 사람에게 오기 전에 기각됐습니다(판정 기록 기준).
  • 데이터 파이프라인과 API 의 주요 변경 5건에서 확정 결함 62건을 배포 전에 고쳤습니다. 배포 직후 보강값이 되돌아갈 수 있던 치명 결함도 여기서 잡았습니다.
  • 운영 공개 직전 보안 감사에서는 10개 축을 병렬로 찾고 반박을 통과한 고위험 2건·중위험 8건만 시험과 함께 고쳤습니다.

실패에서 배운 것보고를 믿지 않고 관문을 만든다

"렌더 통과" 보고를 믿었다

에이전트가 렌더 검사를 통과했다고 보고한 경보 템플릿을 그대로 배포했다가, 주석 속 한 줄 때문에 경보 서버가 재시작을 반복해 알림이 약 32분 끊겼습니다. 이후 배포본 기준 실제 파싱 검사와 기동 확인을 별도 관문으로 두었습니다.

로컬 시계를 믿었다

에이전트가 9시간 어긋난 로컬 시각을 보고 업무 시간에 대량 재처리를 요청한 일이 있었습니다. 미리 넣어 둔 업무시간 가드가 막았고, 이후 시각 판정은 서버·DB 시각으로만 하게 했습니다.

사무실 네트워크에서 외부 확인을 했다

외부 공개 범위를 점검하던 에이전트의 요청이 허용 목록에 든 사무실 네트워크로 나가, 잠긴 주소를 "열림"으로 볼 뻔했습니다. 외부 도달 여부는 게이트웨이 설정으로 확정하고 최종 확인은 사외망에서 합니다.

재개하면 캐시가 먹을 줄 알았다

한도로 멈춘 대규모 워크플로를 재개했더니 이미 끝난 검증이 처음부터 다시 돌았습니다(재개 때 시작된 호출이 모두 새로 실행됨). 병렬을 중첩한 구조에서는 재개 대신 실행 기록에서 결과를 복구하는 절차를 만들었습니다.

LLM 서비스 설계로같은 원칙을 서비스에도

진행 중인 약국 AI Agent 서비스에서는 에이전트를 "업무 지침 + 허용 도구 + 문맥·상태 + 실행 루프"로 정의하고, 테넌트·승인·금액 계산은 모델이 아니라 서버 코드가 통제하도록 설계했습니다. 두 LLM 을 같은 업무 프로그램에서 모델만 바꿔 비교하고, 업무 성공률·수치 보존·도구 정확성·검색 품질·비용을 함께 재는 평가(고유 사례 100개 중 조정용 30개를 뺀 최종 70사례 × 2모델 × 3회 = 420회)를 준비하고 있습니다. 아직 실행 전이라 결과 숫자는 없습니다.

이 포트폴리오와 이력서 키트도 같은 방식으로 만들었습니다. 경력 기록에서 성과를 뽑는 에이전트와 그것을 반박하는 에이전트를 나눴고, 숫자는 출처와 분류(실측·보고·설문·추정·목표 등)를 붙여 사실 목록에 먼저 올린 값만 썼습니다.
